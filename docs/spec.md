## 1. ระบบนี้คืออะไร

Smart SRRT v2 คือระบบติดตามเหตุการณ์โรคและภัยสุขภาพของ **สำนักงานสาธารณสุขอำเภอ (สสอ.) หนึ่งแห่ง** ใช้ตั้งแต่รับแจ้งข่าว ตรวจสอบ มอบหมายงานให้หน่วยบริการลงพื้นที่ รับผลกลับ ติดตาม จนปิดเหตุการณ์

ระบบนี้ไม่ใช่ระบบเวชระเบียน ไม่ใช่เครื่องมือวินิจฉัย และไม่ได้เชื่อมกับระบบรายงานของกระทรวง ข้อมูลที่ต้องส่งให้หน่วยงานอื่นใช้การส่งออกไฟล์

### ปัญหาของระบบเก่าที่ v2 ต้องแก้

| ระบบเก่า | v2 |
|---|---|
| สถานะของเหตุการณ์คำนวณจากช่องในฟอร์มยาวหนึ่งฟอร์ม ผู้ใช้ไม่รู้ว่าขั้นถัดไปคืออะไร | ทุกขั้นเป็นปุ่มที่กดได้ และบันทึกลงไทม์ไลน์ของเหตุการณ์ |
| มอบหมายงานได้เฉพาะผู้ใช้ที่ล็อกอิน แต่คนลงพื้นที่คือหน่วยบริการที่ไม่ได้ล็อกอิน | มอบหมายงานให้หน่วยบริการเป็นหน่วย และหน่วยบริการล็อกอินมาบันทึกผลเอง |
| โมดูลไข้เลือดออก (D331) แยกตาราง แยกสิทธิ์ และไม่เขียนผลกลับไปที่เหตุการณ์ | ทุกโรคอยู่ในเหตุการณ์เดียว ขั้นตอนเฉพาะโรคเป็น "ชุดโรค" ที่เพิ่มได้โดยไม่แก้ตาราง |
| ไม่มีส่วนที่เกี่ยวกับ LINE ซึ่งเป็นช่องทางประสานงานจริง | ระบบเตรียมข้อความ LINE พร้อมลิงก์ไปที่งาน ผู้ใช้กดส่งเอง |
| หน้าจอแสดงรหัส UUID และสถานะภาษาอังกฤษ | หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดงรหัสภายใน |

## 2. ผู้ใช้

| บทบาท (`role`) | ใคร | ทำอะไรได้ |
|---|---|---|
| ผู้ดูแล (`admin`) | เจ้าหน้าที่ สสอ. มีได้มากกว่าหนึ่งคน | ทุกอย่าง: รับแจ้ง ตรวจสอบ ประเมินเกณฑ์ มอบหมายงาน รับผล ปิดเหตุการณ์ จัดการผู้ใช้ หน่วยงาน หมู่บ้าน และค่าตั้งระบบ |
| ผู้ใช้หน่วยบริการ (`unit`) | เจ้าหน้าที่ของ รพ.สต. รพ. หรือ สสช. แต่ละคนผูกกับหน่วยหนึ่งแห่ง | แจ้งเหตุการณ์ รับงานที่มอบหมายให้หน่วยของตน บันทึกผล แนบรูป เห็นเฉพาะเรื่องที่หน่วยของตนแจ้งหรือได้รับมอบหมาย |
| ผู้ดู (`viewer`) | บุคลากรของ สสอ. ที่ไม่ได้บันทึกข้อมูล เช่น สาธารณสุขอำเภอ | เห็นเหตุการณ์ ผู้ป่วย งาน ผล รูปถ่าย สรุป และหน้า "งานวันนี้" เท่ากับผู้ดูแล แก้ไขไม่ได้ ส่งออกได้เฉพาะตัวเลขสรุป และไม่เห็นหน้าตั้งค่า การจัดการผู้ใช้ กับบันทึกความปลอดภัย |
| บุคคลทั่วไป | ไม่ล็อกอิน | เห็นเฉพาะ Dashboard สาธารณะ (ข้อ 7) |

กฎการมองเห็นทั้งหมดบังคับที่ server หน้าจอซ่อนปุ่มเพื่อความสะดวกเท่านั้น ตารางสิทธิ์ละเอียดอยู่ใน [`schema.md` ข้อ 6](schema.md#6-กฎสิทธิ์การมองเห็น)

### การเข้าสู่ระบบ

- เข้าสู่ระบบด้วยบัญชี Google เท่านั้น ระบบไม่เก็บรหัสผ่าน
- อีเมลที่ไม่อยู่ในตารางผู้ใช้ หรือบัญชีที่ถูกระงับ เข้าระบบไม่ได้ ทั้งสองกรณีเห็นข้อความเดียวกัน: "บัญชีนี้ยังไม่มีสิทธิ์เข้าใช้ ติดต่อผู้ดูแลของ [ชื่อหน่วยงาน]" หน้าจอไม่มีปุ่มขอสิทธิ์ และไม่บอกว่าบัญชีถูกระงับ
- เครื่องหนึ่งเครื่องอยู่ในระบบได้ 7 วัน แล้วต้องยืนยันกับ Google ใหม่
- ผู้ใช้หนึ่งคนอยู่ในระบบได้หลายเครื่องพร้อมกัน ไม่จำกัดจำนวน การกดออกจากระบบมีผลกับเครื่องนั้นเครื่องเดียว
- เมื่อผู้ใช้เปิดลิงก์ของงานหรือเหตุการณ์ขณะยังไม่ได้ล็อกอิน ระบบพาไปหน้านั้นหลังล็อกอินสำเร็จ
- การล็อกอินด้วย Google ใช้ไม่ได้ในเบราว์เซอร์ในแอปของ LINE ลิงก์ในข้อความ LINE ที่ระบบเตรียมจึงเปิดในเบราว์เซอร์ของเครื่อง ([ข้อความ LINE](#ข้อความ-line)) เมื่อหน้าล็อกอินถูกเปิดในเบราว์เซอร์ในแอปของ LINE หน้านั้นบอกวิธีเปิดในเบราว์เซอร์ของเครื่อง
- หน้าที่ตอบผู้ที่ยังไม่ได้ล็อกอินมีเฉพาะชื่อระบบและชื่อหน่วยงาน ไม่มีโรค หมู่บ้าน หรือเลขที่เหตุการณ์ ทั้งบนหน้าจอและในข้อมูลที่ใช้สร้างตัวอย่างลิงก์ เพราะเซิร์ฟเวอร์ของ LINE เปิดลิงก์ที่ส่งในแชตเพื่อสร้างตัวอย่างลิงก์ ข้อยกเว้นมีหน้าเดียวคือ [Dashboard สาธารณะ](#7-dashboard-สาธารณะ) ซึ่งแสดงตัวเลขรวมบนหน้าจอ ส่วนตัวอย่างลิงก์ของหน้านั้นมีเฉพาะชื่อหน่วยงานและชื่อหน้า หน้า[คู่มือ](#คู่มือ)ของหน่วยบริการ หน้า[การคุ้มครองข้อมูลส่วนบุคคล](#การคุ้มครองข้อมูลส่วนบุคคล) และคำขอตรวจรุ่น ([ข้อ 8](#ชุดใช้งานจริงและชุดทดสอบ)) ตอบผู้ที่ยังไม่ได้ล็อกอินเช่นกัน และไม่มีข้อมูลของเหตุการณ์ ผู้ป่วย หรือผู้ใช้
- ที่อยู่หลักของระบบเปิดหน้าล็อกอินสำหรับผู้ที่ยังไม่ได้ล็อกอิน หน้าล็อกอินมีลิงก์ "ดู Dashboard สาธารณะ" เมื่อ Dashboard สาธารณะเปิดอยู่ และมีลิงก์ "คู่มือ" กับ "การคุ้มครองข้อมูลส่วนบุคคล" เสมอ

### บัญชีผู้ใช้

- หนึ่งบัญชีเป็นของคนหนึ่งคน และผูกกับอีเมล Google ของคนนั้น หน้าเพิ่มผู้ใช้และคู่มือระบุให้ใช้อีเมลส่วนตัวของแต่ละคน ไม่ใช้อีเมลกลางของหน่วยงาน ระบบตรวจไม่ได้ว่าอีเมลใดเป็นอีเมลกลาง
- ผู้ดูแลเพิ่มผู้ใช้ด้วยชื่อ อีเมล Google บทบาท และหน่วยงาน ไม่มีหน้าสมัครเอง
- ระบบไม่ส่งข้อความหรืออีเมลถึงผู้ใช้ใหม่ และไม่เตรียมข้อความเชิญ เจ้าหน้าที่ สสอ. แจ้งผู้ใช้เอง
- ผู้ดูแลคนแรกมาจากอีเมลที่ตั้งไว้ในค่าตั้งของ Apps Script ระบบสร้างบัญชีนี้เมื่อตารางผู้ใช้ว่างเท่านั้น
- ผู้ดูแลแก้ชื่อ อีเมล บทบาท และหน่วยงานของบัญชีได้ ผู้ใช้แก้ข้อมูลบัญชีของตนเองไม่ได้
- การแก้บทบาทหรือหน่วยงานมีผลตั้งแต่คำขอถัดไป เมื่อผู้ใช้หน่วยบริการย้ายหน่วย ผู้ดูแลแก้หน่วยงานของบัญชีเดิม ผู้ใช้เลิกเห็นงานของหน่วยเดิมและเห็นงานของหน่วยใหม่ งานและผลการทำงานที่บันทึกไว้ยังเป็นของหน่วยเดิม และยังแสดงชื่อผู้บันทึก
- การแก้อีเมลทำให้บัญชีออกจากระบบบนทุกเครื่อง และผูกกับบัญชี Google ของอีเมลใหม่เมื่อล็อกอินครั้งถัดไป ประวัติของบัญชียังอยู่ครบ
- ไม่มีการลบบัญชี ผู้ดูแลระงับบัญชีได้ และเปิดใช้บัญชีที่ระงับใหม่ได้ บัญชีที่ถูกระงับถูกปฏิเสธตั้งแต่คำขอถัดไปบนทุกเครื่อง ชื่อของบัญชีที่ระงับยังแสดงในไทม์ไลน์
- ผู้ดูแลสั่งให้บัญชีใดก็ได้ออกจากระบบบนทุกเครื่องได้ เช่น เมื่อมือถือหาย
- ผู้ดูแลระงับหรือเปลี่ยนบทบาทของบัญชีตนเองไม่ได้ ต้องให้ผู้ดูแลอีกคนทำ และระบบปฏิเสธการระงับหรือเปลี่ยนบทบาทของผู้ดูแลคนสุดท้ายที่ยังใช้งานอยู่ ระบบจึงมีผู้ดูแลอย่างน้อยหนึ่งคนเสมอ
- รายการผู้ใช้แสดงชื่อ อีเมล บทบาท หน่วยงาน สถานะ และเวลาที่เข้าระบบล่าสุด บัญชีที่ยังไม่เคยเข้าแสดงว่า "ยังไม่เคยเข้า"

## 3. ขั้นตอนของเหตุการณ์

เหตุการณ์หนึ่งรายการคือโรคหรือภัยหนึ่งอย่างในหมู่บ้านหนึ่งแห่ง เช่น "ไข้เลือดออก หมู่ 5 ตำบล ก" เหตุการณ์มีผู้ป่วยได้หลายราย และมีงานที่มอบหมายได้หลายงาน แต่ละเหตุการณ์มีเลขที่สั้น ๆ ที่อ่านได้ เช่น `2569-0012` ใช้แสดงบนหน้าจอและในข้อความ LINE

```
รับแจ้ง → ตรวจสอบข่าว → ประเมินเกณฑ์ → มอบหมายงาน → รับผล → ติดตาม → ปิดเหตุการณ์
```

| ขั้น | ใครทำ | ผลที่เกิด | สถานะหลังทำ (`stage`) |
|---|---|---|---|
| รับแจ้ง | ผู้ดูแล หรือหน่วยบริการ | สร้างเหตุการณ์ใหม่ | รอตรวจสอบ (`received`) |
| ตรวจสอบข่าว | ผู้ดูแล | บันทึกผล ตรวจสอบกับใคร และประเภทเหตุการณ์ | ตรวจสอบแล้วจริง (`verified`) หรือ ตรวจสอบแล้วไม่จริง (`not_confirmed`) |
| ประเมินเกณฑ์ | ผู้ดูแล | บันทึกว่าเข้าเกณฑ์สอบสวนโรคหรือไม่ ระบบแสดงเกณฑ์ของโรคนั้นให้อ่านประกอบ | กำลังดำเนินการ (`responding`) |
| มอบหมายงาน | ผู้ดูแล | สร้างงานให้หน่วยบริการหรือให้ สสอ. เอง พร้อมกำหนดเสร็จ และเตรียมข้อความ LINE | ไม่เปลี่ยน |
| รับงานและบันทึกผล | หน่วยบริการ หรือผู้ดูแลบันทึกแทน | บันทึกเวลาที่ทำจริง ผล และรูปถ่าย การรับงานไม่บังคับ | ไม่เปลี่ยน |
| รับผล | ผู้ดูแล | ทำเครื่องหมายว่าตรวจผลแล้ว | ไม่เปลี่ยน |
| ติดตาม | ผู้ดูแล และหน่วยบริการ | ทำซ้ำสามขั้นก่อนหน้าสำหรับงานรอบถัดไป และเพิ่มผู้ป่วยรายใหม่เมื่อพบ | ไม่เปลี่ยน |
| ปิดเหตุการณ์ | ผู้ดูแล | บันทึกสรุป ระบบเตือนถ้ายังมีงานค้าง และยกเลิกงานที่ยังไม่มีผลเมื่อผู้ดูแลยืนยัน | ปิดแล้ว (`closed`) |
| เปิดใหม่ | ผู้ดูแล | ต้องระบุเหตุผล | กำลังดำเนินการ (`responding`) |

การกระทำที่ทำได้นอกลำดับ

| การกระทำ | ใครทำ | ผลที่เกิด | สถานะหลังทำ (`stage`) |
|---|---|---|---|
| แจ้งเตือนข่าว | ผู้ดูแล | บันทึกว่าแจ้งผู้บริหารหรือผู้เกี่ยวข้องรายใด เมื่อไร และช่องทางใด เช่น แจ้ง สสจ. ทางโทรศัพท์ ทำได้หลายครั้ง | ไม่เปลี่ยน |
| แก้ไขข้อมูลเหตุการณ์ | ผู้ดูแล | ทำได้จนกว่าจะปิด เหตุการณ์ที่ปิดแล้วต้องเปิดใหม่ก่อน ไทม์ไลน์บอกว่าใครแก้ช่องใด | ไม่เปลี่ยน |
| แก้ผลการตรวจสอบ | ผู้ดูแล | เปลี่ยนเหตุการณ์ที่บันทึกว่าไม่จริงให้เป็นจริง ต้องระบุเหตุผล | ตรวจสอบแล้วจริง (`verified`) |
| ยกเลิก | ผู้ดูแล | ใช้กับเหตุการณ์ที่บันทึกผิดหรือซ้ำ ต้องระบุเหตุผล และอ้างเลขที่เหตุการณ์ที่ซ้ำได้ ข้อมูลไม่ถูกลบ | ยกเลิก (`void`) |

กฎของขั้นตอน

- ทุกการกระทำเพิ่มหนึ่งแถวในไทม์ไลน์ของเหตุการณ์ พร้อมผู้ทำ เวลาที่ทำจริง และเวลาที่บันทึก
- เวลาที่ทำจริงผู้ใช้กรอกเอง มีทั้งวันที่และเวลา ค่าตั้งต้นคือเวลาปัจจุบัน เวลาที่บันทึกระบบใส่ให้ หน้าจอแสดงให้เห็นเมื่อสองค่านี้ห่างกันมาก เพื่อให้รู้ว่าเป็นการบันทึกย้อนหลัง
- การเทียบกับกำหนดเสร็จและเป้าเวลาทุกจุดใช้เวลาที่ทำจริง
- ระบบไม่ปิดเหตุการณ์เอง
- การแก้ไขข้อมูลตรวจค่า revision ก่อนบันทึก ถ้ามีคนแก้ไปก่อน ระบบปฏิเสธและให้โหลดข้อมูลใหม่
- เวลาที่ทำจริงย้อนหลังได้ไม่จำกัด และเป็นเวลาในอนาคตไม่ได้
- เหตุการณ์ที่ตรวจสอบแล้วไม่จริง (`not_confirmed`) และเหตุการณ์ที่ยกเลิก (`void`) ไม่ถูกนับในสรุปใด ๆ มีข้อยกเว้นข้อเดียว: ตัวชี้วัดการตรวจสอบข่าวนับเหตุการณ์ที่ตรวจสอบแล้วไม่จริงด้วย เพราะเป็นข่าวที่ได้รับการตรวจสอบแล้ว ([ข้อ 6](#ตัวชี้วัดของมาตรฐานทีม))

### ข้อมูลของเหตุการณ์

- **ขอบเขต** ผู้ป่วยรายใหม่ของโรคเดียวกันในหมู่บ้านเดียวกันเพิ่มเข้าเหตุการณ์เดิม โรคเดียวกันในอีกหมู่บ้านเป็นเหตุการณ์ใหม่ เมื่อสร้างเหตุการณ์ที่โรคและหมู่บ้านตรงกับเหตุการณ์ที่ยังไม่ปิด ระบบเตือนและเสนอให้เพิ่มผู้ป่วยในเหตุการณ์เดิม ผู้ดูแลเป็นผู้ตัดสิน
- **พื้นที่** พื้นที่เกิดเหตุเป็นหมู่บ้านในอำเภอเท่านั้น เหตุการณ์ที่เกิดนอกอำเภอไม่บันทึกในระบบนี้
- **เลขที่เหตุการณ์** คือปี พ.ศ. ของวันรับแจ้งตามเวลาไทย ตามด้วยลำดับของปีนั้น ออกตอนสร้างและไม่เปลี่ยน เหตุการณ์ที่ยกเลิกหรือไม่จริงยังถือเลขเดิม เลขจึงมีช่องว่างได้
- **ตอนรับแจ้ง** กรอกเวลาที่ได้รับแจ้ง แหล่งข่าว โรค หมู่บ้าน สถานที่เพิ่มเติม และรายละเอียด ตัวเลือกของแหล่งข่าวมี "D506" สำหรับเรื่องที่ผู้ดูแลพบจากแบบรายงานการเฝ้าระวังทางระบาดวิทยาในรูปแบบดิจิทัลของกรมควบคุมโรค ระบบนี้ไม่เชื่อมต่อกับ D506
- **เมื่อหน่วยบริการแจ้งเหตุการณ์** แบบแจ้งมีสี่ช่อง: โรค หมู่บ้าน สถานที่เพิ่มเติม และรายละเอียด และเพิ่มผู้ป่วยได้ ระบบใส่เวลาที่ได้รับแจ้งเป็นเวลาที่กดส่ง และใส่แหล่งข่าวเป็นหน่วยบริการนั้น ผู้ดูแลแก้สองค่านี้ได้ หน่วยบริการเลือกหมู่บ้านใดก็ได้ในอำเภอ โดยหมู่บ้านในความรับผิดชอบของหน่วยแสดงก่อน ระบบไม่เตือนหน่วยบริการว่ามีเหตุการณ์ของโรคและหมู่บ้านเดียวกันอยู่แล้ว ผู้ดูแลเห็นคำเตือนนั้นตอนตรวจสอบข่าว หลังส่งแล้วหน่วยบริการแก้ไม่ได้ ผู้ดูแลเป็นผู้แก้ข้อมูลของเหตุการณ์
- **ประเภทเหตุการณ์** มีสองค่า: ผู้ป่วยเฉพาะราย และการระบาด ตรงกับชนิดของการสอบสวนในมาตรฐาน
- **การตรวจสอบข่าว** กรอกผล (จริงหรือไม่จริง) ตรวจสอบกับใครหรือหน่วยงานใด และหมายเหตุ
- **การแจ้งเตือนข่าว** เหตุการณ์ที่ตรวจสอบแล้วจริงและยังไม่มีการแจ้งเตือนข่าว แสดงในหน้า "งานวันนี้" เพราะมาตรฐานวัดสัดส่วนของเหตุการณ์ที่ได้แจ้งเตือน แถวอยู่จนมีการแจ้งเตือนข่าวครั้งแรกหรือปิดเหตุการณ์ ระบบไม่มีปุ่มบันทึกว่าไม่ต้องแจ้งเตือน เหตุการณ์ของโรคติดต่ออันตรายแสดงตั้งแต่รับแจ้ง โดยไม่รอการตรวจสอบข่าว
- **กำหนดเริ่มสอบสวน** เมื่อผู้ดูแลบันทึกว่าเข้าเกณฑ์ ระบบตั้งกำหนดเริ่มสอบสวนให้: 24 ชั่วโมงหลังรับแจ้งเป็นค่าทั่วไป และ 12 ชั่วโมงสำหรับโรคติดต่ออันตราย ผู้ดูแลตั้งค่ารายโรคได้ในรายการโรค
- **โรคติดต่ออันตราย** เหตุการณ์ของโรคกลุ่มนี้แสดงกำหนดเวลาตามกฎหมายบนหน้าเหตุการณ์: โทรแจ้งกรมควบคุมโรคภายใน 1 ชั่วโมงหลังได้รับแจ้ง เริ่มสอบสวนภายใน 12 ชั่วโมง และส่งสรุปรายงานสอบสวนภายใน 48 ชั่วโมงหลังพบผู้ป่วย ระบบรู้จากรายการโรค ผู้ใช้ไม่ต้องกรอกระดับความเร่งด่วนเอง
- **จำนวนผู้ป่วยและผู้เสียชีวิต** ผู้ดูแลกรอกและแก้ได้ ใช้กับเหตุการณ์ที่มีผู้ป่วยมากจนไม่ใส่รายชื่อครบ รายชื่อผู้ป่วยใส่เฉพาะรายที่ต้องติดตามหรือมอบหมายงานรายคน ตัวเลขสรุปใช้ค่าที่มากกว่าระหว่างจำนวนที่กรอกกับจำนวนรายชื่อ
- ช่องของระบบเก่าเรื่องการสอบสวนโรคและการดำเนินการตามมาตรการไม่มีในเหตุการณ์ เพราะเป็นงานที่มอบหมายและผลการทำงาน
- ช่อง "การเฝ้าระวัง" และ "ระดับความเสี่ยง" ของระบบเก่าไม่มีใน v2 มาตรฐานระดับอำเภอไม่ได้ให้บันทึกสองค่านี้รายเหตุการณ์

ที่มาของกำหนดเวลา ประเภทเหตุการณ์ และการแจ้งเตือนข่าว อยู่ใน[ผลการค้นมาตรฐาน](research/event-handling-standards.md)

### ผู้ป่วยในเหตุการณ์

ระบบเก็บข้อมูลผู้ป่วยเท่าที่ใช้หาบ้านผู้ป่วย นับเวลาของชุดโรค และนับจำนวนผู้ป่วยกับผู้เสียชีวิต แบบสอบสวนโรคและการแจ้งโรคตามกฎหมายทำนอกระบบ ([ผลการค้นมาตรฐาน ส่วนที่ 7](research/event-handling-standards.md))

- **ข้อมูลที่เก็บ** ชื่อ-สกุล อายุ เพศ บ้านเลขที่ หมู่บ้าน วันเริ่มป่วย การวินิจฉัย เวลาที่พบผู้ป่วยหรือวินิจฉัย และสถานที่รักษา
- **สภาพผู้ป่วย** ไม่บังคับ มีสี่ค่า: ยังรักษาอยู่ หาย เสียชีวิต และไม่ทราบ
- **ประเภทผู้ป่วย** ไม่บังคับ มีสามค่า: สงสัย เข้าข่าย และยืนยัน ค่าตั้งต้นคือสงสัย
- **อายุ** กรอกเป็นปี ผู้ป่วยอายุต่ำกว่า 1 ปีกรอกเป็นเดือน
- ระบบไม่เก็บเลขบัตรประชาชน HN เบอร์โทร สัญชาติ อาชีพ อาการรายข้อ และผลตรวจ
- **ที่อยู่** ผู้ป่วยแต่ละรายมีหมู่บ้านของตนเอง ซึ่งต่างจากหมู่บ้านของเหตุการณ์ได้ ผู้ป่วยที่อยู่นอกอำเภอเลือก "นอกอำเภอ" แล้วพิมพ์ที่อยู่
- **ผู้เพิ่ม** ผู้ดูแลเพิ่มผู้ป่วยได้ทุกเหตุการณ์ หน่วยบริการเพิ่มได้ตอนแจ้งเหตุการณ์ และในเหตุการณ์ที่หน่วยมีงานที่ยังไม่ถูกยกเลิก หน้าเหตุการณ์แสดงว่ารายใดเพิ่มโดยหน่วยบริการ
- **รับทราบ** ผู้ป่วยที่หน่วยบริการเพิ่มหลังการตรวจสอบข่าวแสดงในหน้า "งานวันนี้" จนกว่าผู้ดูแลจะกด "รับทราบผู้ป่วย" หรือมอบหมายงานที่ผูกกับผู้ป่วยรายนั้น ผู้ป่วยที่หน่วยบริการเพิ่มมาพร้อมการแจ้งเหตุการณ์ถือว่าผู้ดูแลรับทราบตอนตรวจสอบข่าว
- **แก้ไข** ผู้ดูแลแก้ข้อมูลผู้ป่วยได้จนกว่าเหตุการณ์จะปิด หน่วยบริการแก้ไม่ได้หลังบันทึก เมื่อผู้ดูแลแก้เวลาที่พบผู้ป่วยหรือวินิจฉัย ระบบคำนวณเวลาที่ควรแจ้งหน่วยบริการภายในของงานของชุดโรคที่ผูกกับผู้ป่วยรายนั้นใหม่ กำหนดเสร็จของงานไม่เปลี่ยน เพราะนับจากเวลาที่หน่วยบริการได้รับรายงาน ([ข้อ 5](#5-ชุดโรค))
- **ยกเลิก** ผู้ดูแลยกเลิกผู้ป่วยที่เพิ่มผิดได้ โดยระบุเหตุผล ผู้ป่วยที่ยกเลิกไม่ถูกลบและไม่ถูกนับ ไม่มีการย้ายผู้ป่วยข้ามเหตุการณ์ ถ้าผู้ป่วยรายนั้นมีงานที่ผูกอยู่และยังไม่มีผลการทำงาน ระบบแสดงรายการ และยกเลิกงานเหล่านั้นเมื่อผู้ดูแลยืนยัน ด้วยเหตุผล "ยกเลิกผู้ป่วย" งานที่มีผลแล้วอยู่ต่อ และไม่ถูกนับในผลการเทียบเป้าของชุดโรค กฎนี้ใช้กับงานทุกชนิดที่ผูกกับผู้ป่วย
- **ผู้ป่วยซ้ำ** เมื่อชื่อ-สกุลตรงกับผู้ป่วยที่มีอยู่ในเหตุการณ์เดียวกัน ระบบเตือนก่อนบันทึก และผู้ใช้ยืนยันได้ถ้าเป็นคนละคน ระบบไม่ค้นชื่อข้ามเหตุการณ์
- **ผู้เสียชีวิต** เหตุการณ์ที่มีผู้ป่วยเสียชีวิตแสดงก่อนเหตุการณ์อื่นในทุกกลุ่มของหน้า "งานวันนี้" รองจากเหตุการณ์ของโรคติดต่ออันตราย ถ้าเหตุการณ์นั้นถูกประเมินว่าไม่เข้าเกณฑ์ ระบบเสนอให้ประเมินเกณฑ์ใหม่ในกลุ่ม "รอประเมินเกณฑ์" และไม่เปลี่ยนผลเอง
- **ประเมินเกณฑ์ใหม่** ผู้ดูแลประเมินเกณฑ์ซ้ำได้ก่อนปิดเหตุการณ์ เมื่อผลเปลี่ยนเป็นเข้าเกณฑ์ กำหนดเริ่มสอบสวนนับจากเวลาที่ประเมินใหม่
- ไทม์ไลน์และข้อความ LINE เรียกผู้ป่วยด้วยลำดับในเหตุการณ์ เช่น "ผู้ป่วยรายที่ 2"
- ชื่อและบ้านเลขที่เห็นได้เฉพาะบุคลากรของ สสอ. (ผู้ดูแลและผู้ดู) หน่วยบริการที่ได้รับมอบหมายงานของผู้ป่วยรายนั้น และหน่วยบริการที่เพิ่มผู้ป่วยรายนั้นเอง

### งานที่มอบหมาย

- งานหนึ่งงานผูกกับเหตุการณ์เสมอ และเลือกผูกกับผู้ป่วยรายใดรายหนึ่งได้
- งานมีชนิด ผู้รับงาน คำสั่งเพิ่มเติม กำหนดเสร็จ และสถานะ: มอบหมายแล้ว (`assigned`) → รับงานแล้ว (`accepted`) → บันทึกผลแล้ว (`done`) งานที่ถูกยกเลิกมีสถานะยกเลิก (`cancelled`)
- **มอบหมายงาน** ทำได้เมื่อเหตุการณ์กำลังดำเนินการ คือหลังประเมินเกณฑ์ ไม่ว่าผลเป็นเข้าเกณฑ์หรือไม่ ผู้ดูแลเลือกผู้รับงานได้หลายหน่วยในครั้งเดียว และระบบสร้างหนึ่งงานต่อหนึ่งหน่วย
- ระบบเสนอหน่วยบริการที่รับผิดชอบหมู่บ้านของเหตุการณ์หรือของผู้ป่วยให้อัตโนมัติ ผู้ดูแลเปลี่ยนได้ เมื่อเหตุการณ์มีผู้ป่วยรายเดียว แบบมอบหมายงานเลือกผู้ป่วยรายนั้นให้ก่อน ผู้ดูแลเอาออกได้
- **กำหนดเสร็จ** บังคับกรอก ค่าตั้งต้นของงานสอบสวนโรคคือกำหนดเริ่มสอบสวนของเหตุการณ์ ถ้าเหตุการณ์ไม่มีกำหนดเริ่มสอบสวน และสำหรับงานชนิดอื่น ค่าตั้งต้นคือสิ้นวันถัดไป งานของชุดโรคใช้กำหนดเสร็จตามชุดโรค (ข้อ 5)
- **ชนิดงานกลาง** มีสี่ชนิด ใช้ได้กับทุกเหตุการณ์: สอบสวนโรค ควบคุมโรค ติดตามผู้สัมผัส และอื่น ๆ ชุดโรคเพิ่มชนิดงานและแบบบันทึกผลของตัวเอง (ข้อ 5)
- **แบบบันทึกผลกลาง** มีสองช่อง: เวลาที่ทำจริง และสรุปผล งานสอบสวนโรคมีช่องเพิ่มหนึ่งช่องที่ไม่บังคับ คือเวลาที่เขียนรายงานสอบสวนเบื้องต้น ซึ่งเติมภายหลังได้ด้วยการแก้ผล เวลาที่ทำจริงของงานสอบสวนโรคคือเวลาที่ออกสอบสวน สองค่านี้ใช้คำนวณความทันเวลาตามมาตรฐาน ([ผลการค้นมาตรฐาน](research/event-handling-standards.md) ส่วนที่ 8) ผู้ดูแลเริ่มเขียนรายงานนี้จากไฟล์ที่ระบบเตรียมให้ได้ ([ร่างรายงานสอบสวน](#ร่างรายงานสอบสวน))
- **งานของ สสอ.** ผู้ดูแลมอบหมายงานให้ สสอ. เป็นผู้รับได้ เช่น งานสอบสวนโรคที่ทีมของ สสอ. ทำเอง งานนี้ไม่มีขั้นแจ้งหน่วยบริการ รับงาน และรับผล ผู้ดูแลเป็นผู้บันทึกผล
- **แก้งาน** ผู้ดูแลแก้คำสั่งเพิ่มเติมและกำหนดเสร็จได้จนกว่างานจะมีผลการทำงาน ผู้รับงานเปลี่ยนไม่ได้ ผู้ดูแลยกเลิกงานแล้วมอบหมายใหม่
- **ยกเลิกงาน** ผู้ดูแลยกเลิกงานที่ยังไม่มีผลการทำงานได้ โดยระบุเหตุผล งานที่มีผลแล้วยกเลิกไม่ได้ หน่วยบริการเลิกเห็นเหตุการณ์และผู้ป่วยจากงานที่ถูกยกเลิก
- **ปิดเหตุการณ์ขณะมีงานค้าง** ระบบแสดงรายการงานค้างก่อนปิด เมื่อผู้ดูแลยืนยัน งานที่ยังไม่มีผลการทำงานถูกยกเลิกด้วยเหตุผล "ปิดเหตุการณ์" การเปิดเหตุการณ์ใหม่ไม่คืนงานเหล่านั้น ผู้ดูแลมอบหมายใหม่เอง
- **รับงาน** ไม่บังคับ หน่วยบริการบันทึกผลของงานที่ยังไม่รับได้ ผู้ใช้ทุกคนของหน่วยเดียวกันเห็นและทำงานของหน่วยได้เท่ากัน และระบบบันทึกว่าใครเป็นผู้ทำ ระบบไม่มีปุ่มปฏิเสธงาน หน่วยที่รับงานไม่ได้แจ้ง สสอ. แล้วผู้ดูแลยกเลิกและมอบหมายใหม่
- **เวลาที่แจ้งหน่วยบริการ** ถ้าหน่วยบริการรับงานหรือบันทึกผลขณะที่งานยังไม่มีเวลาที่แจ้งหน่วยบริการ ระบบใช้เวลาที่รับงาน หรือเวลาที่ทำจริงของผล เป็นเวลาที่แจ้งหน่วยบริการ ผู้ดูแลแก้ได้
- **บันทึกแทน** ผู้ดูแลบันทึกผลแทนหน่วยบริการได้ทุกงาน เช่น เมื่อหน่วยบริการแจ้งผลทางโทรศัพท์หรือ LINE ผลนั้นแสดงว่า "บันทึกโดย สสอ. แทนหน่วยบริการ" และถือว่ารับผลแล้ว
- **แก้ผล** หน่วยบริการแก้ผลของงานของตนได้จนกว่าผู้ดูแลจะรับผล ผู้ดูแลแก้ผลได้จนกว่าจะปิดเหตุการณ์ การแก้ทุกครั้งต้องระบุเหตุผล ผลเดิมถูกเก็บไว้ และไทม์ไลน์บอกว่าใครแก้
- **สิ่งที่หน่วยบริการเห็นจากงาน** งานที่ผูกกับผู้ป่วยแสดงชื่อและบ้านเลขที่ของผู้ป่วยรายนั้น งานที่ไม่ผูกกับผู้ป่วยแสดงจำนวนผู้ป่วยของเหตุการณ์ ไม่แสดงข้อมูลรายคน เมื่อหน่วยบริการต้องรู้ว่าเป็นบ้านใด ผู้ดูแลผูกงานกับผู้ป่วยรายนั้น
- หน่วยบริการเห็นเหตุการณ์จากการแจ้งเองหรือการได้รับมอบหมายงานเท่านั้น การเป็นหน่วยที่รับผิดชอบหมู่บ้านไม่ได้ทำให้เห็นเหตุการณ์ในหมู่บ้านนั้น

## 4. หน้าจอหลัก

### ผู้ดูแล: "งานวันนี้"

หน้าแรกของผู้ดูแล แสดงสิ่งที่ต้องทำกับเหตุการณ์ที่ยังไม่จบ คือเหตุการณ์ที่รอตรวจสอบ ตรวจสอบแล้วจริง หรือกำลังดำเนินการ หน้าแบ่งเป็นกลุ่มตามสิ่งที่ต้องทำ เรียงตามลำดับในตาราง และแต่ละแถวมีปุ่มเดียวสำหรับขั้นถัดไปของกลุ่มนั้น

| ลำดับ | กลุ่ม | สิ่งที่อยู่ในกลุ่ม | แถวแสดง | ปุ่ม |
|---|---|---|---|---|
| 1 | รอตรวจสอบ | เหตุการณ์ที่รอตรวจสอบ | เวลาที่รอมาแล้ว และ "ถ้าเข้าเกณฑ์ ต้องเริ่มสอบสวนภายใน …" | ตรวจสอบข่าว |
| 2 | รอประเมินเกณฑ์ | เหตุการณ์ที่ตรวจสอบแล้วจริงและยังไม่ได้ประเมินเกณฑ์ และเหตุการณ์ที่มีผู้เสียชีวิตแต่ถูกประเมินว่าไม่เข้าเกณฑ์ | เหมือนกลุ่ม "รอตรวจสอบ" เหตุการณ์ชนิดหลังแสดง "มีผู้เสียชีวิต ควรประเมินเกณฑ์ใหม่" | ประเมินเกณฑ์ |
| 3 | เข้าเกณฑ์ ยังไม่ได้มอบหมายงาน | เหตุการณ์ที่เข้าเกณฑ์และยังไม่มีงานที่ไม่ถูกยกเลิก | เวลาที่เหลือถึงกำหนดเริ่มสอบสวน | มอบหมายงาน |
| 4 | ผู้ป่วยที่ยังไม่มีงานตามชุดโรค | ผู้ป่วยในอำเภอของเหตุการณ์ที่กำลังดำเนินการและใช้ชุดโรค ซึ่งยังไม่มีงานของชุดที่ไม่ถูกยกเลิก | ลำดับของผู้ป่วยในเหตุการณ์ และเวลาที่เหลือหรือระยะที่เกินของเวลาที่ควรแจ้งหน่วยบริการภายใน | มอบหมายงานตามชุดโรค |
| 5 | งานของ สสอ. | งานที่ สสอ. เป็นผู้รับและยังไม่มีผลการทำงาน | ชนิดงาน กำหนดเสร็จ และระยะที่เกินหรือเวลาที่เหลือ | บันทึกผล |
| 6 | งานที่ยังไม่ได้แจ้งหน่วยบริการ | งานของหน่วยบริการที่ยังไม่มีผลการทำงานและยังไม่มีเวลาที่แจ้งหน่วยบริการ | หน่วยบริการ ชนิดงาน กำหนดเสร็จ และเวลาที่ควรแจ้งภายในเมื่อชุดโรคกำหนด | เตรียมข้อความ LINE |
| 7 | งานเกินกำหนดและใกล้ครบกำหนด | งานของหน่วยบริการที่แจ้งแล้ว ยังไม่มีผลการทำงาน และเกินกำหนด ใกล้ครบกำหนด หรือหน่วยบริการยังไม่รับงาน | ระยะที่เกินหรือเวลาที่เหลือ ป้าย "ยังไม่รับงาน" และเวลาที่ติดตามงานล่าสุด | เตรียมข้อความติดตามงาน |
| 8 | ผู้ป่วยรายใหม่จากหน่วยบริการ | ผู้ป่วยที่หน่วยบริการเพิ่มหลังการตรวจสอบข่าว และผู้ดูแลยังไม่รับทราบ | ลำดับของผู้ป่วยในเหตุการณ์ และหน่วยบริการที่เพิ่ม | ดูผู้ป่วย |
| 9 | ผลรอตรวจ | งานที่บันทึกผลแล้วและผู้ดูแลยังไม่รับผล | หน่วยบริการ ชนิดงาน เวลาที่ทำจริง และป้าย "ผลไม่ถึงเป้า" ของงานของชุดโรค | ดูผลการทำงาน |
| 10 | ยังไม่ได้แจ้งเตือนข่าว | เหตุการณ์ที่ตรวจสอบแล้วจริงหรือกำลังดำเนินการ และยังไม่มีการแจ้งเตือนข่าว | เวลาที่ผ่านมาตั้งแต่รับแจ้ง | บันทึกการแจ้งเตือนข่าว |
| 11 | รอปิด | เหตุการณ์ที่รอปิด ตามนิยามด้านล่าง | เวลาที่ผ่านมาตั้งแต่รับแจ้ง | ปิดเหตุการณ์ |

นิยามที่กลุ่มใช้

- **งานค้าง** คืองานที่ไม่ถูกยกเลิก และยังไม่มีผลการทำงาน หรือมีผลแล้วแต่ผู้ดูแลยังไม่รับผล
- **เกินกำหนด** คืองานที่เลยกำหนดเสร็จแล้วและยังไม่มีผลการทำงาน
- **ใกล้ครบกำหนด** คืองานที่ยังไม่มีผลการทำงานและกำหนดเสร็จอยู่ภายใน 24 ชั่วโมงข้างหน้า
- **ยังไม่รับงาน** คืองานที่แจ้งหน่วยบริการแล้วเกิน 24 ชั่วโมงและหน่วยบริการยังไม่กดรับงาน งานนี้อยู่ในกลุ่ม "งานเกินกำหนดและใกล้ครบกำหนด" แม้ยังไม่ใกล้ครบกำหนด
- **รอปิด** คือเหตุการณ์ที่กำลังดำเนินการและไม่มีงานค้าง ซึ่งถูกประเมินว่าไม่เข้าเกณฑ์ หรือเข้าเกณฑ์และมีงานที่ไม่ถูกยกเลิกอย่างน้อยหนึ่งงาน เหตุการณ์ที่เข้าเกณฑ์และยังไม่มีงานอยู่ในกลุ่ม "เข้าเกณฑ์ ยังไม่ได้มอบหมายงาน" ไม่ใช่กลุ่มนี้ เหตุการณ์ที่ใช้ชุดโรคมีเงื่อนไขเพิ่ม: ไม่มีผู้ป่วยในกลุ่ม "ผู้ป่วยที่ยังไม่มีงานตามชุดโรค" และครบระยะเฝ้าระวังของชุดโรคแล้ว ([ข้อ 5](#5-ชุดโรค))
- **ผู้ป่วยที่ยังไม่มีงานตามชุดโรค** แถวอยู่จนกว่าผู้ป่วยรายนั้นจะมีงานของชุดอย่างน้อยหนึ่งงานที่ไม่ถูกยกเลิก ผู้ป่วยถูกยกเลิก หรือเหตุการณ์ปิด ระบบไม่มีปุ่มบันทึกว่าไม่ต้องทำ การกด "รับทราบผู้ป่วย" ไม่ทำให้แถวหาย ผู้ป่วยที่อยู่นอกอำเภอไม่อยู่ในกลุ่มนี้ กลุ่มนี้มีไว้เพราะผู้ป่วยของโรคที่มีชุดโรคต้องได้งานตามมาตรการทุกราย แม้เหตุการณ์ถูกประเมินว่าไม่เข้าเกณฑ์สอบสวนโรค
- ค่า 24 ชั่วโมงทั้งสองค่าตายตัวในรุ่นแรก ผู้ดูแลแก้ไม่ได้
- ระยะที่เกินและเวลาที่เหลือแสดงเป็นชั่วโมงเมื่อไม่ถึงหนึ่งวัน และเป็นวันเมื่อมากกว่านั้น

ลำดับและการแสดง

- เหตุการณ์หนึ่งขึ้นได้หลายกลุ่ม เช่น เหตุการณ์ที่ตรวจสอบแล้วจริง ยังไม่ประเมินเกณฑ์ และยังไม่แจ้งเตือนข่าว ขึ้นทั้งกลุ่ม "รอประเมินเกณฑ์" และกลุ่ม "ยังไม่ได้แจ้งเตือนข่าว" งานหนึ่งงานขึ้นกลุ่มเดียว
- งานของ สสอ. ขึ้นกลุ่ม "งานของ สสอ." ตั้งแต่มอบหมายจนมีผลการทำงาน และไม่ขึ้นกลุ่มอื่น
- ทุกกลุ่มเรียงเหตุการณ์ของโรคติดต่ออันตรายก่อน แล้วเหตุการณ์ที่มีผู้เสียชีวิต แล้วแถวที่เวลาเหลือน้อยที่สุดหรือรอมานานที่สุด แถวของงานและของผู้ป่วยใช้โรคและผู้เสียชีวิตของเหตุการณ์ที่ตนอยู่
- เหตุการณ์มีผู้เสียชีวิตเมื่อมีผู้ป่วยที่สภาพผู้ป่วยเป็นเสียชีวิต หรือจำนวนผู้เสียชีวิตที่ผู้ดูแลกรอกมากกว่าศูนย์
- "ถ้าเข้าเกณฑ์ ต้องเริ่มสอบสวนภายใน …" ในกลุ่ม "รอตรวจสอบ" และ "รอประเมินเกณฑ์" คำนวณจากเวลาที่ได้รับแจ้งกับจำนวนชั่วโมงของโรค ผู้ดูแลจึงเห็นว่าเหตุการณ์ใดรอไม่ได้ตั้งแต่ก่อนประเมินเกณฑ์
- เหตุการณ์ของโรคติดต่ออันตรายที่ยังไม่มีการแจ้งเตือนข่าวแสดงเหนือทุกกลุ่มตั้งแต่รับแจ้ง พร้อมเวลาที่เหลือของกำหนดโทรแจ้งกรมควบคุมโรคภายใน 1 ชั่วโมงหลังได้รับแจ้ง แถวนี้หายเมื่อมีการแจ้งเตือนข่าวครั้งแรก และเหตุการณ์นี้ไม่ขึ้นซ้ำในกลุ่ม "ยังไม่ได้แจ้งเตือนข่าว"
- มาตรฐานไม่กำหนดเวลาของการตรวจสอบข่าว การแจ้งเตือนข่าวของโรคอื่น และการปิดเหตุการณ์ ([ผลการค้นมาตรฐาน](research/event-handling-standards.md) ส่วนที่ 2 และ 9) กลุ่ม "รอตรวจสอบ" "รอประเมินเกณฑ์" "ยังไม่ได้แจ้งเตือนข่าว" และ "รอปิด" จึงแสดงเวลาที่ผ่านมา และไม่แสดงคำว่า "เกินกำหนด"
- บนสุดของหน้าแสดงจำนวนแถวของแต่ละกลุ่ม กลุ่มที่ว่างไม่แสดง เมื่อทุกกลุ่มว่าง หน้าแสดงว่าไม่มีสิ่งที่ต้องทำ
- แถวแสดงเลขที่เหตุการณ์ โรค และหมู่บ้าน ไม่แสดงชื่อผู้ป่วยและบ้านเลขที่ ผู้ป่วยถูกเรียกด้วยลำดับในเหตุการณ์
- ปุ่มของแถวพาไปหน้าเหตุการณ์หรือหน้างาน พร้อมเปิดแบบของขั้นนั้น หลังบันทึก ผู้ดูแลกลับมาที่หน้านี้
- แถวในกลุ่ม "งานเกินกำหนดและใกล้ครบกำหนด" อยู่จนกว่าจะมีผลการทำงาน หรือผู้ดูแลแก้กำหนดเสร็จหรือยกเลิกงาน การติดตามงานไม่ทำให้แถวหาย
- ปุ่มของแถวในกลุ่ม "งานที่ยังไม่ได้แจ้งหน่วยบริการ" และกลุ่ม "งานเกินกำหนดและใกล้ครบกำหนด" เตรียมข้อความเดียวที่รวมทุกงานของหน่วยบริการเดียวกันในเหตุการณ์เดียวกันที่อยู่ในกลุ่มนั้น ([ข้อความ LINE](#ข้อความ-line))
- ผู้ดูแลทุกคนเห็นรายการเดียวกัน ระบบไม่มีเจ้าของเหตุการณ์
- เหนือทุกกลุ่ม ผู้ดูแลเห็นแถบเตือนของระบบในสองกรณี: ชุดสำรองล่าสุดที่สำเร็จเก่ากว่า 8 วัน หรือพื้นที่เก็บข้อมูลของบัญชีเจ้าของใช้เกินร้อยละ 80 แถบบอกว่าเกิดอะไรและพาไปหน้าตั้งค่า ผู้ดูไม่เห็นแถบนี้ ([ข้อ 8](#สำรองข้อมูล))
- ผู้ดูเห็นหน้านี้แบบอ่านอย่างเดียว เห็นกลุ่มและแถวเดียวกับผู้ดูแล ปุ่มของแถวเป็น "เปิดเหตุการณ์" หรือ "เปิดงาน" และไม่มีปุ่มเตรียมข้อความ LINE กับปุ่มยืนยัน
- หน้าโหลดข้อมูลใหม่เมื่อเปิด เมื่อผู้ดูแลกลับมาที่แท็บ และหลังบันทึก มีปุ่ม "โหลดใหม่" และแสดงเวลาของข้อมูล หน้าไม่ดึงข้อมูลเองเป็นรอบ
- หน้านี้ใช้ได้ทั้งบนคอมพิวเตอร์และมือถือ
- ชุดโรคมีผลกับหน้านี้สามจุด: กลุ่ม "ผู้ป่วยที่ยังไม่มีงานตามชุดโรค" ป้าย "ผลไม่ถึงเป้า" ในกลุ่ม "ผลรอตรวจ" และเงื่อนไขเพิ่มของกลุ่ม "รอปิด" ชุดโรคไม่มีคำเตือนอื่นในหน้านี้ ([ข้อ 5](#5-ชุดโรค))

หน้าอื่นของผู้ดูแล: [รายการเหตุการณ์](#รายการเหตุการณ์) หน้าเหตุการณ์ (ข้อมูล ผู้ป่วย งาน ไทม์ไลน์) [สรุปภาพรวมและการส่งออก](#6-สรุปภาพรวมและการส่งออก) และตั้งค่า (ผู้ใช้ หน่วยงาน หมู่บ้าน ประชากร รายการโรค ชุดโรค ชื่อ โลโก้ และช่องทางติดต่อของหน่วยงาน และสถานะของระบบ ซึ่งแสดงเวลาของชุดสำรองล่าสุด พื้นที่ที่ใช้ และผลการตรวจการแชร์)

### รายการเหตุการณ์

หน้านี้คือทะเบียนรับแจ้งข่าวของ สสอ. ผู้ดูแลและผู้ดูใช้หน้าเดียวกัน ผู้ใช้หน่วยบริการไม่มีหน้านี้ มาตรฐานทีมไม่กำหนดคอลัมน์ของทะเบียน และรับโปรแกรมอิเล็กทรอนิกส์เป็นทะเบียนได้ ([ผลการค้นเรื่องหน้าสรุปและการส่งออก](research/summary-export-facts.md) ส่วนที่ 6)

- หนึ่งแถวต่อหนึ่งเหตุการณ์ เรียงจากเวลาที่ได้รับแจ้งล่าสุด
- **คอลัมน์** เลขที่เหตุการณ์ วันรับแจ้ง โรค หมู่บ้านและตำบล แหล่งข่าว สถานะ ผลประเมินเกณฑ์ จำนวนผู้ป่วยและผู้เสียชีวิต จำนวนงานที่มีผลแล้วต่องานที่ไม่ถูกยกเลิก และการแจ้งเตือนข่าว
- **ตัวกรอง** ช่วงวันรับแจ้ง โรค ตำบลหรือหมู่บ้าน สถานะ และหน่วยบริการที่มีงานในเหตุการณ์
- **ค้นหา** ด้วยเลขที่เหตุการณ์เท่านั้น ระบบไม่ค้นด้วยชื่อผู้ป่วย เช่นเดียวกับที่ไม่ค้นชื่อข้ามเหตุการณ์ตอนเพิ่มผู้ป่วย
- **ค่าตั้งต้น** แสดงเหตุการณ์ของปีปัจจุบัน รวมเหตุการณ์ที่ตรวจสอบแล้วไม่จริง เหตุการณ์ที่ยกเลิกแสดงเมื่อผู้ใช้เลือก
- จำนวนผู้ป่วยและผู้เสียชีวิตใช้วิธีนับเดียวกับหน้าสรุปภาพรวม ([ข้อ 6](#กติกาการนับ))
- แถวไม่แสดงชื่อผู้ป่วยและบ้านเลขที่ กดแถวเพื่อเปิดหน้าเหตุการณ์
- ตัวเลขในหน้าสรุปภาพรวมลิงก์มาที่หน้านี้พร้อมตัวกรอง

### ผู้ดู

- หน้าแรกของผู้ดูคือ[สรุปภาพรวม](#6-สรุปภาพรวมและการส่งออก) เมนูมีสรุปภาพรวม งานวันนี้ และรายการเหตุการณ์
- ผู้ดูเปิดหน้าเหตุการณ์และหน้างานได้ทุกรายการ เห็นข้อมูล ผู้ป่วย งาน ผล รูปถ่าย และไทม์ไลน์เท่ากับผู้ดูแล ไม่มีปุ่มบันทึก ปุ่มแก้ไข และปุ่มข้อความ LINE
- ผู้ดูไม่เห็นหน้าตั้งค่า การจัดการผู้ใช้ และบันทึกความปลอดภัย
- ผู้ดูส่งออกได้เฉพาะตัวเลขสรุป และแผ่นสรุปร้อยละของแบบติดตามมาตรการ 3-3-1 ([ข้อ 6](#การส่งออก))
- ผู้ดูเปิดหน้าร่างรายงานสอบสวนของทุกเหตุการณ์ได้ อ่านข้อมูลที่ระบบมี บันทึกการสอบสวน และร่างล่าสุดบนหน้าจอ ดาวน์โหลดไฟล์ แก้บันทึกการสอบสวน และสั่งให้ AI ร่างไม่ได้ ([ร่างรายงานสอบสวน](#ร่างรายงานสอบสวน))
- ผู้ดูแลเพิ่มบัญชีผู้ดูในหน้าผู้ใช้เดียวกับบทบาทอื่น บัญชีผู้ดูไม่ผูกกับหน่วยบริการ
- ทุกคำขอบันทึกหรือแก้ไขจากผู้ดูถูกปฏิเสธที่ server

### หน่วยบริการ: "งานของหน่วย"

หน้าแรกของผู้ใช้หน่วยบริการ ออกแบบสำหรับมือถือเป็นหลัก เพราะเปิดจากลิงก์ใน LINE ปุ่ม "แจ้งเหตุการณ์" อยู่บนสุดของหน้า ตามด้วยสามส่วน

1. **งานที่ต้องทำ** งานของหน่วยที่ยังไม่มีผลการทำงาน เรียงตามกำหนดเสร็จ งานเกินกำหนดขึ้นก่อน
2. **งานที่บันทึกผลแล้ว** แสดงจนกว่าเหตุการณ์ของงานนั้นจะปิด
3. **เหตุการณ์ที่หน่วยแจ้ง** พร้อมสถานะปัจจุบัน แสดงจนครบ 30 วันหลังเหตุการณ์นั้นปิด ถูกบันทึกว่าไม่จริง หรือถูกยกเลิก ลิงก์ของเหตุการณ์ยังเปิดได้หลังจากนั้น

หน้างาน: รายละเอียดงาน ข้อมูลผู้ป่วยที่งานผูกอยู่ ปุ่มรับงาน แบบบันทึกผล และช่องแนบรูป งานของชุดโรคแสดงรอบ เป้าหมายของรอบ คำแนะนำของมาตรการ และผลการเทียบเป้าของงานนั้น ([ข้อ 5](#5-ชุดโรค)) งานที่ถูกยกเลิกไม่แสดงในหน้านี้ และลิงก์ของงานนั้นได้คำตอบว่าไม่พบ

### ข้อมูลตั้งต้น

ผู้ดูแลจัดการข้อมูลเหล่านี้ในหน้าตั้งค่า ที่มาของข้อมูลชุดแรกอยู่ใน [`schema.md` ข้อ 4](schema.md#4-ข้อมูลตั้งต้น)

- **หน่วยบริการ** มีสามชนิด: รพ.สต. รพ. และ สสช. ทุกชนิดรับงานและมีสิทธิ์เหมือนกัน องค์กรปกครองส่วนท้องถิ่นไม่มีบัญชีในระบบ หน่วยบริการเป็นผู้ประสานและบันทึกผลเอง
- **หมู่บ้าน** รายการตำบล หมู่ที่ และชื่อหมู่บ้านมาจากสถิติทะเบียนราษฎร์ของกรมการปกครอง ทุกหมู่บ้านมีหน่วยที่รับผิดชอบหนึ่งแห่ง ตำบลหนึ่งมีได้หลายหน่วยบริการ แบ่งตามหมู่ที่ ผู้ดูแลกำหนดหน่วยที่รับผิดชอบได้ทีละหลายหมู่บ้าน และหน้าตั้งค่าแสดงหมู่บ้านที่ยังไม่มีหน่วยที่รับผิดชอบ
- **รายการโรค** ตั้งต้นจากรายชื่อโรคติดต่ออันตรายและโรคติดต่อที่ต้องเฝ้าระวังตามประกาศกระทรวงสาธารณสุข แต่ละโรคมีเกณฑ์สอบสวนและกำหนดเริ่มสอบสวนที่ผู้ดูแลแก้ได้ การแจ้งเหตุการณ์ต้องเลือกโรคจากรายการ ซึ่งค้นด้วยการพิมพ์ได้ ไม่มีช่องพิมพ์ชื่อโรคเอง ผู้ที่ไม่พบโรคในรายการเลือก "อื่น ๆ" แล้วบรรยาย ผู้ดูแลแก้เป็นโรคที่ถูกต้องตอนตรวจสอบข่าว และเพิ่มโรคใหม่ได้เอง ผู้ดูแลเลือกชุดโรคของแต่ละโรคได้ ([ข้อ 5](#5-ชุดโรค)) และเลือกได้ว่าโรคใดแสดงชื่อใน Dashboard สาธารณะ ([ข้อ 7](#โรคที่ไม่แสดงชื่อ))
- **ประชากร** เก็บจำนวนชาย หญิง รวม และจำนวนบ้านของแต่ละหมู่บ้านแยกตามปี จากสถิติชุดเดียวกัน การแก้ตัวเลขของปีหนึ่งไม่เปลี่ยนตัวเลขของปีอื่น ผู้ดูแลนำประชากรของปีใหม่เข้าด้วยปุ่มในหน้าตั้งค่า ระบบดึงไฟล์สถิติของกรมการปกครองของปีที่เลือก แสดงผลให้ตรวจก่อนบันทึก รวมรหัสหมู่บ้านที่ไม่ตรงกับที่มีอยู่ และผู้ดูแลแก้ตัวเลขทีละหมู่บ้านบนหน้าจอได้ ปีของประชากรที่หน้าสรุปภาพรวมใช้อยู่ใน[ข้อ 6](#อัตราป่วยและประชากร)
- **ชื่อและโลโก้หน่วยงาน** แสดงที่หน้าล็อกอิน แถบบนของทุกหน้า Dashboard สาธารณะ และหัวไฟล์ที่ส่งออก โลโก้ไม่บังคับ
- **ช่องทางติดต่อของหน่วยงาน** ข้อความสั้นหนึ่งช่อง เช่น เบอร์โทรของสำนักงาน แสดงในหน้า[คู่มือ](#คู่มือ)และหน้า[การคุ้มครองข้อมูลส่วนบุคคล](#การคุ้มครองข้อมูลส่วนบุคคล) ซึ่งเปิดได้โดยไม่ล็อกอิน ช่องนี้จึงไม่ใส่เบอร์โทรหรืออีเมลส่วนตัวของบุคคล
- **ไม่มีการลบ** หน่วยบริการ หมู่บ้าน และโรคที่ไม่ใช้แล้วถูกเลิกใช้ รายการที่เลิกใช้เลือกไม่ได้ในเหตุการณ์และงานใหม่ และยังแสดงในเหตุการณ์เก่า
- ระบบปฏิเสธการเลิกใช้หน่วยบริการที่ยังมีงานที่ไม่เสร็จ บัญชีที่ยังไม่ถูกระงับ หรือหมู่บ้านในความรับผิดชอบ และบอกว่าต้องย้ายอะไรก่อน
- เมื่อผู้ดูแลแก้ชื่อหน่วยบริการ หมู่บ้าน หรือโรค ทุกหน้ารวมถึงเหตุการณ์เก่าแสดงชื่อปัจจุบัน
- ผู้ดูแลเพิ่มและแก้หมู่บ้านทีละรายการบนหน้าจอได้ เช่น แก้ชื่อให้ตรงกับที่ใช้ในพื้นที่

### ข้อความ LINE

ระบบไม่ส่งข้อความเอง ระบบเตรียมข้อความ แล้วผู้ใช้กด "คัดลอก" หรือ "เปิด LINE" เพื่อเลือกผู้รับและส่งเอง สสอ. กับหน่วยบริการส่งข้อความถึงกันในแชตรายคน ผู้ดูแลส่งถึงเจ้าหน้าที่ของหน่วยบริการที่รับงาน และไม่ใช้กลุ่ม LINE ข้อเท็จจริงทางเทคนิคและแนวทางเรื่องข้อมูลผู้ป่วยที่หัวข้อนี้ใช้อยู่ใน[ผลการค้นเรื่องข้อความ LINE](research/line-message-facts.md)

ข้อความมีหกชนิด

| ผู้ส่ง | ข้อความ | ระบบเตรียมให้เมื่อ | ลิงก์ไปที่ |
|---|---|---|---|
| ผู้ดูแล | แจ้งงานใหม่ | หลังมอบหมายงาน และจากแถวของกลุ่ม "งานที่ยังไม่ได้แจ้งหน่วยบริการ" | งาน หรือเหตุการณ์ |
| ผู้ดูแล | ติดตามงาน | จากแถวของกลุ่ม "งานเกินกำหนดและใกล้ครบกำหนด" และจากหน้างาน | งาน หรือเหตุการณ์ |
| ผู้ดูแล | แจ้งยกเลิกงาน | หลังยกเลิกงานที่แจ้งหน่วยบริการแล้ว รวมถึงงานที่ถูกยกเลิกเพราะปิดเหตุการณ์ | ไม่มีลิงก์ เพราะลิงก์ของงานที่ถูกยกเลิกได้คำตอบว่าไม่พบ |
| หน่วยบริการ | แจ้งเหตุการณ์ | หลังแจ้งเหตุการณ์ | เหตุการณ์ |
| หน่วยบริการ | เพิ่มผู้ป่วยรายใหม่ | หลังเพิ่มผู้ป่วยในเหตุการณ์ที่มีอยู่แล้ว | เหตุการณ์ |
| หน่วยบริการ | บันทึกผลแล้ว | หลังบันทึกผล | งาน |

การแก้งาน การแก้ผล และการรับผลไม่มีข้อความ งานของ สสอ. ไม่มีข้อความ

ตัวอย่างข้อความแจ้งงานใหม่ ด้วยข้อมูลสมมติ ข้อความอีกห้าชนิดใช้โครงเดียวกัน

```
[สสอ.สมมติ] งานใหม่ถึง รพ.สต.สมมติ ก
เหตุการณ์ 2569-0012 ไข้เลือดออก หมู่ 5 ต.สมมติ
1. ลงพื้นที่บ้านผู้ป่วย (ผู้ป่วยรายที่ 1) ภายใน 17 พ.ย. 69 เวลา 16:30 น.
2. สำรวจ ทำลายแหล่งเพาะพันธุ์ และพ่นสารเคมี รัศมี 100 เมตร (ผู้ป่วยรายที่ 1) ภายใน 18 พ.ย. 69 เวลา 13:30 น.
รายละเอียดและบ้านผู้ป่วยดูในลิงก์ ต้องล็อกอิน
https://<APP_HOST>/<หน้าเหตุการณ์>?openExternalBrowser=1
```

- **เนื้อหา** บรรทัดแรกบอกชื่อหน่วยงานของ สสอ. ชนิดของข้อความ และชื่อหน่วยบริการ ตามด้วยเลขที่เหตุการณ์ โรค และหมู่บ้าน แล้วรายการงานพร้อมชนิดงานและกำหนดเสร็จ งานที่ผูกกับผู้ป่วยเรียกผู้ป่วยด้วยลำดับในเหตุการณ์ ข้อความติดตามงานบอกระยะที่เกินหรือเวลาที่เหลือของแต่ละงาน ข้อความ "บันทึกผลแล้ว" บอกชนิดงานและเวลาที่ทำจริง ข้อความ "เพิ่มผู้ป่วยรายใหม่" บอกลำดับของผู้ป่วย
- **สิ่งที่ไม่อยู่ในข้อความ** ชื่อผู้ป่วย บ้านเลขที่ อายุ เพศ วันเริ่มป่วย และข้อความจากช่องที่ผู้ใช้พิมพ์อิสระทุกช่อง เช่น คำสั่งเพิ่มเติมของงาน รายละเอียดของเหตุการณ์ และสรุปผล ผู้รับต้องเปิดลิงก์และล็อกอินจึงจะเห็น แนวทางการใช้สื่อสังคมออนไลน์ของผู้ปฏิบัติงานด้านสุขภาพ พ.ศ. 2559 ให้ลบข้อมูลระบุตัวผู้ป่วยและรายละเอียดที่ทำให้คาดเดาตัวผู้ป่วยได้ก่อนส่ง กฎนี้จึงใช้กับแชตรายคนเท่ากับกลุ่ม
- **แม่แบบ** ถ้อยคำของข้อความตายตัวในรุ่นแรก ระบบไม่มีหน้าแก้แม่แบบ และไม่มีช่องแก้ข้อความก่อนคัดลอก ผู้ใช้แก้ข้อความใน LINE ก่อนส่งได้
- **หนึ่งข้อความต่อหน่วยบริการต่อเหตุการณ์** ข้อความแจ้งงานใหม่รวมทุกงานของหน่วยบริการนั้นในเหตุการณ์นั้นที่ยังไม่มีเวลาที่แจ้งหน่วยบริการและยังไม่มีผลการทำงาน เช่น งานหกงานของชุดโรคติดต่อนำโดยยุงลายเป็นข้อความเดียว ข้อความที่ระบบเตรียมทันทีหลังมอบหมายงานรวมงานที่เพิ่งสร้างทุกงานของหน่วยนั้น รวมถึงงานของชุดโรคที่มีเวลาที่แจ้งหน่วยบริการตั้งแต่ตอนสร้าง ([ข้อ 5](#5-ชุดโรค)) เมื่อผู้ดูแลมอบหมายงานให้หลายหน่วยในครั้งเดียว ระบบเตรียมหนึ่งข้อความต่อหนึ่งหน่วย ข้อความติดตามงานและข้อความแจ้งยกเลิกงานรวมงานด้วยกฎเดียวกัน
- **ลิงก์** ข้อความที่มีงานเดียวลิงก์ไปที่งานนั้น ข้อความที่มีหลายงานลิงก์ไปที่เหตุการณ์ ซึ่งหน้าเหตุการณ์แสดงงานของหน่วยนั้นตามสิทธิ์ ลิงก์มีเพียงรหัสของแถว และมีพารามิเตอร์ `openExternalBrowser=1` เพื่อให้ LINE เปิดลิงก์ในเบราว์เซอร์ของเครื่อง ลิงก์อยู่บรรทัดสุดท้ายเป็นบรรทัดของตัวเอง หน้าเว็บเปิดได้ตามปกติเมื่อมีพารามิเตอร์นี้ติดมา รวมถึงหลังถูกพาไปล็อกอินแล้วกลับมาที่หน้าเดิม
- **ปุ่ม** "คัดลอก" มีบนทุกเครื่อง "เปิด LINE" แสดงเฉพาะบนมือถือ และเปิดหน้าเลือกผู้รับของ LINE พร้อมข้อความ ระบบเลือกผู้รับแทนผู้ใช้ไม่ได้ บนคอมพิวเตอร์ผู้ใช้คัดลอกแล้ววางใน LINE เอง เพราะ LINE บนคอมพิวเตอร์ไม่รองรับการเปิดพร้อมข้อความ รุ่นแรกไม่ใช้ปุ่มแชร์ของเบราว์เซอร์
- **ข้อความพร้อมก่อนกด** หน้าเว็บสร้างข้อความจากข้อมูลที่หน้านั้นโหลดมาแล้ว และไม่เรียก server ตอนกดปุ่ม เพราะเบราว์เซอร์ยอมให้คัดลอกเฉพาะในจังหวะที่ผู้ใช้กด ลิงก์ใช้ที่อยู่ของหน้าเว็บที่ผู้ใช้เปิดอยู่ ระบบไม่เก็บตัวข้อความ
- **ผู้รับ** หน้าเตรียมข้อความของผู้ดูแลแสดงชื่อผู้ใช้ของหน่วยบริการนั้นที่บัญชียังใช้งานได้ เพื่อให้รู้ว่าส่งถึงใครได้ และเตือนเมื่อหน่วยนั้นยังไม่มีผู้ใช้ เพราะผู้รับจะเปิดลิงก์ไม่ได้ ระบบไม่เก็บบัญชี LINE หรือเบอร์โทรของผู้ใช้
- **ยืนยันว่าแจ้งแล้ว** การกด "คัดลอก" หรือ "เปิด LINE" ไม่บันทึกอะไร เมื่อผู้ดูแลกด "ยืนยันว่าแจ้งหน่วยบริการแล้ว" ระบบบันทึกเวลาที่แจ้งหน่วยบริการให้ทุกงานในข้อความที่แสดง และเพิ่มหนึ่งแถวในไทม์ไลน์ต่อหนึ่งงาน ค่าตั้งต้นคือเวลาที่กดยืนยัน ผู้ดูแลแก้ได้ทั้งตอนยืนยันและภายหลัง ปุ่มเดียวกันใช้เมื่อแจ้งด้วยช่องทางอื่น เช่น โทรศัพท์ และระบบไม่ถามช่องทาง งานอยู่ในกลุ่ม "งานที่ยังไม่ได้แจ้งหน่วยบริการ" จนกว่าผู้ดูแลจะยืนยัน หรือหน่วยบริการรับงานหรือบันทึกผล
- **ติดตามงาน** ข้อความรวมงานของหน่วยบริการนั้นในเหตุการณ์นั้นที่อยู่ในกลุ่ม "งานเกินกำหนดและใกล้ครบกำหนด" เมื่อผู้ดูแลกด "ยืนยันว่าติดตามงานแล้ว" ระบบบันทึกเวลาที่ติดตามงานล่าสุดให้ทุกงานในข้อความ และเพิ่มหนึ่งแถวในไทม์ไลน์ต่อหนึ่งงาน ติดตามซ้ำได้ไม่จำกัด
- **แจ้งยกเลิกงาน** ข้อความนี้ไม่มีการยืนยัน และระบบไม่บันทึกอะไรเพิ่ม เพราะการยกเลิกงานอยู่ในไทม์ไลน์แล้ว
- **ข้อความของหน่วยบริการ** หน้าจอหลังบันทึกสำเร็จแสดงข้อความพร้อมปุ่ม "คัดลอก" และ "เปิด LINE" หน่วยบริการข้ามได้ ไม่มีการยืนยันว่าส่ง และระบบไม่บันทึกอะไร เพราะเรื่องนั้นขึ้นหน้า "งานวันนี้" ของผู้ดูแลแล้ว ข้อความใช้เฉพาะข้อมูลที่หน่วยบริการนั้นมีสิทธิ์เห็น
- **ดูและส่งซ้ำ** หน้างานของผู้ดูแลมีปุ่ม "ข้อความ LINE" ตลอดช่วงที่งานยังไม่มีผลการทำงาน ผู้ดูแลเลือกข้อความแจ้งงานใหม่หรือข้อความติดตามงานได้ ระบบสร้างข้อความจากข้อมูลปัจจุบันทุกครั้ง การส่งข้อความแจ้งงานใหม่ซ้ำไม่เปลี่ยนเวลาที่แจ้งหน่วยบริการ

### รูปถ่าย

- แนบได้เฉพาะรูปถ่ายของงานในพื้นที่ เช่น การพ่นสารเคมี หรือภาชนะที่พบลูกน้ำ ไม่รับไฟล์เอกสาร
- รูปแนบกับผลการทำงานเท่านั้น ไม่เกิน 6 รูปต่อผล การแจ้งเหตุการณ์ไม่มีรูป
- หน่วยบริการเพิ่มหรือเอารูปออกได้จนกว่าผู้ดูแลจะรับผล ผู้ดูแลเพิ่มรูปได้จนกว่าจะปิดเหตุการณ์ และเอารูปออกได้ทุกเมื่อ เช่น รูปที่เห็นใบหน้าผู้ป่วย รูปที่เอาออกไม่แสดงอีก
- ระบบบันทึกผลก่อน แล้วส่งรูปทีละรูป รูปที่ส่งไม่สำเร็จจึงไม่ทำให้ผลหาย และผู้ใช้ส่งรูปนั้นใหม่ได้
- เมื่อแก้ผล รูปของผลเดิมตามไปอยู่กับผลใหม่
- หน้าแนบรูปและช่องข้อความอิสระทุกช่องมีคำเตือน: ห้ามถ่ายเอกสารที่มีชื่อผู้ป่วย และห้ามถ่ายใบหน้าผู้ป่วย
- ระบบย่อรูปในเครื่องของผู้ใช้ก่อนส่ง การย่อนี้ลบข้อมูลที่ฝังมากับรูป เช่น พิกัดสถานที่ถ่าย
- รูปเก็บใน Google Drive โฟลเดอร์ส่วนตัวของระบบ ไม่มีลิงก์สาธารณะ เปิดดูได้ผ่านระบบตามสิทธิ์เท่านั้น

### ร่างรายงานสอบสวน

ระบบช่วยผู้ดูแลเริ่มเขียนรายงานสอบสวนเบื้องต้น ระบบรวมข้อมูลที่บันทึกไว้แล้วลงในไฟล์ Word ตามหัวข้อของมาตรฐาน และให้ AI ช่วยเรียบเรียงส่วนบรรยาย ไฟล์ที่ได้เป็นร่างที่ยังไม่ครบ ผู้สอบสวนเติม แก้ และลงนามเองใน Word เป้าหมายคือผู้สอบสวนไม่ต้องเริ่มจากหน้าเปล่า และไม่ต้องพิมพ์ซ้ำสิ่งที่บันทึกในระบบแล้ว

ที่มาของหัวข้อและรูปแบบอยู่ใน[ผลการค้นเรื่องรายงานสอบสวน](research/investigation-report-facts.md) ที่มาของข้อกำหนดเรื่อง Gemini และการสร้างไฟล์อยู่ใน[ผลการค้นเรื่องการร่างด้วย AI](research/ai-report-drafting-facts.md) เหตุผลของการตัดสินใจอยู่ใน [ADR-0009](adr/0009-ai-drafts-the-investigation-report.md)

- **ชนิดรายงาน** รุ่นแรกทำรายงานสอบสวนเบื้องต้นชนิดเดียว ซึ่งมาตรฐานทีมให้เขียนภายใน 48 ชั่วโมงและวัดด้วยตัวชี้วัดที่ 10 รายงานนี้มีหกหัวข้อ ยาว 1–2 หน้า A4: ความเป็นมา ผลการสอบสวน กิจกรรมควบคุมโรคที่ดำเนินการแล้ว แนวโน้มของการระบาด สรุปความสำคัญทางสาธารณสุขและความเร่งด่วน และข้อเสนอเพื่อพิจารณาดำเนินการต่อไป (ผลการค้นเรื่องรายงานสอบสวน ข้อ 3.1)
- **รูปแบบ** การค้นไม่พบแบบฟอร์มที่กรมควบคุมโรคประกาศสำหรับรายงานสอบสวนระดับอำเภอ มาตรฐานกำหนดเพียงหัวข้อ (ผลการค้นเรื่องรายงานสอบสวน ข้อ 4) ไฟล์ของระบบจึงขึ้นต้นด้วยหัวบันทึกข้อความตามระเบียบงานสารบรรณ คือครุฑ ส่วนราชการ ที่ วันที่ เรื่อง และเรียน ตามด้วยหกหัวข้อ และท้ายรายงานที่มีชื่อผู้รายงาน แบบอักษรคือ TH SarabunPSK 16 พอยต์ รูปแบบนี้เป็นข้อเสนอจนกว่า PO ยืนยันรูปแบบที่ สสอ. ใช้จริง ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))
- **ใครใช้** ผู้ดูแลแก้บันทึกการสอบสวน สั่งให้ AI ร่าง และดาวน์โหลดไฟล์ ผู้ดูอ่านหน้าร่างรายงานบนหน้าจอได้ และดาวน์โหลดไฟล์ไม่ได้ เช่นเดียวกับไฟล์ส่งออกที่มีแถวรายผู้ป่วย ([ข้อ 6](#การส่งออก)) หน่วยบริการไม่เห็นปุ่มและไม่เห็นร่าง คำขอของหน่วยบริการได้คำตอบว่าไม่พบ แม้เป็นเหตุการณ์ที่หน่วยนั้นมีงาน
- **เปิดจากที่ใด** หน้าเหตุการณ์มีปุ่ม "ร่างรายงานสอบสวน" เมื่อเหตุการณ์มีงานสอบสวนโรคที่มีผลการทำงานแล้วอย่างน้อยหนึ่งงาน ใช้ได้กับทุกโรค ทั้งเหตุการณ์ที่กำลังดำเนินการและที่ปิดแล้ว ระบบไม่ร่างเอง
- **หน้าร่างรายงาน** มีสามส่วนในหน้าเดียว
  1. **ข้อมูลที่ระบบมี** เรียงตามหกหัวข้อ บอกว่ารายการใดมีแล้ว และรายการใดยังไม่มี รายการที่ยังไม่มีไม่ขวางการดาวน์โหลดหรือการร่าง
  2. **บันทึกการสอบสวน** ช่องข้อความอิสระหนึ่งช่อง ไม่บังคับ ไม่เกิน 5,000 ตัวอักษร ผู้ดูแลพิมพ์หรือวางโน้ตของการสอบสวนโดยไม่ต้องจัดหัวข้อ ใต้ช่องมีรายการเตือนความจำของสิ่งที่มาตรฐานถามและระบบไม่ได้เก็บ: วิธีที่ได้รับแจ้ง สมาชิกทีมสอบสวน วันที่เสร็จสอบสวน วัตถุประสงค์ อาการและผลตรวจทางห้องปฏิบัติการ ประวัติเสี่ยงและผู้สัมผัส สภาพแวดล้อม ข้อสันนิษฐานเรื่องแหล่งโรค แนวโน้ม ความเร่งด่วน และข้อเสนอ ช่องนี้มีคำเตือนเดียวกับช่องข้อความอิสระอื่น คือห้ามพิมพ์ชื่อผู้ป่วย ระบบเก็บข้อความนี้ไว้กับเหตุการณ์
  3. **ปุ่ม** "ดาวน์โหลดไฟล์ตั้งต้น" ซึ่งไม่ใช้ AI และ "ให้ AI ช่วยร่าง"
- **ไฟล์ตั้งต้น** ดาวน์โหลดได้เสมอ แม้การร่างด้วย AI ปิดอยู่หรือ Gemini ใช้ไม่ได้ ไฟล์มีทุกอย่างในคอลัมน์ "ระบบเติมจากตาราง" ของตารางข้างล่าง และมีบันทึกการสอบสวนต่อท้ายไฟล์ตามที่พิมพ์ไว้ เพื่อให้ผู้สอบสวนย้ายข้อความเข้าหัวข้อเอง
- **สิ่งที่อยู่ในไฟล์** ตัวเลข วันเวลา และตารางทุกตารางมาจากตารางของระบบโดยตรง และใช้ข้อมูล ณ เวลาที่ดาวน์โหลด

  | ส่วนของไฟล์ | ระบบเติมจากตาราง | เว้นให้ผู้สอบสวนเติม |
  |---|---|---|
  | หัวบันทึกข้อความ | ส่วนราชการจากชื่อหน่วยงาน วันที่ดาวน์โหลด และเรื่อง ซึ่งมีโรค หมู่บ้าน และตำบล | ที่ และเรียน ซึ่งไฟล์เว้นว่างไว้ |
  | 1 ความเป็นมา | เวลาที่ได้รับแจ้ง แหล่งข่าวและหน่วยงานที่แจ้ง โรค พื้นที่ ผลและเวลาของการตรวจสอบข่าว ตรวจสอบกับใคร การแจ้งเตือนข่าวแต่ละครั้ง หน่วยงานที่รับงานสอบสวนโรค และเวลาที่ออกสอบสวน | วิธีที่ได้รับแจ้ง สมาชิกทีมสอบสวน วันที่เสร็จสอบสวน และวัตถุประสงค์ |
  | 2 ผลการสอบสวน | ประเภทเหตุการณ์ จำนวนผู้ป่วยและผู้เสียชีวิตตาม[กติกาการนับ](#กติกาการนับ) ตารางผู้ป่วยที่มีลำดับ อายุ เพศ หมู่บ้าน วันเริ่มป่วย การวินิจฉัย ประเภทผู้ป่วย สถานที่รักษา และสภาพผู้ป่วย วันเริ่มป่วยของรายแรกและรายล่าสุด ประชากรของหมู่บ้านปีล่าสุด และตารางค่า HI กับ CI รายรอบเมื่อเหตุการณ์ใช้ชุดโรคติดต่อนำโดยยุงลาย | อาการ ผลตรวจทางห้องปฏิบัติการ ประวัติเสี่ยง ผู้สัมผัส สภาพแวดล้อม อัตราป่วยของกลุ่มเสี่ยง และแหล่งโรคกับวิธีถ่ายทอดโรค |
  | 3 กิจกรรมควบคุมโรคที่ดำเนินการแล้ว | ตารางงานที่มีผลแล้ว: ชนิดงาน หน่วยงานที่ทำ เวลาที่ทำจริง และผลการเทียบเป้าของชุดโรค | กิจกรรมส่งผลต่อการควบคุมโรคอย่างไร |
  | 4 แนวโน้มของการระบาด | ข้อเท็จจริงประกอบ: จำนวนวันที่ผ่านมาตั้งแต่วันเริ่มป่วยของรายล่าสุด และวันที่ของระยะเฝ้าระวัง 28 วันเมื่อใช้ชุดโรค | แนวโน้มพร้อมเหตุผล |
  | 5 สรุปความสำคัญทางสาธารณสุขและความเร่งด่วน | ข้อเท็จจริงประกอบ: โรคนี้เป็นโรคติดต่ออันตรายหรือไม่ และมีผู้เสียชีวิตหรือไม่ | ขนาดของปัญหา ผลกระทบ และความเร่งด่วน |
  | 6 ข้อเสนอเพื่อพิจารณาดำเนินการต่อไป | งานที่มอบหมายแล้วและยังไม่มีผล พร้อมกำหนดเสร็จ | ข้อเสนอของผู้สอบสวน |
  | ท้ายรายงาน | ชื่อของผู้ที่บันทึกผลครั้งแรกของงานสอบสวนโรคที่ออกสอบสวนเร็วที่สุด ชื่อหน่วยงาน และวันที่รายงาน เมื่อผลนั้นเป็นการบันทึกแทนหน่วยบริการ ไฟล์เว้นชื่อไว้ | ตำแหน่ง และลายมือชื่อ ซึ่งไฟล์เว้นว่างไว้ |

- **ช่องที่ยังไม่มีข้อมูล** รายการในคอลัมน์ "เว้นให้ผู้สอบสวนเติม" ของหัวข้อที่ 1 ถึง 6 ที่ยังไม่มีข้อความ ปรากฏในไฟล์เป็นข้อความในวงเล็บเหลี่ยมที่บอกว่าต้องเขียนอะไร เช่น "[ระบุวัตถุประสงค์ของการสอบสวน]" ระบบและ AI ไม่แต่งข้อความแทน
- **ไม่มีชื่อผู้ป่วย** ไฟล์ไม่มีชื่อ-สกุล บ้านเลขที่ และที่อยู่ของผู้ป่วยนอกอำเภอ ผู้ป่วยถูกเรียกด้วยลำดับในเหตุการณ์ เช่น "ผู้ป่วยรายที่ 1" เกณฑ์การเขียนรายงานฉบับสมบูรณ์ของกรมควบคุมโรคจัดการระบุชื่อผู้ป่วยเป็นข้อผิดด้านจริยธรรม และมาตรา 10 ของพระราชบัญญัติโรคติดต่อ พ.ศ. 2558 ให้ประมวลผลข้อมูลจากการสอบสวนโรคโดยไม่เปิดเผยชื่อ แหล่งที่อ่านไม่ได้กำหนดคำเรียกแทน ระบบจึงใช้ลำดับในเหตุการณ์เหมือนไทม์ไลน์ (ผลการค้นเรื่องรายงานสอบสวน ข้อ 7) ไฟล์ไม่มีตัวเลือกให้รวมชื่อ
- **AI เขียนส่วนใด** AI เรียบเรียงย่อหน้าบรรยายของแต่ละหัวข้อ จากข้อมูลที่ระบบส่งและข้อความอิสระที่ผู้ใช้บันทึกไว้แล้ว: รายละเอียดของเหตุการณ์ หมายเหตุของการตรวจสอบข่าว สรุปผลและหมายเหตุของผลการทำงานที่ใช้งานอยู่ และบันทึกการสอบสวน ผู้ใช้จึงไม่ต้องพิมพ์สิ่งที่บันทึกไว้แล้วซ้ำ
- **ส่วนที่เป็นดุลยพินิจ** วัตถุประสงค์ แหล่งโรค ผลของกิจกรรม และหัวข้อที่ 4 ถึง 6 เป็นข้อตัดสินของผู้สอบสวน AI ร่างส่วนเหล่านี้จากข้อความอิสระเท่านั้น เมื่อข้อความอิสระไม่มีเรื่องนั้น ไฟล์คงข้อความในวงเล็บเหลี่ยมไว้
- **ตัวเลขในข้อความของ AI** ระบบตรวจว่าตัวเลขทุกตัวในข้อความที่ AI ตอบมีอยู่ในข้อความที่ส่งไป ย่อหน้าที่มีตัวเลขอื่นถูกทำเครื่องหมาย "[ตรวจตัวเลข]" ในหน้าจอและในไฟล์ ระบบเก็บเครื่องหมายนี้ไว้กับร่างล่าสุด
- **ข้อความของ AI ในไฟล์** ถูกเน้นสี และไฟล์มีบรรทัดแรกว่า "ข้อความที่เน้นสีร่างโดย AI จากข้อมูลในระบบและบันทึกการสอบสวน ผู้สอบสวนตรวจและแก้ก่อนลงนาม" ผู้สอบสวนเอาการเน้นสีและบรรทัดนี้ออกเองเมื่อตรวจแล้ว
- **ข้อมูลที่ส่งให้ AI** server เป็นผู้ประกอบข้อความที่ส่ง ไม่ใช่หน้าเว็บ

  | กลุ่ม | รายการ |
  |---|---|
  | ส่ง | โรค ประเภทเหตุการณ์ ชนิดของแหล่งข่าว เวลาของแต่ละขั้น จำนวนผู้ป่วยและผู้เสียชีวิต ของผู้ป่วยแต่ละราย: ลำดับ ช่วงอายุ 10 ปี เพศ วันเริ่มป่วย การวินิจฉัย ประเภทผู้ป่วย และสภาพผู้ป่วย ของงานแต่ละงาน: ชนิดงาน เวลาที่ทำจริง ค่า HI กับ CI และผลการเทียบเป้า และข้อความอิสระสี่ชนิดข้างต้น |
  | ไม่ส่ง | ชื่อ-สกุล บ้านเลขที่ ที่อยู่ของผู้ป่วยนอกอำเภอ อายุเป็นปี ชื่อของเจ้าหน้าที่ เลขที่เหตุการณ์ และรหัสของแถว |
  | ส่งเป็นคำแทน | ชื่อหมู่บ้าน ตำบล อำเภอ จังหวัด ชื่อหน่วยบริการ ชื่อ สสอ. หน่วยงานที่แจ้ง สถานที่เพิ่มเติม สถานที่รักษา ผู้ที่ใช้ตรวจสอบข่าว และผู้รับการแจ้งเตือนข่าว เช่น "[หมู่บ้าน 1]" และ "[หน่วยบริการ 2]" ชื่อเหล่านี้ที่ปรากฏในข้อความอิสระถูกแทนด้วยคำแทนเดียวกัน ระบบเติมชื่อจริงกลับตอนสร้างไฟล์ |

- **ตรวจก่อนส่ง** เมื่อผู้ดูแลกด "ให้ AI ช่วยร่าง" ระบบแสดงข้อความทั้งหมดที่จะส่ง ข้อความอิสระแต่ละรายการมีตัวเลือก "ไม่ส่งข้อความนี้" ระบบไม่ยอมส่งเมื่อพบชื่อหรือนามสกุลของผู้ป่วยในเหตุการณ์นั้นอยู่ในข้อความ และบอกว่าพบในรายการใด ผู้ดูแลแก้ข้อความหรือเลือกไม่ส่งรายการนั้น แล้วกด "ยืนยันและส่งให้ AI" server ตรวจซ้ำและส่งเฉพาะข้อความที่ตรงกับที่แสดง ถ้าข้อมูลเปลี่ยนระหว่างนั้น ระบบแสดงข้อความใหม่ให้ตรวจอีกครั้ง ระบบจำรายการที่ผู้ดูแลเลือกไม่ส่งไว้กับร่างล่าสุด และเลือกรายการเดิมให้ก่อนในการร่างครั้งถัดไป
- **การเรียก Gemini** server เรียกหนึ่งคำขอต่อการร่างหนึ่งครั้ง ขอคำตอบเป็นโครงสร้างหนึ่งข้อความต่อหนึ่งหัวข้อ สั่งไม่ให้บริการเก็บคำขอเมื่อ API มีตัวเลือกนั้น และไม่ใช้เครื่องมือค้นเว็บ กุญแจของ API และชื่อรุ่นอยู่ในค่าตั้งของ Apps Script ระบบรอคำตอบไม่เกิน 2 นาที ลองใหม่เองหนึ่งครั้งเมื่อ Gemini ตอบว่าไม่พร้อมให้บริการชั่วคราว และส่งข้อความให้ AI ได้ไม่เกิน 30 ครั้งต่อวันตามเวลาไทยทั้งระบบ เพื่อจำกัดค่าใช้จ่าย การนับรวมครั้งที่ไม่สำเร็จ และการลองใหม่เองนับรวมกับคำขอเดิมเป็นหนึ่งครั้ง
- **เมื่อร่างไม่สำเร็จ** หน้าจอบอกสาเหตุเป็นภาษาไทยพร้อมรหัสอ้างอิง ร่างเดิมไม่เปลี่ยน และปุ่ม "ดาวน์โหลดไฟล์ตั้งต้น" ยังใช้ได้
- **ร่างล่าสุด** ระบบเก็บข้อความที่ AI ตอบของการร่างครั้งล่าสุดของแต่ละเหตุการณ์ หน้าร่างรายงานแสดงข้อความนั้นตามหัวข้อแบบอ่านอย่างเดียว พร้อมปุ่ม "ดาวน์โหลดไฟล์ Word" และ "ร่างใหม่" การร่างใหม่ทับร่างเดิมหลังผู้ดูแลยืนยัน ระบบไม่เก็บข้อความที่ส่ง ไม่เก็บร่างรุ่นก่อน และไม่รับไฟล์ที่แก้แล้วกลับเข้ามา รายงานฉบับลงนามอยู่ในแฟ้มของ สสอ.
- **เมื่อข้อมูลเปลี่ยนหลังร่าง** หน้าร่างรายงานบอกว่าข้อมูลของเหตุการณ์เปลี่ยนหลังการร่างครั้งล่าสุด ตารางและตัวเลขในไฟล์ใช้ข้อมูลปัจจุบันเสมอ ส่วนข้อความของ AI เป็นของการร่างครั้งล่าสุด
- **ไฟล์ Word** หน้าเว็บสร้างไฟล์ `.docx` ในเบราว์เซอร์ของผู้ใช้ จากแม่แบบที่อยู่กับหน้าเว็บ server ไม่สร้างและไม่เก็บไฟล์ และไม่มีไฟล์ใน Google Drive ชื่อไฟล์มีเลขที่เหตุการณ์ ระบบไม่มีหน้าแก้เอกสารในเว็บ ไม่ออก PDF และไม่มีหน้าแก้แม่แบบ หน้าดาวน์โหลดเตือนว่าไฟล์ที่ดาวน์โหลดแล้วอยู่นอกการควบคุมของระบบ
- **เวลาที่เขียนรายงานสอบสวนเบื้องต้น** การร่างและการดาวน์โหลดไม่นับว่าเขียนรายงานแล้ว หลังผู้ดูแลดาวน์โหลดไฟล์ของเหตุการณ์ที่ยังไม่ปิด และยังไม่มีงานสอบสวนโรคใดมีเวลาที่เขียนรายงานสอบสวนเบื้องต้น ระบบถามว่าจะบันทึกเวลานั้นหรือไม่ ค่าตั้งต้นคือเวลาปัจจุบัน ผู้ดูแลแก้ได้ เมื่อยืนยัน ระบบบันทึกเป็นการแก้ผลของงานสอบสวนโรคที่ออกสอบสวนเร็วที่สุด และใส่เหตุผลของการแก้ให้เองว่า "บันทึกเวลาที่เขียนรายงานสอบสวนเบื้องต้น"
- **ไทม์ไลน์และบันทึกความปลอดภัย** การร่างด้วย AI ที่สำเร็จเพิ่มหนึ่งแถวในไทม์ไลน์ บันทึกความปลอดภัยเก็บทุกครั้งที่ส่งข้อความให้ AI ทั้งที่สำเร็จและไม่สำเร็จ และทุกครั้งที่ผู้ดูแลดาวน์โหลดไฟล์ โดยไม่มีตัวข้อความ
- **การเปิดและปิด** หน้าตั้งค่ามีค่า "ร่างรายงานด้วย AI" ที่ผู้ดูแลเปิดปิดได้ เมื่อปิด หรือเมื่อ server ไม่มีกุญแจของ API หน้าร่างรายงานไม่มีปุ่ม "ให้ AI ช่วยร่าง" และบอกว่าการร่างด้วย AI ยังไม่เปิดใช้ ร่างที่เก็บไว้ยังอ่านและดาวน์โหลดได้
- **ข้อมูลสมมติและข้อมูลจริง** ระดับที่ไม่เสียค่าใช้จ่ายของ Gemini นำข้อความไปพัฒนาบริการและห้ามส่งข้อมูลส่วนบุคคล จึงใช้ได้กับข้อมูลสมมติเท่านั้น ชุดใช้งานจริงใช้กุญแจของระดับชำระเงิน คำสั่ง[เริ่มใช้ข้อมูลจริง](#การเริ่มใช้ข้อมูลจริง)ปิดการร่างด้วย AI ของชุดใช้งานจริง และลบกุญแจของ API ที่ใช้กับข้อมูลสมมติออกจากค่าตั้งของ Apps Script หลังจากนั้นผู้ดูแลเปิดค่าในหน้าตั้งค่าแล้วก็ยังร่างด้วย AI ไม่ได้ จนกว่า PO ตั้งกุญแจของระดับชำระเงิน ซึ่งเป็นการอนุมัติการเปิดใช้กับข้อมูลจริง ([ADR-0008](adr/0008-delivery-process-and-gates.md)) PO ปิดการเก็บ Logs ของ AI Studio ในโปรเจกต์ของกุญแจนั้นก่อน เพราะโปรเจกต์ที่ผูกการชำระเงินเก็บคำขอไว้โดยค่าเริ่มต้น (ผลการค้นเรื่องการร่างด้วย AI ข้อ 2.4) ระหว่างนั้นผู้ดูแลใช้ไฟล์ตั้งต้นได้
- **สิ่งที่ไม่ทำในรุ่นแรก** รายงานฉบับสมบูรณ์ รายงานสรุปเสนอผู้บริหาร กราฟเส้นโค้งการระบาด แผนที่ และรูปถ่ายในไฟล์ แบบสอบสวนโรคเฉพาะรายยังทำนอกระบบตามเดิม และระบบไม่ส่งรายงานให้ผู้ใด

### คู่มือ

- คู่มือของหน่วยบริการเป็นหน้าเดียวในเว็บของระบบ ทำสำหรับมือถือ เปิดได้โดยไม่ล็อกอิน และมีลิงก์จากหน้าล็อกอินกับเมนู ผู้ใช้เปิดระบบจากลิงก์ใน LINE บนมือถือ คู่มือจึงอยู่ที่เดียวกับระบบ
- หน้านี้ไม่มีข้อมูลของเหตุการณ์ ภาพประกอบถ่ายจากข้อมูลสมมติ
- คู่มือของหน่วยบริการมีหกหัวข้อ: เข้าระบบครั้งแรกด้วยอีเมล Google ส่วนตัว เปิดลิงก์จาก LINE ในเบราว์เซอร์ของเครื่อง รับงานและบันทึกผล แนบรูปและสิ่งที่ห้ามถ่าย แจ้งเหตุการณ์ และติดต่อใครเมื่อเข้าระบบไม่ได้ ซึ่งแสดงช่องทางติดต่อของหน่วยงาน
- คู่มือของผู้ดูแลเป็นอีกหน้าหนึ่ง เห็นเมื่อล็อกอินเป็นผู้ดูแล มีไว้ให้ผู้ดูแลคนที่สองทำงานแทนได้เมื่อผู้ดูแลอีกคนไม่อยู่ มีหกหัวข้อ: เส้นทางของเหตุการณ์จากรับแจ้งถึงปิด มอบหมายงานและส่งข้อความ LINE รับผลและบันทึกผลแทนหน่วยบริการ ร่างรายงานสอบสวน เพิ่มและระงับผู้ใช้ และสิ่งที่ต้องทำเมื่อเห็นแถบเตือนของชุดสำรอง พื้นที่ หรือการแชร์
- ไม่มีคู่มือของผู้ดู ไม่มีไฟล์ PDF และไม่มีวิดีโอ
- เมื่อหน้าจอที่คู่มือกล่าวถึงเปลี่ยน คู่มือถูกแก้ใน PR เดียวกัน

## 5. ชุดโรค

ทุกโรคใช้ขั้นตอนในข้อ 3 เหมือนกัน **ชุดโรค** (disease pack) เพิ่มสี่อย่างให้โรคที่มีแนวทางเฉพาะ: ชนิดงาน เป้าเวลา แบบบันทึกผล และรอบการทำงาน ชุดโรคเป็นคำนิยามในโค้ด การเพิ่มโรคใหม่ไม่เปลี่ยนตาราง ([ADR-0005](adr/0005-fixed-core-tables-and-disease-packs.md))

### กฎที่ใช้กับทุกชุดโรค

- **โรคกับชุดโรค** ผู้ดูแลเลือกชุดโรคของแต่ละโรคในหน้ารายการโรค จากชุดที่มีในโค้ด โรคหนึ่งใช้ได้ชุดเดียว และชุดหนึ่งใช้กับหลายโรคได้ เหตุการณ์ใช้ชุดของโรคปัจจุบันของตนเสมอ เมื่อชุดนั้นเปิดใช้อยู่
- **เมื่อผู้ดูแลแก้โรคของเหตุการณ์** ถ้าโรคใหม่มีชุดโรค ระบบเริ่มเสนองานของชุดตั้งแต่ตอนนั้น ถ้าโรคใหม่ไม่ใช้ชุดเดิม ระบบแสดงงานของชุดเดิมที่ยังไม่มีผลการทำงาน และยกเลิกเมื่อผู้ดูแลยืนยัน ด้วยเหตุผล "เปลี่ยนโรค" งานที่มีผลแล้วอยู่ต่อ
- **การเสนองาน** ระบบเปิดแบบ "มอบหมายงานตามชุดโรค" ให้ผู้ดูแลในสามจังหวะ: หลังบันทึกผลประเมินเกณฑ์ เมื่อเหตุการณ์มีผู้ป่วยที่ยังไม่มีงานของชุด, หลังผู้ดูแลเพิ่มผู้ป่วยในเหตุการณ์ที่กำลังดำเนินการ และจากปุ่มในกลุ่ม "ผู้ป่วยที่ยังไม่มีงานตามชุดโรค" ของหน้า ["งานวันนี้"](#ผู้ดูแล-งานวันนี้) แบบนี้แสดงทุกงานที่ชุดเสนอ พร้อมหน่วยบริการและกำหนดเสร็จ ผู้ดูแลเอางานออก แก้หน่วย หรือแก้กำหนดเสร็จได้ แล้วยืนยันครั้งเดียว ระบบสร้างทุกงานในคำขอเดียว และเตรียมข้อความ LINE หนึ่งข้อความต่อหนึ่งหน่วย ระบบไม่สร้างงานโดยไม่มีการยืนยัน
- **หน่วยบริการที่ได้งาน** งานที่ผูกกับผู้ป่วยเสนอให้หน่วยที่รับผิดชอบหมู่บ้านของผู้ป่วย งานที่ไม่ผูกกับผู้ป่วยเสนอให้หน่วยที่รับผิดชอบหมู่บ้านของเหตุการณ์ ถ้าหมู่บ้านนั้นยังไม่มีหน่วยที่รับผิดชอบ ผู้ดูแลเลือกหน่วยเอง
- **ผู้ป่วยนอกอำเภอ** ระบบไม่เสนองานของชุดให้ผู้ป่วยที่อยู่นอกอำเภอ และไม่แสดงรายนั้นในกลุ่ม "ผู้ป่วยที่ยังไม่มีงานตามชุดโรค" เพราะบ้านอยู่นอกพื้นที่ที่ สสอ. มอบหมายงานได้ ผู้ดูแลยังสร้างงานเองได้ และรายนั้นยังนับเป็นผู้ป่วยของเหตุการณ์
- **ประเภทผู้ป่วย** ผู้ป่วยทุกประเภท รวมผู้ป่วยสงสัย ได้งานของชุด
- **งานของชุดที่ผู้ดูแลเพิ่มเอง** ในเหตุการณ์ที่ใช้ชุดโรค แบบมอบหมายงานปกติมีชนิดงานของชุดให้เลือกเพิ่มจากชนิดงานกลาง งานที่เพิ่มเองใช้แบบบันทึกผลของชนิดนั้น ผู้ดูแลกำหนดเสร็จเอง งานไม่อยู่ในรอบใด จึงมีเฉพาะการเทียบเป้าเวลากับกำหนดเสร็จ ไม่มีเป้าของผล และไม่ถูกนับเป็นรอบของมาตรการ
- **จุดเริ่มนับ** รอบการทำงานนับจาก**เวลาที่หน่วยบริการได้รับรายงาน** ซึ่งคือเวลาที่แจ้งหน่วยบริการของงานนั้น งานของชุดที่มอบให้หน่วยซึ่งเป็นผู้เพิ่มผู้ป่วยรายนั้นเองได้เวลาที่แจ้งหน่วยบริการเป็นเวลาที่หน่วยเพิ่มผู้ป่วย ตั้งแต่ตอนสร้างงาน แบบ "มอบหมายงานตามชุดโรค" มีช่อง "หน่วยบริการได้รับรายงานเมื่อ" ค่าตั้งต้นคือ "จะแจ้งหลังบันทึกนี้" ผู้ดูแลเปลี่ยนเป็นเวลาที่ผ่านมาแล้วได้เมื่อแจ้งไปก่อนแล้ว เช่น ทางโทรศัพท์ ซึ่งระบบบันทึกเป็นเวลาที่แจ้งหน่วยบริการของงานที่สร้าง
- **กำหนดเสร็จ** ระบบคำนวณกำหนดเสร็จตอนสร้างงานจากเวลาที่หน่วยบริการได้รับรายงาน ถ้างานยังไม่มีเวลาที่แจ้งหน่วยบริการ ระบบใช้เวลาที่สร้างงานไปก่อน เมื่อผู้ดูแลยืนยันหรือแก้เวลาที่แจ้งหน่วยบริการ หน้ายืนยันแสดงกำหนดเสร็จใหม่ของงานของชุดที่ยังไม่มีผลการทำงาน และบันทึกพร้อมกันในคำขอเดียว งานที่ผู้ดูแลแก้กำหนดเสร็จเองแล้วไม่ถูกปรับ เวลาที่แจ้งหน่วยบริการซึ่งระบบใส่เองเมื่อหน่วยบริการรับงานหรือบันทึกผล ไม่ปรับกำหนดเสร็จ
- **ผลการเทียบเป้า** งานของชุดมีผลการเทียบได้สองค่า แสดงและนับแยกกัน แต่ละค่ามี 4 แบบ ระบบไม่เดาค่าที่ขาด

  | แบบ | เทียบเป้าเวลา | เทียบเป้าผล (เฉพาะรอบที่มีเป้าของผล) |
  |---|---|---|
  | ถึงเป้า | เวลาที่ทำจริงไม่เกินกำหนดเสร็จ และทำสิ่งที่รอบนั้นกำหนดแล้ว | ทุกค่าที่กรอกอยู่ในเกณฑ์ และค่าที่รอบนั้นต้องใช้มีครบ |
  | ไม่ถึงเป้า | เวลาที่ทำจริงเกินกำหนดเสร็จ ไม่ได้ทำสิ่งที่รอบนั้นกำหนด หรือเลยกำหนดเสร็จแล้วยังไม่มีผลการทำงาน | มีค่าที่กรอกอย่างน้อยหนึ่งค่าเกินเกณฑ์ |
  | ยังไม่ครบกำหนด | ยังไม่มีผลการทำงาน และยังไม่ถึงกำหนดเสร็จ | ยังไม่มีผลการทำงาน และยังไม่ถึงกำหนดเสร็จ |
  | ประเมินไม่ได้ | ขาดเวลาที่ต้องใช้ เช่น ผู้ป่วยไม่มีเวลาที่วินิจฉัย | ค่าที่รอบนั้นต้องใช้ว่าง และไม่มีค่าใดเกินเกณฑ์ หรือเลยกำหนดเสร็จแล้วยังไม่มีผลการทำงาน |

  งานที่ถูกยกเลิก และงานของผู้ป่วยที่ถูกยกเลิก ไม่ถูกนับ การเทียบเป้าเวลาใช้กำหนดเสร็จที่เก็บอยู่กับงาน การแก้กำหนดเสร็จอยู่ในไทม์ไลน์
- **ตารางของชุดโรคในหน้าเหตุการณ์** แถวเป็นผู้ป่วยแต่ละรายและงานที่ไม่ผูกกับผู้ป่วย คอลัมน์เป็นรอบ แต่ละช่องแสดงสถานะของงานและผลการเทียบเป้าทั้งสองค่า
- **ผลที่ไม่ถึงเป้า** งานที่เทียบเป้าผลได้ "ไม่ถึงเป้า" มีป้าย "ผลไม่ถึงเป้า" ในกลุ่ม "ผลรอตรวจ" ผู้ดูแลตัดสินเองว่าจะมอบหมายงานซ้ำหรือไม่ ระบบไม่สร้างงานเอง
- **สิ่งที่หน่วยบริการเห็น** หน้างานแสดงชื่อรอบ กำหนดเสร็จ เป้าหมายของรอบ และคำแนะนำของมาตรการ เมื่อกรอกค่าที่มีเป้า แบบบันทึกแสดงผลการเทียบทันที หลังบันทึก หน่วยบริการเห็นผลการเทียบเป้าของงานของตน และไม่เห็นตารางของชุดโรคของทั้งเหตุการณ์
- **หน้าตั้งค่าชุดโรค** ผู้ดูแลเปิดปิดชุดโรค แก้เป้าเวลา และแก้จำนวนวันของแต่ละรอบได้ หน้านี้แสดงค่าตั้งต้นของมาตรการคู่กับค่าที่ใช้อยู่ มีปุ่มคืนค่าตั้งต้น และแสดงชนิดงาน แบบบันทึกผล กับเป้าของผลให้อ่านอย่างเดียว เพราะสามอย่างนี้แก้ได้ในโค้ดเท่านั้น ค่าที่แก้มีผลกับงานที่สร้างหลังจากนั้น ระบบบันทึกผู้แก้และวันที่แก้
- **เมื่อปิดชุดโรค** ระบบเลิกเสนองาน เลิกแสดงกลุ่ม "ผู้ป่วยที่ยังไม่มีงานตามชุดโรค" และใช้นิยาม "รอปิด" ทั่วไปกับเหตุการณ์ของโรคนั้น งานของชุดที่สร้างไว้แล้วอยู่ต่อ และยังเทียบเป้าตามเดิม

### ชุดโรคติดต่อนำโดยยุงลาย (รุ่นแรก)

ชุดนี้ทำตาม **มาตรการควบคุมโรค 3-3-1 (3-7-14-21-28)** ใน "มาตรการดำเนินงานเฝ้าระวัง ป้องกัน และควบคุมโรคติดต่อนำโดยยุงลายในช่วงการระบาด พ.ศ. 2569 (ฉบับปรับปรุง)" ของกองโรคติดต่อนำโดยแมลง กรมควบคุมโรค ซึ่งกระทรวงสาธารณสุขส่งถึงนายแพทย์สาธารณสุขจังหวัดทุกจังหวัดเมื่อเมษายน 2569 เป็นฉบับใหม่ที่สุดที่พบเมื่อ 17 พฤศจิกายน 2569 ข้อความต้นฉบับ ความต่างจากฉบับก่อน และแหล่งข้อมูลทั้งหมดอยู่ใน[ผลการค้นเรื่องมาตรการ 3-3-1](research/dengue-pack-facts.md) ซึ่งเรียกฉบับนี้ว่า [D13]

มาตรการใช้กับโรคติดต่อนำโดยยุงลายสามโรค ชุดนี้จึงเป็นชุดตั้งต้นของ "ไข้เด็งกี่" "ไข้ปวดข้อยุงลาย" และ "โรคติดเชื้อไวรัสซิกา" ในรายการโรค ผู้ดูแลเอาชุดออกจากโรคใดก็ได้

มาตรการถูกแก้ทุกหนึ่งถึงสองปี เมื่อกรมออกฉบับใหม่ การแก้ชนิดงาน แบบบันทึกผล และเป้าของผล ทำในโค้ดผ่าน PR พร้อมแก้หัวข้อนี้

#### มาตรการฉบับ พ.ศ. 2569

ตารางนี้สรุปจากต้นฉบับ "ได้รับรายงาน" หมายถึงหน่วยบริการในพื้นที่ได้รับรายงานว่ามีผู้ป่วย

| วัน | ผู้ทำตามมาตรการ | งาน | พื้นที่ | เป้าหมายตามมาตรการ |
|---|---|---|---|---|
| 0 | สถานบริการสาธารณสุขที่พบผู้ป่วย | รายงานให้ สสอ. รพ.สต. และ อปท. ทราบ | — | ภายใน 3 ชั่วโมงแรก |
| 0 | รพ.สต. ร่วมกับ อสม. และชุมชน | ตรวจสอบข้อมูลผู้ป่วย ประเมินความเสี่ยงของพื้นที่ ทำลายแหล่งเพาะพันธุ์ยุงลาย และแนะนำให้เจ้าของบ้านใช้สเปรย์กระป๋องกำจัดยุง | บ้านผู้ป่วย | ภายใน 3 ชั่วโมงหลังได้รับรายงาน |
| 1 | อสม. อสส. และ อปท. | สำรวจและทำลายแหล่งเพาะพันธุ์ยุงลาย และ อปท. พ่นสารเคมีกำจัดยุง ทั้งในและนอกบ้าน | บ้านผู้ป่วย บ้านในรัศมี 100 เมตร และจุดที่สงสัยเป็นแหล่งโรค | 1 วันหลังได้รับรายงาน |
| 3 | อสม. อสส. หรือ อปท. | พ่นสารเคมีซ้ำเป็นครั้งที่ 2 | รัศมี 100 เมตรเดิม | — |
| 7 | อสม. อสส. หรือ อปท. | สำรวจแหล่งเพาะพันธุ์ซ้ำ และพ่นสารเคมีหากจำเป็น | ที่เดิม | HI และ CI ในรัศมี 100 เมตรจากบ้านผู้ป่วยเป็นศูนย์ |
| 14 | อสม. อสส. หรือ อปท. | สำรวจและทำลายแหล่งเพาะพันธุ์ยุงลายทั้งหมู่บ้าน และเฝ้าระวังผู้ป่วยรุ่นที่ 2 | หมู่บ้านที่พบผู้ป่วย | HI ของหมู่บ้านไม่เกินร้อยละ 5 |
| 21 | อสม. อสส. หรือ อปท. | เหมือนวันที่ 14 | หมู่บ้านที่พบผู้ป่วย | HI ของหมู่บ้านไม่เกินร้อยละ 5, CI ของสถานพยาบาลและโรงเรียนเป็นศูนย์ และ CI ของโรงธรรม โรงแรม โรงงาน และสถานที่ราชการไม่เกินร้อยละ 5 |
| 28 | ชุมชน | คงการสำรวจและทำลายแหล่งเพาะพันธุ์ทุก 7 วัน และเฝ้าระวังผู้ป่วยรุ่นที่ 2 หลังจาก 28 วัน ทบทวนและถอดบทเรียน | ชุมชน | — |

หมายเหตุของมาตรการเรื่องผู้ป่วยรายใหม่ ซึ่งระบบแสดงเป็นคำแนะนำ

- ผู้ป่วยรายใหม่**ใน**รัศมี 100 เมตรเดิม: พ่นสารเคมีเฉพาะบ้านผู้ป่วยรายใหม่ภายใน 1 วันหลังได้รับแจ้ง และถ้าพบหลังวันที่ 7 ให้คงการพ่นเสริมทุก 7 วันในรัศมี 100 เมตร จนกว่าการแพร่เชื้อจะหยุดลง
- ผู้ป่วยรายใหม่**นอก**รัศมี 100 เมตรเดิม: พ่นสารเคมีทั้งกลุ่มบ้านหรือหมู่บ้าน เพิ่มจากรัศมี 100 เมตร ในวันที่ 1, 3, 7 แล้วคงการพ่นเสริมทุก 7 วัน จนกว่าการแพร่เชื้อจะหยุดลง
- การระบาดต่อเนื่องเกิน 2 ชั่วอายุยุง หรือประมาณ 28 วัน: สำนักงานสาธารณสุขจังหวัดลงพื้นที่ประเมินประสิทธิภาพของมาตรการ

#### งาน รอบ และแบบบันทึกผล

ผู้ป่วยรายแรกของเหตุการณ์ได้ 6 งาน ทุกงานมอบให้หน่วยบริการ ซึ่งเป็นผู้ประสานกับ อสม. และองค์กรปกครองส่วนท้องถิ่น และเป็นผู้บันทึกผล หน่วยงานที่พ่นจริงบันทึกไว้ในแบบบันทึกผล และไม่ต้องมีบัญชีในระบบ

| รอบ | งาน | ผูกกับ | กำหนดเสร็จ | ช่องในแบบบันทึกผล นอกจากเวลาที่ทำและหมายเหตุ | เป้าของผล |
|---|---|---|---|---|---|
| วันที่ 0 (`day_0`) | ลงพื้นที่บ้านผู้ป่วย | ผู้ป่วย | 3 ชั่วโมงหลังได้รับรายงาน | ทำลายแหล่งเพาะพันธุ์แล้วหรือไม่ และฉีดหรือแนะนำให้ใช้สเปรย์กระป๋องแล้วหรือไม่ | — |
| วันที่ 1 (`day_1`) | สำรวจ ทำลายแหล่งเพาะพันธุ์ และพ่นสารเคมี รัศมี 100 เมตร | ผู้ป่วย | 24 ชั่วโมงหลังได้รับรายงาน | พ่นสารเคมีหรือไม่ หน่วยงานที่พ่น และจำนวนหลังคาเรือนที่พ่น | — |
| วันที่ 3 (`day_3`) | พ่นสารเคมีซ้ำ รัศมี 100 เมตร | ผู้ป่วย | สิ้นวันที่ 3 | เหมือนวันที่ 1 | — |
| วันที่ 7 (`day_7`) | สำรวจซ้ำ รัศมี 100 เมตร | ผู้ป่วย | สิ้นวันที่ 7 | HI, CI และพ่นสารเคมีหรือไม่ | HI และ CI เป็นศูนย์ |
| วันที่ 14 (`day_14`) | สำรวจทั้งหมู่บ้าน | เหตุการณ์ | สิ้นวันที่ 14 | HI | HI ไม่เกินร้อยละ 5 |
| วันที่ 21 (`day_21`) | สำรวจทั้งหมู่บ้านและสถานที่ | เหตุการณ์ | สิ้นวันที่ 21 | HI, CI ของสถานพยาบาลและโรงเรียน และ CI ของศาสนสถาน โรงแรม โรงงาน และสถานที่ราชการ | HI ไม่เกินร้อยละ 5, CI ของกลุ่มแรกเป็นศูนย์ และ CI ของกลุ่มหลังไม่เกินร้อยละ 5 |

- วันที่ N คือวันตามปฏิทินไทยที่ถัดจากวันที่หน่วยบริการได้รับรายงานไป N วัน
- **HI และ CI** กรอกเป็นร้อยละ ตั้งแต่ 0 ถึง 100 ทศนิยมไม่เกินสองตำแหน่ง ระบบไม่คำนวณค่านี้เอง และไม่เก็บจำนวนบ้านกับจำนวนภาชนะ ทุกช่องเว้นว่างได้ ช่องที่ว่างทำให้ผลการเทียบเป็น "ประเมินไม่ได้" ตามตารางในกฎทั่วไป ค่าที่รอบต้องใช้คือ HI ของทุกรอบที่มีเป้า และ CI ของรอบวันที่ 7 ส่วน CI ของสถานที่ในรอบวันที่ 21 เว้นว่างได้เมื่อหมู่บ้านไม่มีสถานที่กลุ่มนั้น
- แบบบันทึกผลขอ HI และ CI เฉพาะรอบที่มาตรการกำหนดเป้า รอบวันที่ 1 และ 3 ไม่มีช่องนี้
- **เวลาที่ทำของรอบวันที่ 1 และ 3** คือเวลาที่พ่นสารเคมี งานของสองรอบนี้ที่บันทึกว่าไม่ได้พ่น ได้ผลการเทียบเป้าเวลาเป็น "ไม่ถึงเป้า"
- เมื่อเวลาที่ทำเกินกำหนดเสร็จ แบบบันทึกขอให้ระบุเหตุที่ล่าช้าในหมายเหตุ ตรงกับช่อง "ปัจจัยล่าช้า" ในแบบติดตามของกรม ระบบไม่เก็บ "ปัจจัยสนับสนุน"
- งานพ่นสารเคมีแสดงคำแนะนำของมาตรการ: พ่นทั้งในและนอกบ้าน ที่บ้านผู้ป่วย บ้านในรัศมี 100 เมตร และจุดที่สงสัยเป็นแหล่งโรค
- งานรอบวันที่ 14 และ 21 แสดงคำแนะนำ: ถ้าพบผู้ป่วยรายใหม่ในหมู่บ้าน ให้เพิ่มผู้ป่วยในเหตุการณ์
- มาตรการฉบับนี้ไม่มีการทำประชาคม ชุดจึงไม่เสนองานนี้ ผู้ดูแลที่ต้องการมอบหมายใช้ชนิดงานกลาง "อื่น ๆ"
- การสอบสวนโรคเป็นงานของชนิดงานกลาง "สอบสวนโรค" ไม่ใช่ช่องในแบบบันทึกผลของชุดนี้

#### เป้าเวลา

| เป้าเวลา | เริ่มนับ | สิ้นสุด | ค่าตั้งต้น |
|---|---|---|---|
| แจ้งหน่วยบริการ | เวลาที่พบผู้ป่วยหรือวินิจฉัย | เวลาที่หน่วยบริการได้รับรายงาน | 3 ชั่วโมง |
| ลงพื้นที่บ้านผู้ป่วย | เวลาที่หน่วยบริการได้รับรายงาน | เวลาที่ทำของงานรอบวันที่ 0 | 3 ชั่วโมง |
| พ่นสารเคมี | เวลาที่หน่วยบริการได้รับรายงาน | เวลาที่ทำของงานรอบวันที่ 1 | 24 ชั่วโมง |

- เป้า "แจ้งหน่วยบริการ" เทียบรายผู้ป่วย โดยใช้เวลาที่แจ้งหน่วยบริการของงานรอบวันที่ 0 ของผู้ป่วยรายนั้น ผู้ป่วยที่ไม่มีเวลาที่วินิจฉัยได้ผลเป็น "ประเมินไม่ได้"
- ผู้ป่วยที่หน่วยบริการเพิ่มเอง หน่วยนั้นได้รับรายงานตั้งแต่เวลาที่เพิ่มผู้ป่วย
- ระบบไม่มีข้อยกเว้นสำหรับการได้รับรายงานนอกเวลาราชการ เพราะตัวชี้วัดของกรมนับผู้ป่วยกลุ่มนี้รวมด้วย
- สามเป้านี้ตรงกับตัวชี้วัดของแนวทางการติดตามประเมินมาตรการควบคุมโรค 3-3-1 ปีงบประมาณ 2568 ของกองโรคติดต่อนำโดยแมลง ไม่พบว่าตัวชี้วัดนี้ยังใช้ในปีงบประมาณ 2569 และ 2570

#### ตารางติดตามตามแบบของกรม

แบบติดตามการประเมินมาตรการ 3-3-1 ของกรมมีวันและเวลาสี่จุดต่อผู้ป่วยหนึ่งราย ระบบมีครบจากงานของชุด ผู้ใช้ไม่ต้องกรอกเพิ่ม

| ช่องในแบบของกรม | ค่าในระบบ |
|---|---|
| วันและเวลาที่ได้รับการวินิจฉัย | เวลาที่พบผู้ป่วยหรือวินิจฉัยของผู้ป่วย |
| วันและเวลาที่รายงานให้ รพ.สต. ทราบ | เวลาที่หน่วยบริการได้รับรายงาน |
| วันและเวลาที่ รพ.สต. ดำเนินการ | เวลาที่ทำของงานรอบวันที่ 0 |
| วันและเวลาที่ อปท. พ่นสารเคมี | เวลาที่ทำของงานรอบวันที่ 1 |
| ปัจจัยล่าช้า | หมายเหตุของผลการทำงาน |

ตารางของชุดโรคในหน้าเหตุการณ์แสดงสี่จุดเวลานี้และผลการเทียบเป้าเวลาสามค่าของผู้ป่วยแต่ละราย เรียงตามแบบของกรม ไฟล์ส่งออกตามแบบนี้และร้อยละรายสัปดาห์อยู่ใน[ข้อ 6](#6-สรุปภาพรวมและการส่งออก)

#### ผู้ป่วยรายถัดไปในเหตุการณ์เดิม

- ระบบเสนองานที่ผูกกับผู้ป่วยครบสี่งานให้ผู้ป่วยรายใหม่ทุกราย และแสดงหมายเหตุของมาตรการเรื่องในรัศมีกับนอกรัศมี 100 เมตรเดิมเป็นคำแนะนำในแบบ ผู้ดูแลเอางานออกเอง เช่น เมื่อบ้านอยู่ติดกับผู้ป่วยรายก่อน ระบบตัดสินเองไม่ได้เพราะไม่เก็บพิกัดบ้าน
- ระบบเสนองานรอบวันที่ 14 และ 21 ของผู้ป่วยรายใหม่เพิ่ม และไม่เลื่อนงานรอบเดิม หมู่บ้านที่ยังมีผู้ป่วยเพิ่มจึงถูกสำรวจถี่ขึ้น งานที่เสนอซึ่งกำหนดเสร็จห่างจากงานสำรวจทั้งหมู่บ้านที่มีอยู่และไม่ถูกยกเลิกไม่เกิน 3 วัน ระบบไม่เลือกให้ ผู้ดูแลเลือกเองได้
- แบบแสดงงานของชุดที่เหตุการณ์มีอยู่แล้วข้างงานที่เสนอ

#### ระยะเฝ้าระวัง 28 วัน และการปิดเหตุการณ์

- **ระยะเฝ้าระวัง** คือ 28 วันนับจากวันที่หน่วยบริการได้รับรายงานของผู้ป่วยรายล่าสุดของเหตุการณ์ วันที่หน่วยบริการได้รับรายงานของผู้ป่วยคือเวลาที่แจ้งหน่วยบริการที่เร็วที่สุดของงานของชุดที่ผูกกับผู้ป่วยรายนั้นและไม่ถูกยกเลิก ถ้างานเหล่านั้นยังไม่มีเวลาที่แจ้ง ใช้เวลาที่มอบหมาย ผู้ป่วยที่ไม่มีงานของชุดใช้เวลาที่ผู้ป่วยถูกเพิ่มในระบบ
- หน้าเหตุการณ์แสดงว่าวันนี้เป็นวันที่เท่าไรของระยะเฝ้าระวัง
- เหตุการณ์ที่ใช้ชุดนี้ขึ้นกลุ่ม "รอปิด" เมื่อเข้านิยาม "รอปิด" ทั่วไป ไม่มีผู้ป่วยที่ยังไม่มีงานตามชุดโรค และครบระยะเฝ้าระวังแล้ว แถวแสดง "ครบ 28 วัน ไม่มีผู้ป่วยรายใหม่" ก่อนหน้านั้นเหตุการณ์ไม่ขึ้นกลุ่ม "รอปิด" ผู้ดูแลยังปิดจากหน้าเหตุการณ์ได้ทุกเมื่อ และระบบไม่ปิดเหตุการณ์เอง
- ระบบไม่เตือนให้เพิ่มรอบสำรวจทุก 7 วัน เพราะการสำรวจทุก 7 วันตามมาตรการเป็นงานประจำของชุมชนและ อสม. ผู้ดูแลเพิ่มงานสำรวจหรืองานพ่นเสริมเองได้ด้วยงานของชุดที่เพิ่มเอง
- การทบทวนและถอดบทเรียนหลัง 28 วันบันทึกในสรุปตอนปิดเหตุการณ์ ระบบไม่มีช่องแยก

#### ข้อเท็จจริงของอำเภอที่ PO ให้

PO ให้ข้อมูลเมื่อ 17 พฤศจิกายน 2569

- หน่วยงานในอำเภอบันทึกผลสำรวจลูกน้ำ ค่า HI และ CI ในแอปสมาร์ท อสม. อยู่แล้ว การกรอก HI และ CI ในระบบนี้จึงเป็นการกรอกซ้ำ PO ให้กรอกไปก่อนในเบื้องต้น และทบทวนหลังการทดลองใช้ในช่วงที่ 7 ของ [roadmap](roadmap.md)
- อำเภอใช้ D506 ซึ่งเป็นแบบรายงานการเฝ้าระวังทางระบาดวิทยาในรูปแบบดิจิทัล D506 ไม่มีขั้นตอนของมาตรการ 3-3-1 ระบบนี้ไม่เชื่อมต่อกับ D506 ผู้ดูแลที่พบผู้ป่วยจาก D506 เลือกแหล่งข่าวเป็น "D506" และกรอกเวลาที่วินิจฉัยตามที่เห็นในนั้น
- แบบรายงานอ้างอิงแบบของมาตรฐาน 3-3-1 ระดับประเทศก่อน

#### ข้อตีความที่มาตรการไม่ได้ระบุ

มาตรการไม่ได้ระบุเรื่องเหล่านี้ไว้ชัด PO รับวิธีที่ระบบทำเมื่อ 17 พฤศจิกายน 2569 ผลการเทียบกับแหล่งข้อมูลอยู่ใน[ผลการค้น ส่วนที่ 12](research/dengue-pack-facts.md)

1. "1 วันหลังได้รับรายงาน" ของรอบวันที่ 1 คือ 24 ชั่วโมง ส่วนรอบวันที่ 3, 7, 14 และ 21 ครบกำหนดเมื่อสิ้นวันนั้น
2. ผู้ป่วยทุกประเภทเริ่มมาตรการ ต้นฉบับเขียนว่า "วันที่พบผู้ป่วยยืนยัน" แต่แผนผังในฉบับเดียวกันให้เริ่มทันทีเมื่อผลตรวจคัดกรองเป็นบวก
3. เมื่อหน่วยบริการเป็นผู้เพิ่มผู้ป่วยเอง เวลาที่หน่วยบริการได้รับรายงานคือเวลาที่เพิ่มผู้ป่วย
4. งานรอบวันที่ 14 และ 21 เสนอรายผู้ป่วย ไม่เลื่อนงานรอบเดิม และไม่เลือกงานที่ห่างจากงานสำรวจทั้งหมู่บ้านที่มีอยู่ไม่เกิน 3 วัน
5. การสำรวจ CI ของสถานที่ในรอบวันที่ 21 อยู่ในงานเดียวกับการสำรวจหมู่บ้าน และใช้ขอบเขตหมู่บ้าน ต้นฉบับไม่ระบุขอบเขตพื้นที่ และใช้คำว่า "โรงธรรม" ซึ่งแบบบันทึกผลใช้คำว่า "ศาสนสถาน" ตามฉบับก่อน
6. ระยะเฝ้าระวัง 28 วันนับจากวันที่หน่วยบริการได้รับรายงานของผู้ป่วยรายล่าสุด เอกสารของกรมใช้ทั้งวันที่พบผู้ป่วยและวันเริ่มป่วยเป็นวันอ้างอิง และไม่มีเอกสารใดกำหนดเกณฑ์ปิดเหตุการณ์
7. งานรอบวันที่ 0 มีช่อง "ฉีดหรือแนะนำให้ใช้สเปรย์กระป๋อง" ช่องเดียว เพราะตารางของต้นฉบับให้แนะนำเจ้าของบ้าน แต่แผนผังในฉบับเดียวกันยังให้ทีมฉีดสเปรย์ในบ้านผู้ป่วย
8. ร้อยละของเป้าเวลาสามค่าจัดผู้ป่วยเข้าสัปดาห์ระบาดตามเวลาที่พบผู้ป่วยหรือวินิจฉัย รายที่ไม่มีค่านี้ใช้เวลาที่ถูกเพิ่มในระบบ แนวทางการติดตามประเมินให้เก็บข้อมูล "ตามสัปดาห์ระบาด" โดยไม่ระบุว่าใช้วันที่ใด และช่องวันที่ช่องแรกของแบบรายผู้ป่วยคือวันที่ได้รับการวินิจฉัย ([ผลการค้นเรื่องหน้าสรุปและการส่งออก](research/summary-export-facts.md) ส่วนที่ 3)

#### ส่วนของมาตรการที่รุ่นแรกไม่ครอบคลุม

ผู้ดูแลยังสร้างงานเองได้ทุกกรณี แต่ระบบไม่เสนอและไม่เตือนให้

- การตัดสินว่าผู้ป่วยรายใหม่อยู่ในหรือนอกรัศมี 100 เมตรเดิม และการพ่นเสริมทุก 7 วัน
- การเฝ้าระวังและติดตามผู้ป่วยรุ่นที่ 2 ซึ่งต้นฉบับไม่นิยาม ระบบแสดงเพียงผู้ป่วยรายใหม่ที่ถูกเพิ่มในเหตุการณ์
- การรณรงค์ทำลายแหล่งเพาะพันธุ์ภายใน 7 วันเมื่อมีฝนตกในพื้นที่ที่มีการแพร่เชื้อ
- การประเมินพื้นที่ระบาดต่อเนื่องโดยสำนักงานสาธารณสุขจังหวัด
- การดำเนินการแบบทั้งกลุ่มบ้านหรือหมู่บ้านเมื่อพื้นที่ระบาดต่อเนื่องจนทำตามมาตรการรายผู้ป่วยไม่ได้

## 6. สรุปภาพรวมและการส่งออก

ผู้ดูแลและผู้ดูเห็นหน้า "สรุปภาพรวม" เหมือนกัน หน้านี้เป็นหน้าแรกของผู้ดู ผู้ใช้หน่วยบริการไม่มีหน้านี้และส่งออกไม่ได้ ข้อเท็จจริงเรื่องสัปดาห์ระบาด อัตราป่วย และแบบของกรมที่หัวข้อนี้ใช้อยู่ใน[ผลการค้นเรื่องหน้าสรุปและการส่งออก](research/summary-export-facts.md) ที่มาของตัวชี้วัดอยู่ใน[ผลการค้นมาตรฐาน ส่วนที่ 8](research/event-handling-standards.md)

### กติกาการนับ

- **กติกาเดียว** ทุกตัวเลขของหน้านี้นับจากเหตุการณ์ที่เวลาที่ได้รับแจ้งอยู่ในช่วงที่เลือก ตามเวลาไทย และใช้หมู่บ้านของเหตุการณ์ ผู้ป่วย ผู้เสียชีวิต และงานนับตามเหตุการณ์ที่ตนอยู่ หน้าจอเขียนกำกับว่า "นับตามวันรับแจ้ง"
- ตัวอย่าง: เหตุการณ์ที่รับแจ้ง 30 ธันวาคม 2569 ในหมู่ 3 ผู้ดูแลกรอกจำนวนผู้ป่วย 30 ราย ใส่รายชื่อ 3 ราย หนึ่งรายบ้านอยู่หมู่ 7 และงานเสร็จ 2 มกราคม 2570 เหตุการณ์ ผู้ป่วย 30 ราย และงานทุกงาน นับเป็นของเดือนธันวาคม 2569 หมู่ 3
- ระบบไม่นับผู้ป่วยตามวันเริ่มป่วยและหมู่บ้านของผู้ป่วยแต่ละราย เพราะผู้ป่วยที่ไม่ได้ใส่รายชื่อไม่มีสองค่านี้ และระบบนี้เป็นทะเบียนรับแจ้งข่าว ไม่ใช่ระบบรายงานผู้ป่วย
- **จำนวนผู้ป่วยและผู้เสียชีวิต** ของเหตุการณ์หนึ่งคือค่าที่มากกว่าระหว่างจำนวนที่ผู้ดูแลกรอกกับจำนวนรายชื่อ ([ข้อ 3](#ข้อมูลของเหตุการณ์)) รายชื่อที่นับคือผู้ป่วยที่ไม่ถูกยกเลิก และผู้เสียชีวิตคือรายที่สภาพผู้ป่วยเป็นเสียชีวิต
- **เหตุการณ์ที่นับ** ตารางจำนวนเหตุการณ์ ผู้ป่วย และงาน นับเฉพาะเหตุการณ์ที่ตรวจสอบแล้วจริง คือมี `stage` เป็น `verified`, `responding` หรือ `closed` ตรงกับ [Dashboard สาธารณะ](#7-dashboard-สาธารณะ) เหตุการณ์ที่รอตรวจสอบแสดงเป็นจำนวนแยก
- **ข้อยกเว้นมีสองข้อ** ตัวชี้วัดการตรวจสอบข่าวนับเหตุการณ์ที่รอตรวจสอบและที่ตรวจสอบแล้วไม่จริงด้วย และร้อยละของเป้าเวลาของชุดโรคนับรายผู้ป่วยตามเวลาที่พบผู้ป่วยหรือวินิจฉัย ทั้งสองข้ออธิบายในหัวข้อของตนเอง
- หน้านี้แสดงถึงระดับหมู่บ้าน และไม่ซ่อนค่าต่ำกว่า 5 เพราะผู้เห็นเป็นบุคลากรของ สสอ. ทั้งหมด

### ช่วงเวลาและตัวกรอง

- ค่าตั้งต้นคือปีปฏิทินปัจจุบัน ซึ่งตรงกับปีของเลขที่เหตุการณ์และปีของประชากร
- ตัวเลือกสำเร็จรูปมีสี่แบบ: ปีนี้, ปีงบประมาณนี้ (1 ตุลาคม ถึง 30 กันยายน), 12 เดือนล่าสุด และกำหนดเอง "12 เดือนล่าสุด" คือสิบสองเดือนเต็มที่จบที่เดือนก่อนเดือนปัจจุบัน ตามช่วงประเมินของมาตรฐานทีม
- มีตัวกรองโรคหนึ่งตัว

- ตัวเลขในส่วนที่ 1 ถึง 4 และชื่อหน่วยงานในส่วนที่ 5 เป็นลิงก์ไปหน้า[รายการเหตุการณ์](#รายการเหตุการณ์) พร้อมตัวกรองของช่องนั้น
- หน้านี้แสดงเวลาของข้อมูล และใช้ได้ทั้งบนคอมพิวเตอร์และมือถือ

### อัตราป่วยและประชากร

- อัตราป่วยคือจำนวนผู้ป่วยคูณ 100,000 หารด้วยประชากร แสดงทศนิยมสองตำแหน่ง หน่วยต่อประชากรแสนคนเป็นหน่วยที่กรมควบคุมโรคใช้ ส่วนการแสดงอัตราระดับตำบลและหมู่บ้านเป็นการเลือกของระบบ ไม่พบเอกสารที่กำหนด
- อัตราป่วยเป็นของโรคหนึ่งโรค ส่วน "ตามโรค" จึงแสดงอัตราของทั้งอำเภอรายโรค และส่วน "ตามพื้นที่" แสดงอัตราเมื่อเลือกโรคในตัวกรอง
- ตัวหารคือประชากร ณ สิ้นปีของปีที่วันสุดท้ายของช่วงที่เลือกอยู่ ถ้ายังไม่มีประชากรของปีนั้น ใช้ปีล่าสุดก่อนหน้า หน้าจอเขียนว่า "ใช้ประชากร ณ สิ้นปี พ.ศ. …"
- ตัวอย่าง: ดูสรุปปี 2570 ในเดือนมีนาคม 2570 ไฟล์สิ้นปี 2570 ยังไม่ออก ระบบใช้ประชากรสิ้นปี 2569 สรุปของปีงบประมาณ 2570 ซึ่งจบ 30 กันยายน 2570 ใช้ประชากรของปี 2570 และใช้ของปี 2569 จนกว่าไฟล์ของปี 2570 จะถูกนำเข้า
- วิธีนี้ต่างจากของกองระบาดวิทยา ซึ่งใช้ประชากรกลางปี คือค่าเฉลี่ยของประชากรสิ้นปีสองปีติดกัน PO เลือกประชากรสิ้นปีเมื่อ 17 พฤศจิกายน 2569 เพราะอธิบายบนหน้าจอได้ตรง และตัวเลขทางการของอำเภอมาจาก D506 ไม่ใช่ระบบนี้ อัตราของระบบนี้จึงไม่เท่ากับอัตราในรายงานของกรม แม้ใช้จำนวนผู้ป่วยเท่ากัน
- ประชากรของตำบลและของอำเภอรวมแถวที่ไม่ระบุหมู่ ตาม [`schema.md` ข้อ 3](schema.md#3-ตารางแกนกลาง)
- การนำประชากรของปีใหม่เข้าอยู่ในหัวข้อ[ข้อมูลตั้งต้น](#ข้อมูลตั้งต้น)

### งานตามหน่วยบริการ

หนึ่งแถวต่อหนึ่งหน่วยงานที่มีงานในช่วงที่เลือก รวมแถวของ สสอ.

| คอลัมน์ | นับอะไร |
|---|---|
| งานที่ได้รับ | งานที่ไม่ถูกยกเลิก |
| บันทึกผลแล้ว | งานที่มีผลการทำงาน |
| บันทึกผลภายในกำหนดเสร็จ | งานที่เวลาที่ทำจริงของผลไม่เกินกำหนดเสร็จ แสดงจำนวนและร้อยละ |
| เกินกำหนด | งานที่เลยกำหนดเสร็จแล้วและยังไม่มีผลการทำงาน ณ เวลาที่เปิดหน้า |

ตัวหารของร้อยละคืองานที่บันทึกผลแล้วรวมกับงานที่เกินกำหนด งานที่ยังไม่ถึงกำหนดเสร็จและยังไม่มีผลไม่อยู่ในตัวหาร

### ตัวชี้วัดของมาตรฐานทีม

หน้าสรุปคำนวณตัวชี้วัดที่ 6, 8 และ 10 ของมาตรฐานทีมระดับอำเภอ พ.ศ. 2563 จากเหตุการณ์ที่รับแจ้งในช่วงที่เลือก แต่ละแถวแสดงตัวตั้ง ตัวหาร ร้อยละ และเกณฑ์ของมาตรฐาน เมื่อตัวหารเป็นศูนย์ แถวแสดงว่า "ไม่มีข้อมูล" ตัวเลือก "12 เดือนล่าสุด" ตรงกับช่วงที่มาตรฐานประเมิน

| ตัวชี้วัด | ตัวตั้ง | ตัวหาร | เกณฑ์ของมาตรฐาน |
|---|---|---|---|
| 6 ตรวจสอบข่าว | เหตุการณ์ที่ตรวจสอบข่าวแล้ว ทั้งจริงและไม่จริง | เหตุการณ์ที่รับแจ้งทั้งหมด ไม่นับที่ยกเลิก | ร้อยละ 80 |
| 6 แจ้งเตือนข่าว | เหตุการณ์ที่มีการแจ้งเตือนข่าว | เหตุการณ์ที่ตรวจสอบแล้วจริง | ร้อยละ 80 |
| 8 ความครบถ้วนของการสอบสวนโรค | เหตุการณ์ที่เข้าเกณฑ์และมีผลของงานสอบสวนโรค | เหตุการณ์ที่เข้าเกณฑ์ | ร้อยละ 60–79 ระดับพื้นฐาน และร้อยละ 80 ขึ้นไป ระดับดี |
| 10 สอบสวนทันเวลา | เหตุการณ์ที่เวลาที่ออกสอบสวนไม่เกินกำหนดเริ่มสอบสวน | เหตุการณ์ที่เข้าเกณฑ์และมีผลของงานสอบสวนโรค | เท่าตัวชี้วัดที่ 8 |
| 10 รายงานสอบสวนเบื้องต้นทันเวลา | เหตุการณ์ที่เวลาที่เขียนรายงานสอบสวนเบื้องต้นห่างจากเวลาที่ออกสอบสวนไม่เกิน 48 ชั่วโมง | เหตุการณ์ที่มีเวลาที่เขียนรายงานสอบสวนเบื้องต้น | เท่าตัวชี้วัดที่ 8 |

- **ข้อยกเว้นของกติกาการนับ** ตัวชี้วัดการตรวจสอบข่าวนับเหตุการณ์ที่รอตรวจสอบในตัวหาร และนับเหตุการณ์ที่ตรวจสอบแล้วไม่จริงทั้งในตัวตั้งและตัวหาร เพราะมาตรฐานวัดสัดส่วนของข่าวที่ได้รับการตรวจสอบ ไม่ว่าผลเป็นอย่างไร
- งานสอบสวนโรคคืองานของชนิดงานกลาง "สอบสวนโรค" ที่ไม่ถูกยกเลิก เมื่อเหตุการณ์มีหลายงาน ใช้เวลาที่ออกสอบสวนที่เร็วที่สุด และเวลาที่เขียนรายงานสอบสวนเบื้องต้นที่เร็วที่สุด
- **ข้อตีความสองข้อ** ซึ่งหน้าจอเขียนกำกับ PO รับเมื่อ 17 พฤศจิกายน 2569
  1. มาตรฐานนับตัวชี้วัดที่ 8 จากจำนวนรายงานสอบสวนโรค ระบบเก็บเฉพาะร่างล่าสุดที่ระบบช่วยเตรียม ([ข้อ 4](#ร่างรายงานสอบสวน)) ไม่เก็บรายงานฉบับที่ลงนาม จึงนับจากผลของงานสอบสวนโรค และแสดงจำนวนเหตุการณ์ที่มีเวลาที่เขียนรายงานสอบสวนเบื้องต้นไว้ข้างกัน
  2. มาตรฐานไม่ระบุจุดเริ่มนับ 48 ชั่วโมงของรายงานสอบสวนเบื้องต้น ระบบนับจากเวลาที่ออกสอบสวน เพราะมาตรฐานเขียนว่ารายงานนี้ "ควรจะจัดทำทันทีเมื่อกลับมาจากการสอบสวนในพื้นที่"
- หลักฐานที่มาตรฐานใช้ประเมินคือทะเบียนรับแจ้งข่าว บันทึกการแจ้งเตือน และรายงานสอบสวนโรค ตัวเลขในส่วนนี้ช่วยให้ทีมเห็นสถานะของตนเองก่อนการประเมิน
- **นอกขอบเขต** ส่วนของตัวชี้วัดที่ 6 เรื่องการตรวจจับการระบาดในระบบเฝ้าระวังและการแจ้งเตือนผลเดือนละ 1 ครั้ง เป็นงานของระบบรายงานผู้ป่วย ซึ่งระบบนี้ไม่ได้เชื่อม ตัวชี้วัดที่ 9 และ 11 วัดคุณภาพของตัวรายงาน ซึ่งระบบไม่เก็บฉบับที่ลงนาม ระบบไม่ทำรายงานสถานการณ์ถึงนายอำเภอ เพราะไม่มีแบบหรือเนื้อหาที่กำหนด

### ร้อยละที่ถึงเป้าของชุดโรค

ส่วนนี้นับผลการเทียบเป้า ([ข้อ 5](#5-ชุดโรค)) ของแต่ละชุดโรคแยกกัน และนับเป้าเวลากับเป้าผลแยกกัน

- **เป้าเวลาของชุด** ชุดโรคติดต่อนำโดยยุงลายมีสามค่า: แจ้งหน่วยบริการ ลงพื้นที่บ้านผู้ป่วย และพ่นสารเคมี นับรายผู้ป่วยตามวิธีของแนวทางการติดตามประเมินมาตรการควบคุมโรค 3-3-1 ของกองโรคติดต่อนำโดยแมลง
  - ผู้ป่วยที่นับคือผู้ป่วยในอำเภอที่ไม่ถูกยกเลิก ของเหตุการณ์ที่ตรวจสอบแล้วจริงและโรคใช้ชุดนั้น ผู้ป่วยนอกอำเภอไม่นับ เพราะระบบไม่เสนองานของชุดให้รายนั้น
  - ผู้ป่วยอยู่ในช่วงเวลาและสัปดาห์ระบาดตามเวลาที่พบผู้ป่วยหรือวินิจฉัย รายที่ไม่มีค่านี้ใช้เวลาที่ถูกเพิ่มในระบบ ข้อนี้เป็นข้อยกเว้นของกติกาการนับ เพราะผู้ป่วยรายหลังของเหตุการณ์เดิมต้องอยู่ในสัปดาห์ของตนเอง ไม่ใช่สัปดาห์ที่เหตุการณ์รับแจ้ง
  - ตัวตั้งคือผู้ป่วยที่ผลการเทียบเป็น "ถึงเป้า" ตัวหารคือผู้ป่วยทุกรายยกเว้นรายที่ "ยังไม่ครบกำหนด" ซึ่งแสดงเป็นจำนวนแยก รายที่ "ไม่ถึงเป้า" "ประเมินไม่ได้" หรือไม่มีงานของรอบที่เป้านั้นใช้ อยู่ในตัวหาร
  - ตัวอย่างจากแนวทางของกรม: สัปดาห์หนึ่งมีผู้ป่วย 10 ราย ติดตามได้ 5 ราย แจ้งหน่วยบริการทัน 1 ราย ได้ร้อยละ 10
  - ส่วนนี้แสดงยอดของช่วงที่เลือก และแยกรายสัปดาห์ระบาด
- **รอบการทำงาน** หนึ่งแถวต่อหนึ่งรอบของชุด นับรายงานตามกติกาการนับทั่วไป งานที่นับคืองานของรอบที่ไม่ถูกยกเลิก และไม่ใช่งานของผู้ป่วยที่ถูกยกเลิก งานของชุดที่ผู้ดูแลเพิ่มเองไม่อยู่ในรอบใดและไม่นับ แต่ละแถวแสดงร้อยละของการเทียบเป้าเวลา และรอบที่มีเป้าของผลแสดงร้อยละของการเทียบเป้าผล ตัวตั้งและตัวหารใช้กฎเดียวกับเป้าเวลาของชุด
- ชุดโรคที่ถูกปิดยังแสดงในส่วนนี้ เมื่อช่วงที่เลือกมีงานของชุดนั้น

### สัปดาห์ระบาด

- ระบบนับสัปดาห์ระบาดตามกฎของกองระบาดวิทยา กรมควบคุมโรค ที่เผยแพร่พร้อมปฏิทินปี 2569: สัปดาห์เริ่มวันอาทิตย์และสิ้นสุดวันเสาร์ สัปดาห์ที่ 1 เริ่มวันที่ 1 มกราคม สัปดาห์สุดท้ายสิ้นสุดวันที่ 31 ธันวาคม และไม่มีสัปดาห์ใดคร่อมสองปี ปี 2569 มี 53 สัปดาห์
- ระบบคำนวณเลขสัปดาห์จากวันที่ตามเวลาไทย ไม่เก็บตารางปฏิทิน และมีการทดสอบเทียบกับปฏิทินปี 2569 ของกองระบาดวิทยา
- สัปดาห์แรกและสัปดาห์สุดท้ายของปีมักมีไม่ครบ 7 วัน หน้าจอและไฟล์ส่งออกจึงแสดงช่วงวันที่ของทุกสัปดาห์
- สัปดาห์ระบาดใช้เฉพาะกับเป้าเวลาของชุดโรค ส่วนอื่นของหน้าสรุปแบ่งตามเดือน
- กองระบาดวิทยายังไม่เผยแพร่ปฏิทินปี 2570 และเปลี่ยนวิธีนับมาแล้วครั้งหนึ่งเมื่อปี 2568 กฎของปี 2570 จึงเป็น **Not Verified** ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))

- หัวไฟล์มีชื่อหน่วยงาน ชนิดของไฟล์ ช่วงวันที่ ตัวกรอง และเวลาที่ส่งออก
- ไฟล์ถูกสร้างแล้วดาวน์โหลดลงเครื่องของผู้ใช้ ระบบไม่เก็บสำเนา
- server ตรวจบทบาทก่อนส่งข้อมูลของไฟล์ทุกชนิด คำขอของผู้ดูหรือผู้ใช้หน่วยบริการที่อยู่นอกตารางนี้ถูกปฏิเสธ
- ทุกการส่งออกบันทึกใน audit log: ผู้ส่งออก ชนิดของไฟล์ ช่วงวันที่ ตัวกรอง จำนวนแถว และการรวมชื่อ ไม่มีข้อมูลผู้ป่วย
- ค่าที่ผู้ใช้กรอกไม่ถูกตีความเป็นสูตร ([ข้อ 8](#ความปลอดภัย))

**ชื่อและบ้านเลขที่** ไฟล์ข้อมูลเต็มและแผ่นรายผู้ป่วยของแบบติดตามไม่มีชื่อ-สกุล บ้านเลขที่ และที่อยู่ของผู้ป่วยนอกอำเภอ เว้นแต่ผู้ดูแลเลือก "รวมชื่อและบ้านเลขที่" ซึ่งค่าตั้งต้นคือไม่เลือก หน้าส่งออกเตือนว่าไฟล์ที่ดาวน์โหลดแล้วอยู่นอกการควบคุมของระบบ ไฟล์ที่รวมชื่อมีข้อความ "มีข้อมูลผู้ป่วย" ที่หัวไฟล์

**ไฟล์ข้อมูลเต็ม** ผู้ดูแลเลือกช่วงวันรับแจ้งและโรค ไฟล์รวมเหตุการณ์ที่ตรวจสอบแล้วไม่จริง เพราะแผ่นเหตุการณ์คือทะเบียนรับแจ้งข่าวที่มาตรฐานทีมใช้เป็นหลักฐาน และไม่รวมเหตุการณ์กับผู้ป่วยที่ยกเลิก ไฟล์ไม่มีไทม์ไลน์ รูปถ่าย และบันทึกความปลอดภัย

|---|---|---|
| เหตุการณ์ | เหตุการณ์ | เลขที่เหตุการณ์ สถานะ โรค แหล่งข่าวและหน่วยงานที่แจ้ง เวลาที่ได้รับแจ้ง ตำบล หมู่ที่ หมู่บ้าน สถานที่เพิ่มเติม รายละเอียด ประเภทเหตุการณ์ จำนวนผู้ป่วยและผู้เสียชีวิตที่กรอก จำนวนรายชื่อผู้ป่วย เวลาที่ตรวจสอบข่าว ตรวจสอบกับใคร หมายเหตุของการตรวจสอบ เวลาที่แจ้งเตือนข่าวครั้งแรก ผลประเมินเกณฑ์ กำหนดเริ่มสอบสวน เวลาที่ปิด และสรุปตอนปิด |

แผ่นงานแสดงผลที่ใช้งานอยู่ของแต่ละงาน ผลที่ถูกแก้ไม่อยู่ในไฟล์

**ไฟล์ตามแบบติดตามมาตรการ 3-3-1** เป็นไฟล์ของชุดโรคติดต่อนำโดยยุงลาย ทำตามแบบตัวอย่างสองแบบในแนวทางการติดตามประเมินมาตรการควบคุมโรค 3-3-1 ปีงบประมาณ 2568 ของกองโรคติดต่อนำโดยแมลง ผู้ใช้ไม่ต้องกรอกอะไรเพิ่ม ผู้ส่งออกเลือกช่วงวันที่ ซึ่งเทียบกับเวลาที่พบผู้ป่วยหรือวินิจฉัย ผู้ป่วยที่อยู่ในไฟล์และวิธีคิดร้อยละเป็นไปตามหัวข้อ[ร้อยละที่ถึงเป้าของชุดโรค](#ร้อยละที่ถึงเป้าของชุดโรค)

- **แผ่นรายผู้ป่วย** หนึ่งแถวต่อผู้ป่วย เรียงช่องตามแบบของกรม: วันและเวลาที่ได้รับการวินิจฉัย อายุ ที่อยู่ วันและเวลาที่รายงานให้หน่วยบริการทราบ วันและเวลาที่หน่วยบริการดำเนินการ วันและเวลาที่พ่นสารเคมี และปัจจัยล่าช้าของสองขั้นหลัง ซึ่งมาจากหมายเหตุของผลการทำงาน ([ข้อ 5](#ตารางติดตามตามแบบของกรม)) ระบบเพิ่มเลขที่เหตุการณ์ ลำดับของผู้ป่วย สัปดาห์ระบาด หน่วยบริการ และผลการเทียบเป้าเวลาสามค่า ที่อยู่คือหมู่บ้านและตำบล ชื่อผู้ป่วยและบ้านเลขที่มีเมื่อเลือกรวมชื่อ แบบของกรมมีช่อง "ปัจจัยสนับสนุน" และปัจจัยล่าช้าของขั้นรายงาน ซึ่งระบบไม่เก็บ
- **แผ่นสรุปร้อยละ** หนึ่งแถวต่อสัปดาห์ระบาด และแถวรวมของช่วงที่เลือก คอลัมน์คือสัปดาห์ ช่วงวันที่ จำนวนผู้ป่วย และของเป้าเวลาแต่ละค่า: จำนวนที่ยังไม่ครบกำหนด จำนวนที่ถึงเป้า และร้อยละ หัวคอลัมน์ของร้อยละใช้ถ้อยคำของแบบของกรม แบบของกรมมีเฉพาะร้อยละ ระบบเพิ่มจำนวนไว้ข้างกัน เพราะแนวทางเรียกแบบนี้ว่าตัวอย่างที่ปรับได้
- แนวทางนี้เป็นของปีงบประมาณ 2568 ไม่พบตัวชี้วัดนี้ในปีงบประมาณ 2569 และ 2570 และยังไม่ทราบว่ามีหน่วยงานใดขอข้อมูลนี้จาก สสอ. หรือไม่ เรื่องหลังเป็น **Not Verified** ใน[ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน)

## 7. Dashboard สาธารณะ

บุคคลทั่วไปเปิดดูได้โดยไม่ต้องล็อกอิน Dashboard สาธารณะของระบบเก่าแสดงจำนวนเหตุการณ์ถึงระดับหมู่บ้าน ไม่ซ่อนค่าน้อย และนับเหตุการณ์ที่ยังไม่ได้ตรวจสอบกับที่ตรวจสอบแล้วไม่จริงด้วย v2 เปลี่ยนทั้งสามเรื่องตาม [ADR-0006](adr/0006-patient-data-and-public-disclosure.md) ข้อเท็จจริงเรื่องการซ่อนค่าน้อย กฎหมาย แดชบอร์ดของกรมควบคุมโรค และข้อจำกัดของ cache ที่หัวข้อนี้ใช้อยู่ใน[ผลการค้นเรื่อง Dashboard สาธารณะ](research/public-dashboard-facts.md)

### ผู้ดูและจุดประสงค์

- ผู้ดูคือประชาชนในอำเภอ ผู้นำชุมชน อสม. องค์กรปกครองส่วนท้องถิ่น และโรงเรียน ซึ่งต้องการรู้ว่าตำบลของตนมีโรคใดถูกแจ้งเข้ามา เพื่อระวังตัว
- หน้านี้ไม่ใช่สถิติทางการของอำเภอ ตัวเลขทางการมาจากระบบรายงานของกรมควบคุมโรค หน้านี้จึงไม่ได้ออกแบบให้ใช้แทนรายงานถึงนายอำเภอหรือ สสจ. บุคลากรของ สสอ. ใช้[สรุปภาพรวม](#6-สรุปภาพรวมและการส่งออก)

### ที่อยู่ของหน้า

- Dashboard สาธารณะมีที่อยู่ของตัวเอง ซึ่ง สสอ. ส่งต่อหรือทำ QR ได้ หน้านี้ไม่ใช่หน้าแรกของระบบ ที่อยู่หลักของระบบเปิดหน้าล็อกอิน ([ข้อ 2](#การเข้าสู่ระบบ))
- หน้านี้มีปุ่ม "เข้าสู่ระบบสำหรับเจ้าหน้าที่"
- ผู้ใช้ทุกบทบาทมีลิงก์ไปหน้านี้ในเมนู และเห็นตัวเลขชุดเดียวกับบุคคลทั่วไป ซึ่งซ่อนค่าแล้วเหมือนกัน ผู้ดูแลจึงตรวจได้ว่าคนนอกเห็นอะไร
- หน้านี้ขอให้เครื่องมือค้นหาไม่เก็บเข้าดัชนี ผู้ดูเข้าถึงจากลิงก์ที่ สสอ. ส่งเอง
- ตัวอย่างลิงก์ที่ LINE หรือ Facebook แสดงมีเฉพาะชื่อหน่วยงานกับคำว่า "Dashboard สาธารณะ" ไม่มีตัวเลขและชื่อโรค

### กติกาการนับของ Dashboard สาธารณะ

- ใช้[กติกาการนับ](#กติกาการนับ)ของสรุปภาพรวมทุกข้อ: นับตามวันรับแจ้ง ใช้ตำบลของหมู่บ้านของเหตุการณ์ จำนวนผู้ป่วยของเหตุการณ์หนึ่งคือค่าที่มากกว่าระหว่างจำนวนที่ผู้ดูแลกรอกกับจำนวนรายชื่อ และไม่นับเหตุการณ์กับผู้ป่วยที่ยกเลิก
- นับเฉพาะเหตุการณ์ที่ตรวจสอบแล้วว่าจริง คือมี `stage` เป็น `verified`, `responding` หรือ `closed`
- ตัวอย่าง: เหตุการณ์ที่รับแจ้ง 30 ธันวาคม 2569 ในตำบล ก มีผู้ป่วย 30 ราย หนึ่งรายบ้านอยู่ตำบล ข ทั้ง 30 รายนับเป็นของเดือนธันวาคม 2569 ตำบล ก
- ตัวเลขของหน้านี้กับของสรุปภาพรวมใช้กติกาเดียวกัน แต่ต่างกันได้ระหว่างรอบเผยแพร่ เพราะสรุปภาพรวมคำนวณทุกครั้งที่เปิด

### ตัวเลขที่แสดง

- แสดงสองตัวเลข: จำนวนเหตุการณ์ และจำนวนผู้ป่วย ของแต่ละโรค ตำบล และเดือน ไม่ลงถึงระดับหมู่บ้าน
- ไม่แสดงผู้เสียชีวิต อัตราป่วย ประชากร ตัวชี้วัดของมาตรฐานทีม และร้อยละใด ๆ ผู้เสียชีวิตมีจำนวนน้อยจนคนในตำบลรู้ว่าหมายถึงใคร ส่วนอัตราและร้อยละใช้คำนวณย้อนหาจำนวนที่ซ่อนได้
- ไม่มีรายละเอียดรายเหตุการณ์ รายผู้ป่วย ชื่อ สถานที่ หรือวันเริ่มป่วยรายคน

### โรคที่ไม่แสดงชื่อ

โรคที่ไม่แสดงชื่อไม่มีแถวของตัวเอง และนับรวมในแถว "โรคอื่น ๆ" พร้อมกับโรค "อื่น ๆ" ของรายการโรค

- **โรคติดต่ออันตราย** ไม่แสดงชื่อเสมอ และผู้ดูแลเปิดไม่ได้ เหตุการณ์สงสัยโรคติดต่ออันตรายหนึ่งเรื่องจึงไม่ขึ้นหน้าสาธารณะพร้อมชื่อโรคและชื่อตำบลก่อนที่กรมควบคุมโรคหรือจังหวัดจะประกาศ มาตรา 9 ของพระราชบัญญัติโรคติดต่อ พ.ศ. 2558 ให้อธิบดีกรมควบคุมโรคเป็นผู้ประกาศชื่อ อาการสำคัญ และสถานที่ที่มีโรคระบาด
- **โรคอื่น** แต่ละโรคมีค่า "แสดงชื่อใน Dashboard สาธารณะ" ที่ผู้ดูแลแก้ได้ในหน้าตั้งค่า รายการโรคตั้งต้นมีค่าเป็นแสดง ยกเว้นกลุ่มโรคที่มีการตีตรา: โรคติดต่อทางเพศสัมพันธ์ เอชไอวี/เอดส์ วัณโรค โรคเรื้อน และไวรัสตับอักเสบ PO ตรวจรายชื่อนี้พร้อมรายการโรคตั้งต้น ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน)) โรคที่ผู้ดูแลเพิ่มเองมีค่าตั้งต้นเป็นไม่แสดง
- ระบบรวมจำนวนจริงของทุกโรคในแถว "โรคอื่น ๆ" ก่อน แล้วจึงซ่อนค่าน้อย
- แถว "โรคอื่น ๆ" ยังบอกว่ามีเหตุการณ์ในตำบลและเดือนนั้น โดยไม่บอกว่าเป็นโรคใด

### ช่วงเวลา

- แสดงทีละปีปฏิทิน พ.ศ. แบ่งเป็นเดือน ค่าตั้งต้นคือปีปัจจุบัน และเลือกปีก่อนหน้าที่มีเหตุการณ์ได้
- ไม่มีช่วงกำหนดเอง ปีงบประมาณ และ 12 เดือนล่าสุด เพราะผู้ที่เลือกช่วงได้เองเทียบสองช่วงที่ต่างกันหนึ่งวัน แล้วหักลบหาเหตุการณ์รายวันได้

### การซ่อนค่าน้อยและยอดรวม

- **ตารางเดียว** ตัวเลขรวมสาธารณะคือตารางเดียว หนึ่งช่องคือหนึ่งโรค หนึ่งตำบล และหนึ่งเดือน แต่ละช่องมีจำนวนเหตุการณ์และจำนวนผู้ป่วย
- **การซ่อน** server ซ่อนค่าของแต่ละตัวเลขก่อนเก็บและก่อนส่ง: จำนวน 0 เป็น 0 จำนวน 1–4 เป็น "<5" และจำนวนตั้งแต่ 5 เป็นจำนวนจริง สองตัวเลขของช่องเดียวกันซ่อนแยกกัน
- **server ไม่ส่งตัวเลขอื่น** คำตอบของ Dashboard สาธารณะไม่มียอดรวมของโรค ตำบล เดือน หรือปี ที่คำนวณจากจำนวนจริง
- **ยอดรวมคำนวณจากช่องที่แสดงแล้ว** ทุกยอดรวมบนหน้าคำนวณในเบราว์เซอร์จากตารางที่ได้รับ ยอดรวมที่ไม่มีช่องซ่อนอยู่คือผลบวก ยอดรวมที่มีช่องซ่อนอยู่แสดงเป็นช่วง ค่าต่ำสุดนับช่องที่ซ่อนช่องละ 1 และค่าสูงสุดนับช่องละ 4 ช่วง 1–4 เขียนว่า "<5"
- ตัวอย่าง: ไข้เลือดออก พฤศจิกายน 2569 ตำบล ก มีผู้ป่วย 6 ราย ตำบล ข "<5" ตำบล ค "<5" และตำบลอื่น 0 ยอดของทั้งอำเภอแสดงเป็น "8–14" ถ้าหน้าแสดงยอดจริงว่า 8 ผู้อ่านรู้ว่าตำบล ข และตำบล ค มีแห่งละ 1 ราย
- วิธีนี้ทำให้คำนวณย้อนหาช่องที่ซ่อนไม่ได้โดยโครงสร้าง แม้ผู้อ่านรู้กฎครบ ซึ่งเป็นกรณีของระบบนี้เพราะ repository เป็นสาธารณะ การซ่อน 1–4 คู่กับยอดรวมจริงเป็นแบบที่แหล่งข้อมูลระบุว่าคำนวณย้อนได้ ([ผลการค้น ข้อ 2.3](research/public-dashboard-facts.md))
- ผลที่ต้องรับ: ยอดรวมทั้งปีของโรคที่มีช่องซ่อนอยู่มากเป็นช่วงกว้าง เช่น "15–48"
- **ค่า 0 แสดงเป็น 0** ผู้ดูจึงแยกตำบลที่ไม่มีเหตุการณ์ออกจากตำบลที่มีได้ ผู้ที่เปิดหน้าสองรอบเห็นช่องเปลี่ยนจาก 0 เป็น "<5" และรู้ว่ามีเหตุการณ์ใหม่ในตำบลนั้น ซึ่งเป็นจุดประสงค์ของหน้านี้ และรอบเผยแพร่รายสัปดาห์ลดความละเอียดของเวลาให้
- ลำดับของแถวและความยาวของแถบสีคำนวณจากค่าที่แสดงเท่านั้น แถบของช่องที่ซ่อนยาวเท่ากันทุกช่อง
- เกณฑ์ 5 เป็นการเลือกของระบบตาม ADR-0006 ไม่พบมาตรฐานของไทยที่กำหนดเกณฑ์เป็นตัวเลข หน่วยงานของสหราชอาณาจักรแนะนำเกณฑ์ขั้นต่ำ 5 สำหรับเครื่องมือออนไลน์ และหน่วยงานของสหรัฐใช้ 10

### รอบเผยแพร่

- ระบบคำนวณตัวเลขรวมสาธารณะใหม่ทั้งชุดทุกเช้าวันจันทร์ตามเวลาไทย จากข้อมูล ณ เวลานั้น ของทุกปีที่มีเหตุการณ์ แล้วเก็บผลที่ซ่อนค่าแล้วไว้ในตาราง `public_snapshot` ([`schema.md` ข้อ 3](schema.md#3-ตารางแกนกลาง))
- คำขอของ Dashboard สาธารณะอ่านเฉพาะตารางนี้ ไม่อ่านตารางเหตุการณ์และผู้ป่วย
- หน้าแสดง "ข้อมูล ณ วันที่ … ปรับปรุงทุกวันจันทร์"
- การแก้ย้อนหลัง เช่น การยกเลิกเหตุการณ์ การแก้โรค หรือการแก้ผลการตรวจสอบ ปรากฏในรอบถัดไป
- ไม่มีปุ่มเผยแพร่ทันที การคำนวณนอกรอบมีกรณีเดียว คือเมื่อผู้ดูแลเปิด Dashboard สาธารณะขณะที่ยังไม่มีตัวเลขรวมสาธารณะ
- เมื่อผู้ดูแลเปลี่ยนโรคหนึ่งเป็นไม่แสดงชื่อ แถวของโรคนั้นหายจากหน้าทันที และจำนวนของโรคนั้นเข้าไปอยู่ในแถว "โรคอื่น ๆ" ตั้งแต่รอบถัดไป การเปลี่ยนโรคเป็นแสดงชื่อมีผลในรอบถัดไป
- รอบคำนวณทำงานทุกสัปดาห์แม้ Dashboard สาธารณะปิดอยู่
- หน้าตั้งค่าแสดงเวลาของรอบล่าสุด และเตือนเมื่อรอบล่าสุดเก่ากว่า 8 วัน
- เหตุผล: ตัวเลขที่เปลี่ยนทันทีทำให้ผู้ที่เห็นเพื่อนบ้านเข้าโรงพยาบาลวันอังคาร แล้วเห็นช่องของตำบลเปลี่ยนในวันพุธ เดาการวินิจฉัยได้ แนวทางของสหราชอาณาจักรเตือนเรื่องตัวเลขที่ออกรายวัน และยอมรับรอบรายสัปดาห์สำหรับจำนวนผู้ติดเชื้อโควิด-19 รายพื้นที่ย่อย ([ผลการค้น ข้อ 2.5](research/public-dashboard-facts.md))
- cache ของ Apps Script เก็บได้นานสุด 6 ชั่วโมงและอาจถูกลบก่อนกำหนด ระบบใช้ cache เพื่อลดการอ่านตาราง ไม่ได้ใช้กำหนดรอบเผยแพร่

### การจัดหน้า

- ผู้ดูเลือกปี และเลือก "ทั้งอำเภอ" หรือตำบลหนึ่งตำบล ค่าตั้งต้นคือ "ทั้งอำเภอ"
- ตารางมีหนึ่งแถวต่อโรคที่มีเหตุการณ์ในปีและพื้นที่ที่เลือก หนึ่งคอลัมน์ต่อเดือน และคอลัมน์รวมทั้งปี
- มีปุ่มสลับระหว่างจำนวนผู้ป่วยกับจำนวนเหตุการณ์ ค่าตั้งต้นคือจำนวนผู้ป่วย
- ทุกมุมมองคำนวณในเบราว์เซอร์จากตารางเดียว การเลือกปี ตำบล หรือตัวเลขจึงไม่ทำให้ server ส่งข้อมูลเพิ่ม
- เป็นตารางพร้อมแถบสีในช่อง แบบเดียวกับสรุปภาพรวม ออกแบบให้อ่านบนมือถือก่อน และเลื่อนตารางไปทางขวาได้
- รุ่นแรกไม่มีแผนที่ กราฟแยก ปุ่มดาวน์โหลดไฟล์ และปุ่มบันทึกรูปภาพ

### ข้อความประจำหน้า

ข้อความประจำหน้าเป็นข้อความคงที่ ผู้ดูแลพิมพ์ข้อความเองไม่ได้ และไม่มีช่องเบอร์ติดต่อ

- ชื่อและโลโก้หน่วยงาน
- "ข้อมูล ณ วันที่ … ปรับปรุงทุกวันจันทร์" และ "นับตามวันรับแจ้ง"
- คำอธิบายว่า "<5" หมายถึงจำนวน 1 ถึง 4 ที่ไม่แสดงเพื่อคุ้มครองผู้ป่วย และยอดรวมที่เป็นช่วงเกิดจากช่องที่ไม่แสดง
- "ตัวเลขจากทะเบียนรับแจ้งข่าวของ สสอ. ไม่ใช่สถิติทางการ"
- "ตัวเลขนี้นับเหตุการณ์ที่ สสอ. รับแจ้งและตรวจสอบแล้ว จึงไม่เท่ากับจำนวนผู้ป่วยในระบบรายงานของกรมควบคุมโรค" เพราะแดชบอร์ดของกรมเปิดดูได้ถึงระดับอำเภอ และผู้อ่านเทียบตัวเลขสองแหล่งได้
- หน้านี้ใช้คำว่า "เหตุการณ์ที่ได้รับแจ้ง" และ "ผู้ป่วย" ไม่ใช้คำว่า "โรคระบาด" "การระบาด" และ "สถานการณ์โรค" คำว่า "โรคระบาด" มีความหมายตามมาตรา 4 และมาตรา 9 ของพระราชบัญญัติโรคติดต่อ พ.ศ. 2558

### การเปิดและปิด

- หน้าตั้งค่ามีค่า "เปิด Dashboard สาธารณะ" หนึ่งค่า ผู้ดูแลเปิดและปิดได้เองโดยไม่ต้องรอการ deploy เช่น เมื่อพบว่าตัวเลขของตำบลหนึ่งทำให้คนในพื้นที่เดาตัวผู้ป่วยได้
- เมื่อปิด บุคคลทั่วไปเห็นข้อความว่าหน้านี้ยังไม่เปิดให้ดู server ไม่ส่งตัวเลข และหน้าล็อกอินไม่มีลิงก์มาหน้านี้ ผู้ใช้ที่ล็อกอินแล้วเห็นข้อความเดียวกัน
- การเปิดและการปิดบันทึกใน audit log
- คำสั่ง[เริ่มใช้ข้อมูลจริง](#การเริ่มใช้ข้อมูลจริง)ปิด Dashboard สาธารณะของชุดใช้งานจริง และหน้านี้ปิดอยู่จนกว่า PO ยืนยันข้อกฎหมายในหัวข้อถัดไป ([roadmap ช่วงที่ 7](roadmap.md))

### ความเสี่ยงที่ยอมรับ และข้อที่ยังไม่ยืนยัน

- **ตำบลขนาดเล็ก** หน้านี้แสดงครบทุกตำบล ตามไฟล์สถิติของกรมการปกครองของเดือนธันวาคม 2568 อำเภอสองมีสองตำบลที่ประชากรต่ำกว่า 5,000 คน คือแดนชุมพล 2,411 คน และทุ่งน้าว 3,200 คน ซึ่งเล็กกว่าพื้นที่ขั้นต่ำ 5,000 คนที่หน่วยงานสถิติของสหราชอาณาจักรยอมรับสำหรับจำนวนผู้ติดเชื้อรายสัปดาห์ ช่อง "<5" ของสองตำบลนี้ทำให้เพื่อนบ้านเดาตัวผู้ป่วยได้ง่ายกว่าตำบลอื่น PO ยอมรับความเสี่ยงนี้เมื่อ 17 พฤศจิกายน 2026 เพราะการควบคุมโรคในหมู่บ้าน เช่น การพ่นหมอกควันรอบบ้านผู้ป่วย เปิดเผยมากกว่าตัวเลขนี้ โรคที่มีการตีตราไม่แสดงชื่อ และผู้ดูแลปิดหน้าได้ ทางเลือกที่ไม่เลือกคือรวมสองตำบลนี้กับตำบลข้างเคียง
- **Not Verified: ข้อกฎหมาย** มาตรา 10 ของพระราชบัญญัติโรคติดต่อ พ.ศ. 2558 ให้เก็บข้อมูลจากการเฝ้าระวังที่พาดพิงถึงตัวบุคคล "ทั้งที่ระบุตัวได้หรือไม่สามารถระบุตัวได้" เป็นความลับ ไม่พบบทบัญญัติที่ห้ามหรืออนุญาตให้ สสอ. เผยแพร่จำนวนรวมรายตำบล พิสูจน์ด้วยการที่ PO ถามนิติกรหรือผู้รับผิดชอบของสำนักงานสาธารณสุขจังหวัด ก่อนเปิด Dashboard สาธารณะของชุดใช้งานจริง ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))
- แดชบอร์ดของกรมควบคุมโรคที่เปิดดูได้โดยไม่ล็อกอินแสดงจำนวนผู้ป่วยรายอำเภอโดยไม่ซ่อนค่าน้อย Dashboard สาธารณะของระบบนี้จึงเข้มกว่า ข้อเท็จจริงนี้บอกว่ากรมแสดงอะไร ไม่ได้ยืนยันว่าการแสดงเช่นนั้นปลอดภัย

### แถบข้อมูลสมมติ

ระหว่างที่ระบบใช้ข้อมูลสมมติ Dashboard สาธารณะมีแถบ "ข้อมูลสมมติ ไม่ใช่สถานการณ์จริง" ค้างอยู่บนหน้า เพราะระบบที่ deploy ในช่วงพัฒนาเปิดดูได้จากอินเทอร์เน็ต แถบนี้เป็นไปตาม[ข้อ 8](#8-ข้อกำหนดทั่วไป)

### สิ่งที่ไม่ทำ

ระบบเก่ามีรายการลิงก์ประกาศ แนวทาง และคู่มือที่บุคคลทั่วไปเปิดได้ และบันทึกเวลาของการเปิดหน้าทุกครั้งโดยไม่มีหน้าจอใดแสดงค่านั้น PO ตัดสินเมื่อ 17 พฤศจิกายน 2026 ว่า v2 ไม่ทำทั้งสองอย่าง และไม่ใส่เครื่องมือนับผู้เข้าชมของภายนอก การเผยแพร่ข่าวสารเป็นงานของช่องทางอื่นของ สสอ. และไม่มีหน้าจอหรือมาตรฐานใดใช้จำนวนผู้เข้าชม

## 8. ข้อกำหนดทั่วไป

**ระบบต้องช่วยงาน ไม่เพิ่มภาระ** ช่องข้อมูลและขั้นตอนมีได้เมื่อมาตรฐานของงานกำหนด หรือเมื่อหน้าจอหรือสรุปของระบบใช้ค่านั้น ช่องบังคับมีเฉพาะที่ขั้นถัดไปต้องใช้ และค่าที่ระบบรู้อยู่แล้วผู้ใช้ไม่ต้องกรอกซ้ำ

- หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดง UUID หรือรหัสสถานะภาษาอังกฤษ
- หน้าจอของหน่วยบริการใช้งานได้บนมือถือ และแต่ละงานมีลิงก์ของตัวเอง
- การบันทึกทุกครั้งกันการส่งซ้ำ กดปุ่มซ้ำหรือสัญญาณหลุดแล้วส่งใหม่ต้องไม่สร้างรายการซ้ำ
- หลังบันทึกสำเร็จ หน้าจอแสดงข้อมูลล่าสุดทันที ผู้ใช้ไม่ต้องโหลดใหม่เอง
- หน้าจอหลักแต่ละหน้าโหลดข้อมูลด้วยคำขอเดียว เป้าหมายคือพร้อมใช้ภายใน 3 วินาทีบนมือถือ ค่านี้เป็นเป้าที่ต้องวัดจริงตั้งแต่ช่วงที่ 0 ของ roadmap ยังไม่ใช่ผลที่พิสูจน์แล้ว
- ปุ่มที่ผู้ใช้ไม่มีสิทธิ์จะไม่แสดง
- ชื่อปุ่มบอกทั้งการกระทำและสิ่งที่ถูกกระทำ เช่น "ปิดเหตุการณ์" และการกระทำที่ต่างกันใช้คำต่างกัน
- การกระทำที่มีผลมาก เช่น ปิดเหตุการณ์ หรือยกเลิก มีหน้าต่างยืนยันแยกที่บอกผลที่จะเกิด ปุ่มยืนยันไม่ใช้ปุ่มเดียวกับปุ่มบันทึก
- คำที่แสดงบนหน้าจอใช้ตาม [`GLOSSARY.md`](../GLOSSARY.md)
- ข้อมูลไม่ถูกลบ ข้อยกเว้นมีสี่อย่าง: การล้างข้อมูลสมมติครั้งเดียวเมื่อ[เริ่มใช้ข้อมูลจริง](#การเริ่มใช้ข้อมูลจริง) การเอาชุดสำรองที่เกินจำนวนออก การลบเมื่อครบ[ระยะเวลาเก็บข้อมูล](#ระยะเวลาเก็บข้อมูล)ซึ่งต้องอนุมัติแยก และการร่างรายงานสอบสวนใหม่ ซึ่งเขียนทับข้อความที่ AI ร่างครั้งก่อน ([ข้อ 4](#ร่างรายงานสอบสวน))
- ระบบสำรองไฟล์ฐานข้อมูลเองทุกสัปดาห์ เก็บ 8 ชุด และบอกผู้ดูแลเมื่อการสำรองไม่สำเร็จ ([สำรองข้อมูล](#สำรองข้อมูล))
- Log ของระบบไม่มีชื่อผู้ป่วย ข้อความบรรยายเหตุการณ์ ข้อความที่ส่งให้ AI ข้อความที่ AI ตอบ หรือ token
- ระหว่างที่ระบบใช้ข้อมูลสมมติ ทุกหน้ารวมถึง [Dashboard สาธารณะ](#7-dashboard-สาธารณะ) มีแถบ "ข้อมูลสมมติ ไม่ใช่สถานการณ์จริง" ค้างอยู่บนหน้า แถบนี้ถูกเอาออกจากชุดใช้งานจริงเมื่อ PO อนุมัติการเริ่มใช้ข้อมูลจริง และอยู่ในชุดทดสอบเสมอ

### ความปลอดภัย

- server ตรวจค่าที่รับเข้าทุกช่อง ทั้งชนิด ความยาว และค่าที่อนุญาต โดยไม่พึ่งการตรวจของหน้าเว็บ
- ค่าที่ผู้ใช้กรอกไม่ถูกตีความเป็นสูตร ทั้งในไฟล์ฐานข้อมูลและไฟล์ที่ส่งออก
- หน้าเว็บโหลดสคริปต์จากที่อยู่ของตัวเองและจากบริการเข้าสู่ระบบของ Google เท่านั้น และไม่ยอมให้เว็บอื่นฝังหน้าไว้ในกรอบ
- เมื่อผู้ดูแลเปิดหน้าตั้งค่า ระบบตรวจการแชร์ของโฟลเดอร์ส่วนตัวของระบบ ไฟล์ฐานข้อมูล โฟลเดอร์รูปถ่าย และโฟลเดอร์ของชุดสำรอง การแชร์ที่ถูกต้องมีอย่างเดียว คือ[บัญชีสำรอง](#บัญชีสำรอง)ที่ได้สิทธิ์อ่าน ระบบเตือนเมื่อพบบัญชีอื่น พบการแชร์ด้วยลิงก์ หรือพบว่าบัญชีสำรองแก้ไขได้
- เมื่อเกิดข้อผิดพลาด ผู้ใช้เห็นข้อความภาษาไทยพร้อมรหัสอ้างอิง ซึ่งใช้ค้นใน log ได้

### สำรองข้อมูล

ข้อเท็จจริงของ Google ที่หัวข้อนี้และสามหัวข้อถัดไปใช้อยู่ใน[ผลการค้นเรื่องการสำรองและการแยกชุด](research/backup-environment-facts.md)

- ระบบคัดลอกไฟล์ฐานข้อมูลทั้งไฟล์เป็นชุดสำรองทุกคืนวันอาทิตย์ตามเวลาไทย ก่อนรอบเผยแพร่ของ Dashboard สาธารณะในเช้าวันจันทร์ Apps Script กำหนดเวลาของงานได้ถึงระดับชั่วโมง นาทีที่ทำงานจึงไม่คงที่
- ชุดสำรองอยู่ในโฟลเดอร์ย่อยของโฟลเดอร์ส่วนตัวของระบบ ชื่อไฟล์มีวันที่และเวลาของการสำรอง
- สำรองเฉพาะไฟล์ฐานข้อมูล รูปถ่ายและโลโก้ไม่ถูกคัดลอกซ้ำ เพราะระบบไม่ลบไฟล์รูป และพื้นที่ของบัญชีมีจำกัด
- การคัดลอกทำภายใต้ lock เดียวกับการเขียน หลังคัดลอก ระบบเปิดสำเนาแล้วเทียบชื่อแท็บและจำนวนแถวของทุกแท็บกับต้นฉบับ การสำรองสำเร็จเมื่อตรงกันทุกแท็บ แล้วระบบบันทึกเวลาที่สำเร็จ
- ระบบเก็บชุดสำรอง 8 ชุดล่าสุด ชุดที่เกินถูกย้ายลงถังขยะของ Google Drive เพราะ Apps Script ลบไฟล์ถาวรเองไม่ได้ Google ล้างถังขยะเมื่อครบ 30 วัน ระหว่างนั้นไฟล์ยังอยู่ ยังนับพื้นที่ และผู้ที่เข้าถึงโฟลเดอร์ยังเปิดได้ สำเนาที่มีอยู่จริงจึงมีได้ถึง 13 ชุด การหมุนชุดสำรองนี้ระบบทำเองโดยไม่ขออนุมัติรายครั้ง ([ADR-0008](adr/0008-delivery-process-and-gates.md))
- ระบบสำรองเพิ่มหนึ่งชุดก่อน migration ของโครงสร้าง และก่อนคำสั่งเริ่มใช้ข้อมูลจริง ถ้าการสำรองนี้ไม่สำเร็จ การกระทำนั้นไม่เริ่ม ชุดสำรองชนิดนี้นับรวมใน 8 ชุด
- หน้าตั้งค่าแสดงเวลาของชุดสำรองล่าสุดที่สำเร็จ และพื้นที่ที่ใช้ของบัญชีเจ้าของเป็นร้อยละ ระบบอ่านค่าพื้นที่ตอนสำรองและเมื่อผู้ดูแลเปิดหน้าตั้งค่า แล้วเก็บค่าไว้ให้หน้า "งานวันนี้" ใช้
- ผู้ดูแลเห็นแถบเตือนบนหน้า ["งานวันนี้"](#ผู้ดูแล-งานวันนี้) เมื่อชุดสำรองล่าสุดที่สำเร็จเก่ากว่า 8 วัน หรือพื้นที่ใช้เกินร้อยละ 80 ความล้มเหลวของงานตามเวลาปรากฏที่อื่นเพียงในอีเมลสรุปของ Google ถึงบัญชีเจ้าของ และเมื่อพื้นที่ของบัญชีเต็ม ทั้งระบบบันทึกไม่ได้ และ Gmail ของบัญชีนั้นรับส่งไม่ได้
- หน้าเว็บไม่มีปุ่มสำรองทันทีและไม่มีปุ่มกู้คืน
- **ความเสี่ยงที่ PO ยอมรับเมื่อ 17 พฤศจิกายน 2026** การกู้คืนเสียข้อมูลที่บันทึกหลังชุดสำรองล่าสุด ซึ่งมากได้ถึง 7 วัน ประวัติเวอร์ชันของ Google Sheets เป็นทางเสริมสำหรับความผิดพลาดที่พบเร็ว Google ไม่รับรองระยะเวลาเก็บของประวัตินั้น

### บัญชีสำรอง

- ชุดสำรอง ประวัติเวอร์ชัน และถังขยะอยู่ในบัญชีเจ้าของทั้งหมด จึงไม่ช่วยเมื่อเข้าบัญชีเจ้าของไม่ได้ หรือบัญชีนั้นถูกลบ บัญชีเจ้าของสร้างไฟล์ที่เป็นของบัญชีอื่นไม่ได้ สำเนาที่รอดจากการเสียบัญชีเจ้าของจึงต้องให้อีกบัญชีหนึ่งเป็นฝ่ายคัดลอก
- บัญชีสำรองคือบัญชี Google ของบุคลากร สสอ. อีกคนหนึ่งที่มีสิทธิ์เห็นข้อมูลทั้งหมดอยู่แล้ว เช่น ผู้ดูแลคนที่สอง หรือสาธารณสุขอำเภอ ไม่ใช่บัญชีอื่นของเจ้าของบัญชีเดิม เพราะต้องรอดจากกรณีที่เจ้าของบัญชีย้ายงาน
- บัญชีสำรองได้สิทธิ์อ่านโฟลเดอร์ส่วนตัวของระบบ ซึ่งรวมไฟล์ฐานข้อมูล รูปถ่าย และชุดสำรอง เมื่อเจ้าของเข้าบัญชีไม่ได้ ผู้ถือบัญชีสำรองยังเปิดและคัดลอกไฟล์เหล่านี้ได้
- สคริปต์คัดลอกหนึ่งตัวทำงานในบัญชีสำรองทุกสัปดาห์ คัดลอกชุดสำรองล่าสุดเป็นไฟล์ของบัญชีสำรอง และเก็บ 8 ชุดล่าสุดด้วยวิธีเดียวกับระบบ โค้ดของสคริปต์อยู่ใน repository แยกจาก API และไม่มีที่อยู่ให้เรียกจากภายนอก
- อีเมลของบัญชีสำรองเก็บใน Script Properties การตรวจการแชร์ใช้ค่านี้แยกบัญชีสำรองออกจากการแชร์ที่ไม่ตั้งใจ ([ความปลอดภัย](#ความปลอดภัย))
- **ความเสี่ยงที่ PO ยอมรับเมื่อ 17 พฤศจิกายน 2026** เมื่อบัญชีเจ้าของถูกลบ รูปถ่ายหาย ฐานข้อมูลรอดจากสำเนาของบัญชีสำรอง
- การนำระบบกลับมาใช้จากสำเนาของบัญชีสำรองคือการย้ายระบบไปบัญชีอื่น ([`operations.md` ข้อ 11](operations.md#11-ย้ายระบบไปบัญชีอื่น))

### กู้คืน

- การกู้คืนคือการให้ระบบใช้สำเนาของชุดสำรองชุดหนึ่งเป็นไฟล์ฐานข้อมูล ระบบไม่เขียนข้อมูลของชุดสำรองทับไฟล์เดิม เพราะ Google Sheets ตีความค่าที่ขึ้นต้นด้วย `=` เป็นสูตรเมื่อเขียนกลับ และไฟล์เดิมต้องเก็บไว้ตรวจสาเหตุ
- ลำดับ: เปิดโหมดปิดปรับปรุง คัดลอกชุดสำรองที่เลือกเป็นไฟล์ใหม่ เปลี่ยน ID ของไฟล์ฐานข้อมูลใน Script Properties ให้ชี้ไฟล์ใหม่ ตรวจเลขรุ่นของโครงสร้างและจำนวนแถวของทุกแท็บเทียบกับชุดสำรอง แล้วปิดโหมดปิดปรับปรุง ชุดสำรองต้นทางไม่ถูกแก้
- ที่อยู่ของระบบที่ผู้ใช้เปิดไม่เปลี่ยน ID ของไฟล์ฐานข้อมูลเปลี่ยน
- ข้อมูลที่บันทึกหลังชุดสำรองนั้นไม่กลับมา รวมถึงไทม์ไลน์และบันทึกความปลอดภัยของช่วงนั้น ผู้ใช้ที่ล็อกอินหลังชุดสำรองต้องล็อกอินใหม่ รูปที่ส่งหลังชุดสำรองยังอยู่ใน Google Drive แต่ไม่มีแถวที่อ้างถึง
- หลังกู้คืน ระบบเพิ่มแถว `database_restored` ในบันทึกความปลอดภัย และรายงานของการกู้คืนบอกช่วงเวลาของข้อมูลที่หาย กับจำนวนรูปที่ไม่มีแถวอ้างถึง
- **โหมดปิดปรับปรุง** เป็นค่าใน Script Properties เมื่อเปิด server ปฏิเสธทุกคำขอก่อนอ่านฐานข้อมูล รวมถึงคำขอของ Dashboard สาธารณะ และหน้าเว็บแสดง "ระบบปิดปรับปรุงชั่วคราว" ใช้ระหว่างกู้คืน migration และคำสั่งเริ่มใช้ข้อมูลจริง เปิดและปิดได้เฉพาะเจ้าของ Apps Script ไม่มีปุ่มบนหน้าเว็บ คำขอตรวจรุ่นยังตอบ และบอกว่าระบบปิดปรับปรุงอยู่
- ผู้กู้คืนและขั้นตอนอยู่ใน [`operations.md` ข้อ 3](operations.md#3-กู้คืน) หลังเริ่มใช้ข้อมูลจริง PO เป็นผู้กู้คืนชุดใช้งานจริงเอง

### ระยะเวลาเก็บข้อมูล

PO กำหนดเมื่อ 17 พฤศจิกายน 2026 ตัวเลขในตารางเป็น **Not Verified** จนกว่า PO ได้คำตอบจากสำนักงานสาธารณสุขจังหวัด ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))

| ข้อมูล | ระยะเวลา |
|---|---|
| เหตุการณ์ งาน ผลการทำงาน ร่างรายงานสอบสวน ไทม์ไลน์ บันทึกความปลอดภัย และข้อมูลของผู้ป่วยที่ไม่ใช่ชื่อกับที่อยู่ | ตลอดอายุของระบบ |
| ชื่อ-สกุล บ้านเลขที่ ที่อยู่ของผู้ป่วยนอกอำเภอ และรูปถ่าย | 10 ปีนับจากวันที่เหตุการณ์ปิด ยกเลิก หรือตรวจสอบแล้วไม่จริง |
| ชื่อและอีเมลของผู้ใช้ | ตลอดอายุของระบบ เพราะไทม์ไลน์แสดงชื่อผู้ทำ |
| ชุดสำรอง ทั้งของบัญชีเจ้าของและบัญชีสำรอง | 8 สัปดาห์ และอีกไม่เกิน 30 วันในถังขยะ |

- รุ่นแรกไม่มีการลบและไม่มีการทำให้ระบุตัวไม่ได้อัตโนมัติ การทำเช่นนั้นเมื่อครบกำหนดเป็นงานที่ PO อนุมัติแยก และจะเกิดครั้งแรกในปี พ.ศ. 2579 การตรวจว่ามีเหตุการณ์ใดครบกำหนดอยู่ในงานประจำปี ([`operations.md` ข้อ 12](operations.md#12-งานประจำปี))
- ไม่พบกฎหมายหรือระเบียบที่กำหนดอายุการเก็บเป็นตัวเลขสำหรับทะเบียนเหตุการณ์หรือข้อมูลผู้ป่วยของงานควบคุมโรค ([ผลการค้นเรื่องอายุการเก็บ ส่วนที่ 2](research/data-retention-governance-facts.md))
- ตัวเลข 10 ปีมาจากระเบียบสำนักนายกรัฐมนตรีว่าด้วยงานสารบรรณ ซึ่งให้เก็บหนังสือราชการ "ไม่น้อยกว่า 10 ปี" ให้หนังสืออิเล็กทรอนิกส์ "เก็บไว้ตลอดไป" และให้อำนาจสั่งทำลายแก่หัวหน้าส่วนราชการระดับกรม ระเบียบไม่ได้ระบุว่าแถวข้อมูลในระบบงานเป็นหนังสืออิเล็กทรอนิกส์หรือไม่ ระยะที่สั้นกว่า 10 ปีจึงเสี่ยงเป็นการทำลายเอกสารราชการโดยผู้ที่ไม่มีอำนาจ
- มาตรฐานทีมประเมินผลงานย้อนหลัง 1 ถึง 2 ปี และผลการรับรองใช้ได้ 3 ปี ระยะ 10 ปีจึงครอบคลุมการประเมิน
- พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ไม่กำหนดตัวเลข แต่ให้ระบุระยะเวลาในคำแจ้ง และยกเว้นหน้าที่ลบสำหรับการเก็บเพื่อประโยชน์สาธารณะด้านการสาธารณสุข เอกสารนี้ไม่สรุปว่าข้อยกเว้นนั้นใช้กับระบบนี้หรือไม่
- ประกาศของคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลให้การลบครอบคลุมสำเนาและชุดสำรอง และถือว่าอายุ ที่อยู่ กับวันที่รับบริการเป็นข้อมูลที่ระบุตัวบุคคลทางอ้อมได้ การทำให้ระบุตัวไม่ได้เมื่อครบกำหนดจึงต้องพิจารณาอายุ หมู่บ้าน และวันเริ่มป่วยด้วย ไม่ใช่เฉพาะชื่อกับบ้านเลขที่

### การคุ้มครองข้อมูลส่วนบุคคล

หัวข้อนี้บอกสิ่งที่ระบบมีให้ ไม่ใช่คำแนะนำทางกฎหมาย หน้าที่ตามกฎหมายเป็นของผู้ควบคุมข้อมูลส่วนบุคคล ซึ่งแหล่งที่ค้นไม่ระบุว่าเป็นหน่วยงานใดสำหรับงานของ สสอ. ([ผลการค้น ส่วนที่ 4](research/data-retention-governance-facts.md))

- หน้า "การคุ้มครองข้อมูลส่วนบุคคล" อยู่ในเว็บของระบบ เปิดได้โดยไม่ล็อกอิน และมีลิงก์จากหน้าล็อกอินกับเมนู เนื้อหาเรียงตามมาตรา 23 ของพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562: วัตถุประสงค์และฐานของการเก็บ ข้อมูลที่เก็บและ[ระยะเวลาเก็บ](#ระยะเวลาเก็บข้อมูล) ผู้ที่เห็นข้อมูล ชื่อและช่องทางติดต่อของผู้ควบคุมข้อมูล และสิทธิของเจ้าของข้อมูล
- หน้านี้ครอบคลุมเจ้าของข้อมูลสองกลุ่ม: ผู้ป่วย และเจ้าหน้าที่ผู้ใช้ระบบ ซึ่งระบบเก็บชื่อ อีเมล และประวัติการเข้าระบบ
- ชื่อหน่วยงานและช่องทางติดต่อในหน้านี้มาจากค่าตั้ง ข้อความส่วนอื่น Claude Code ร่างในช่วงที่ 7 จากเอกสารชุดนี้ และ PO ให้ผู้รับผิดชอบของสำนักงานสาธารณสุขจังหวัดตรวจ
- ระบบไม่มีขั้นตอนขอความยินยอมจากผู้ป่วย ฐานของการเก็บตามที่ PO ระบุคือการเฝ้าระวังและควบคุมโรค ([ADR-0001](adr/0001-rebuild-on-apps-script-and-sheets.md))
- เมื่อการร่างรายงานด้วย AI เปิดอยู่ หน้านี้ระบุว่าข้อมูลใดของเหตุการณ์ถูกส่งให้ผู้ให้บริการ AI ในต่างประเทศ และข้อมูลใดไม่ถูกส่ง ตาม[รายการในข้อ 4](#ร่างรายงานสอบสวน) บันทึกรายการกิจกรรมการประมวลผลมีผู้ให้บริการ AI เป็นผู้รับข้อมูลด้วย
- มาตรการขั้นต่ำตามประกาศของคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2565 ที่ระบบมี: การยืนยันตัวตนและสิทธิ์ตามบทบาทกับหน่วยงาน ([ข้อ 2](#2-ผู้ใช้)) การเพิ่มและระงับผู้ใช้ การทบทวนรายการผู้ใช้ปีละครั้ง ไทม์ไลน์ที่เก็บทุกการเปลี่ยนแปลง และบันทึกความปลอดภัยที่เก็บการล็อกอิน การส่งออก การส่งข้อความให้ AI การดาวน์โหลดร่างรายงานสอบสวน กับการถูกปฏิเสธ
- Claude Code ร่างบันทึกรายการกิจกรรมการประมวลผลตามมาตรา 39 ในช่วงที่ 7 เพื่อให้ PO ส่งต่อผู้ควบคุมข้อมูล ขั้นตอนเมื่อเกิดเหตุละเมิดอยู่ใน [`operations.md` ข้อ 10](operations.md#10-เหตุละเมิดข้อมูลส่วนบุคคล)
- PO ถามสำนักงานสาธารณสุขจังหวัดสี่เรื่องก่อนเริ่มใช้ข้อมูลจริง: ผู้ควบคุมข้อมูลและเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล การแจ้งผู้ป่วย ระยะเวลาเก็บกับอำนาจทำลาย และนโยบายของกระทรวงเรื่องที่เก็บข้อมูล ([`operations.md` ข้อ 13](operations.md#13-คำถามถึงสำนักงานสาธารณสุขจังหวัด)) สี่เรื่องนี้ไม่เป็นเงื่อนไขบังคับของระบบ รายงานความพร้อมแสดงสถานะของแต่ละเรื่อง และ PO ยอมรับเรื่องที่ยังไม่มีคำตอบด้วยการอนุมัติการเริ่มใช้ข้อมูลจริง

### ชุดใช้งานจริงและชุดทดสอบ

- ก่อนเริ่มใช้ข้อมูลจริงมีระบบชุดเดียว ซึ่งใช้ข้อมูลสมมติ ชุดนี้กลายเป็นชุดใช้งานจริงเมื่อ PO อนุมัติการเริ่มใช้ข้อมูลจริง ที่อยู่ของระบบที่ผู้ใช้รู้จักจึงไม่เปลี่ยน
- ชุดทดสอบถูกสร้างในช่วงที่ 7 จากชุดสำรองของชุดแรก ก่อนล้างข้อมูลสมมติ การสร้างนี้เป็นการทดลองกู้คืนด้วย
- ชุดทดสอบแยกจากชุดใช้งานจริงครบสี่ส่วน

  | ส่วน | เหตุผลที่แยก |
  |---|---|
  | ไฟล์ฐานข้อมูลและโฟลเดอร์ของระบบ | ข้อมูลจริงไม่ถูกคัดลอกมาที่ชุดทดสอบ |
  | Apps Script project | แต่ละชุดมีที่อยู่ของ API งานตามเวลา และ Script Properties ของตัวเอง |
  | โปรเจกต์ Cloudflare Pages | แต่ละชุดมีที่อยู่คงที่ของหน้าเว็บและค่าตั้งของตัวเอง ที่อยู่ตัวอย่างของ Cloudflare เปลี่ยนทุกครั้ง จึงลงทะเบียนให้ล็อกอินด้วย Google ไม่ได้ |
  | OAuth client ในโปรเจกต์ Google Cloud ของตัวเอง | นโยบายของ Google ให้แยกโปรเจกต์ของการทดสอบกับการใช้งานจริง และ client ของชุดใช้งานจริงไม่มีที่อยู่ของชุดทดสอบ |

- ผู้ใช้ของชุดทดสอบมีเฉพาะ PO กับบัญชีสมมติ เจ้าหน้าที่จริงไม่มีบัญชีในชุดนี้ และชุดนี้มีแถบข้อมูลสมมติเสมอ
- `main` deploy ขึ้นชุดทดสอบเองเมื่อ merge ชุดใช้งานจริงตาม branch `release` การ Deploy ขึ้นชุดใช้งานจริงคือ PR จาก `main` เข้า `release` ซึ่ง PO สั่ง merge คำสั่งนั้นคือการอนุมัติ Deploy ครั้งนั้น ทั้งหน้าเว็บและ API ([`operations.md` ข้อ 8](operations.md#8-deploy-ขึ้นชุดใช้งานจริง))
- เมื่อ Deploy มี migration ของโครงสร้าง ระบบสำรองก่อน เปิดโหมดปิดปรับปรุงระหว่างเปลี่ยนโครงสร้าง และหยุดถ้าสำรองไม่สำเร็จ
- หลังเริ่มใช้ข้อมูลจริง Claude Code ไม่เปิดสี่อย่างของชุดใช้งานจริง: ไฟล์ฐานข้อมูล โฟลเดอร์ใน Google Drive log ของ Apps Script และหน้าเว็บในฐานะผู้ใช้ เมื่อผู้ใช้พบข้อผิดพลาด PO ค้น log ด้วยรหัสอ้างอิงแล้วคัดลอกบรรทัดนั้นให้ และ Claude Code ทำซ้ำในชุดทดสอบ ([`operations.md` ข้อ 9](operations.md#9-ข้อผิดพลาดในชุดใช้งานจริง))
- **คำขอตรวจรุ่น** ตอบโดยไม่ต้องล็อกอิน และคืนเพียงเลขรุ่นของโค้ด เลขรุ่นของโครงสร้าง และสถานะของโหมดปิดปรับปรุง Claude Code ใช้คำขอนี้กับหน้าล็อกอินตรวจชุดใช้งานจริงหลัง Deploy และไม่ตรวจอย่างอื่น
- PO เปลี่ยนสถานะของหน้ายินยอมของ Google เป็น In production ตั้งแต่ช่วงที่ 1 ระบบขอเฉพาะตัวตนและอีเมล จึงไม่ต้องผ่านการตรวจของ Google ชื่อและโลโก้ของระบบบนหน้าจอของ Google ต้องผ่านการตรวจอีกขั้นหนึ่ง ซึ่งรุ่นแรกไม่ทำ

### การเริ่มใช้ข้อมูลจริง

- การอนุมัติการเริ่มใช้ข้อมูลจริงคือการที่ PO สั่ง merge PR ที่บันทึกวันเริ่มใช้ใน [roadmap](roadmap.md) PR นั้นมีรายงานความพร้อมตาม[รายการตรวจ](operations.md#6-รายการตรวจก่อนเริ่มใช้ข้อมูลจริง) การอนุมัตินี้รวมการอนุมัติให้ล้างข้อมูลสมมติของชุดแรก
- **คำสั่งเริ่มใช้ข้อมูลจริง** เป็นฟังก์ชันของ server ที่เรียกจากหน้าเว็บไม่ได้ และทำงานเฉพาะเมื่อระบบยังใช้ข้อมูลสมมติ คำสั่งทำตามลำดับ: เปิดโหมดปิดปรับปรุง สำรองและตรวจชุดสำรอง ล้างตารางตามด้านล่าง ย้ายรูปของข้อมูลสมมติลงถังขยะของ Google Drive ปิด Dashboard สาธารณะ ปิดการร่างรายงานด้วย AI และลบกุญแจของ Gemini API เปลี่ยนค่าข้อมูลสมมติเป็นเท็จ เพิ่มแถว `real_data_started` ในบันทึกความปลอดภัย แล้วปิดโหมดปิดปรับปรุง

  | การกระทำ | ตาราง |
  |---|---|
  | ล้างทุกแถว | `events`, `patients`, `tasks`, `task_results`, `attachments`, `report_drafts`, `timeline`, `public_snapshot`, `sessions`, `audit_log` และ `users` |
  | เก็บไว้ | `units`, `villages`, `population`, `diseases` และ `settings` |

- เมื่อ `users` ว่าง ระบบสร้างผู้ดูแลคนแรกจากค่าตั้งของ Apps Script ตาม[ข้อ 2](#บัญชีผู้ใช้) แล้ว PO เพิ่มผู้ดูแลคนที่สองและผู้ใช้จริง เลขที่เหตุการณ์เริ่มนับใหม่
- หน่วยบริการและหน่วยที่รับผิดชอบของหมู่บ้านไม่ถูกล้าง PO จึงใส่หน่วยบริการจริงตั้งแต่ช่วงที่ 1 ชื่อหน่วยบริการ หมู่บ้าน และประชากรเป็นข้อมูลสาธารณะของหน่วยงาน ไม่ใช่ข้อมูลของบุคคล
- Claude Code ซ้อมคำสั่งนี้ในชุดทดสอบก่อน แล้วรันในชุดแรกหนึ่งครั้งหลัง PO อนุมัติ ตรวจด้วย Playwright ว่าระบบว่างและไม่มีแถบข้อมูลสมมติ แล้วเลิกเข้าถึงชุดนั้นก่อนที่ข้อมูลจริงรายการแรกจะถูกกรอก
- ในวันเริ่มใช้ ทุกหน่วยบริการเข้าใช้ได้พร้อมกัน ระบบไม่มีกลไกเปิดทีละกลุ่ม หน่วยที่ยังไม่ล็อกอินทำงานต่อได้ เพราะผู้ดูแลส่ง LINE และบันทึกผลแทนหน่วยบริการได้
- ผู้ดูแลบันทึกเหตุการณ์ที่รับแจ้งตั้งแต่วันเริ่มใช้ เหตุการณ์ที่ยังอยู่ในระยะเฝ้าระวัง ผู้ดูแลเลือกกรอกย้อนหลังเองได้ ไม่มีการนำเข้าเป็นชุด
- ก่อนอนุมัติ ระบบต้องมีผู้ดูแลที่จะใช้งานจริงอย่างน้อย 2 คน เพื่อให้มีคนตรวจสอบข่าว มอบหมายงาน และเพิ่มผู้ใช้ได้เมื่ออีกคนไม่อยู่

### ข้อจำกัดที่ทราบ

- ต้องมีอินเทอร์เน็ต รุ่นแรกยังบันทึกแบบออฟไลน์ไม่ได้
- การล็อกอินด้วย Google ใช้ไม่ได้ในเบราว์เซอร์ในแอปของ LINE ตามเอกสารของ LINE และของ Google ผู้ใช้ต้องเปิดระบบในเบราว์เซอร์ของเครื่อง ([ผลการค้นเรื่องข้อความ LINE](research/line-message-facts.md) ส่วนที่ 4)
- ระบบไม่รู้ว่าข้อความ LINE ถูกส่งจริงหรือไม่ เวลาที่แจ้งหน่วยบริการคือเวลาที่ผู้ดูแลยืนยัน
- ทั้งระบบพึ่งบริการของ Google ถ้า Google ขัดข้อง ระบบใช้ไม่ได้
- การร่างรายงานด้วย AI พึ่ง Gemini ซึ่งเป็นบริการภายนอกที่เปลี่ยนรุ่นและราคาบ่อย เมื่อ Gemini ใช้ไม่ได้หรือการร่างด้วย AI ปิดอยู่ ผู้ดูแลยังดาวน์โหลดไฟล์ตั้งต้นที่ระบบเติมข้อมูลให้ได้ ([ร่างรายงานสอบสวน](#ร่างรายงานสอบสวน))
- การร่างด้วย AI กับข้อมูลจริงเป็นส่วนเดียวของระบบที่มีค่าใช้จ่าย และ Google เก็บข้อความที่ส่งกับคำตอบไว้ 55 วันเพื่อตรวจการใช้ผิดนโยบาย ซึ่งระบบปิดไม่ได้ ([ผลการค้นเรื่องการร่างด้วย AI](research/ai-report-drafting-facts.md) ข้อ 2.3 และ 3.4)
- API ของ Apps Script มองไม่เห็น IP ของผู้เรียก จึงจำกัดการเรียกถี่ ๆ เป็นราย IP ไม่ได้ ระบบลดผลกระทบด้วยการปฏิเสธคำขอที่ไม่มี session ก่อนอ่านฐานข้อมูล ให้คำขอของ Dashboard สาธารณะอ่านเฉพาะตารางตัวเลขรวมสาธารณะ และ cache คำตอบนั้น
- ทั้งระบบรับคำขอพร้อมกันได้จำกัด ([`schema.md` ข้อ 7](schema.md#7-ขนาดที่ออกแบบรองรับ)) การเรียกถี่ ๆ จากภายนอกจึงทำให้ผู้ใช้จริงใช้งานไม่ได้ชั่วคราว เอกสารของ Google ไม่ระบุว่าคำขอของผู้ที่ไม่ล็อกอินใช้โควตาเดียวกับผู้ใช้หรือไม่ เรื่องนี้วัดในช่วงที่ 0 ของ roadmap ถ้าใช้โควตาเดียวกัน แผนของช่วงที่ 5 วางสำเนาของตัวเลขรวมสาธารณะไว้ที่ Cloudflare เพื่อให้ Dashboard สาธารณะไม่เรียก Apps Script ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))
- session token เก็บในเบราว์เซอร์ของผู้ใช้ เพราะ Apps Script ตั้ง cookie ที่สคริปต์อ่านไม่ได้ให้ไม่ได้ ระบบลดความเสี่ยงด้วยข้อจำกัดการโหลดสคริปต์ในหัวข้อความปลอดภัย
- ข้อมูลอยู่ในบัญชี Gmail ส่วนตัวของ PO ซึ่ง PO ยอมรับความเสี่ยงแล้ว ([ADR-0001](adr/0001-rebuild-on-apps-script-and-sheets.md)) การค้นไม่พบข้อความที่กล่าวถึงบัญชีส่วนบุคคลหรือห้ามบริการคลาวด์ของต่างประเทศโดยเจาะจง แต่ยังอ่านพระราชบัญญัติการรักษาความมั่นคงปลอดภัยไซเบอร์ พ.ศ. 2562 และนโยบายความมั่นคงปลอดภัยสารสนเทศของกระทรวงสาธารณสุขไม่ได้ เรื่องนี้จึงเป็น **Not Verified** ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))
- การกู้คืนเสียข้อมูลได้ถึง 7 วัน และเมื่อบัญชีเจ้าของถูกลบ รูปถ่ายหาย ([สำรองข้อมูล](#สำรองข้อมูล) และ[บัญชีสำรอง](#บัญชีสำรอง))
- ระบบไม่บันทึกว่าใครเปิดดูข้อมูลของผู้ป่วยรายใด บันทึกความปลอดภัยเก็บการล็อกอิน การส่งออก การส่งข้อความให้ AI การดาวน์โหลดร่างรายงานสอบสวน และการถูกปฏิเสธ ส่วนการเปลี่ยนแปลงอยู่ในไทม์ไลน์
- Apps Script project ไฟล์ฐานข้อมูล OAuth client และโปรเจกต์ Cloudflare Pages ผูกกับบัญชีของ PO และ Google ไม่ให้โอน deployment งานตามเวลา กับค่าตั้งของ Apps Script ไปบัญชีอื่น การเปลี่ยนเจ้าของจึงเป็นการสร้างชุดใหม่แล้วกู้คืนข้อมูล ([`operations.md` ข้อ 11](operations.md#11-ย้ายระบบไปบัญชีอื่น))

## 9. ขอบเขต

### รุ่นแรก

ทุกข้อในข้อ 2–8 และชุดโรคติดต่อนำโดยยุงลาย

### รุ่นถัดไป (ยังไม่ทำ)

- รายงานสอบสวนฉบับสมบูรณ์ และรายงานสรุปเสนอผู้บริหาร รุ่นแรกร่างเฉพาะรายงานสอบสวนเบื้องต้น
- ส่งข้อความ LINE อัตโนมัติ
- อีเมลสรุปงานค้างทุกเช้า
- หน้าจอให้ผู้ดูแลสร้างแบบบันทึกเอง
- ชุดโรคอื่นนอกจากชุดโรคติดต่อนำโดยยุงลาย
- การใช้งานแบบออฟไลน์
- ประชากรแยกอายุ

### สิ่งที่ระบบนี้ไม่ได้ทำแทน

ระบบนี้ไม่ใช่ช่องทางแจ้งโรคตามกฎหมาย การแจ้งโรคติดต่อที่ต้องเฝ้าระวังต่อเจ้าพนักงานของ สสจ. ผ่านระบบรายงานของกรมควบคุมโรคยังทำตามเดิม ระบบนี้เป็นทะเบียนรับแจ้งข่าวและเครื่องมือติดตามงานของ สสอ.

## 10. เกณฑ์ยอมรับของรุ่นแรก

รุ่นแรกผ่านเมื่อทำเส้นทางนี้ได้ครบด้วยข้อมูลสมมติ บนระบบที่ deploy จริง

1. ผู้ดูแลเพิ่มหน่วยบริการ หมู่บ้าน และผู้ใช้ของหน่วยบริการ
2. หน่วยบริการเปิดลิงก์จาก LINE บนมือถือ ล็อกอินด้วย Google และแจ้งเหตุการณ์ไข้เลือดออก
3. ผู้ดูแลเห็นเรื่องในงานวันนี้ ตรวจสอบ ประเมินเกณฑ์ เพิ่มผู้ป่วย มอบหมายงานของชุดโรคติดต่อนำโดยยุงลาย และมอบหมายงานสอบสวนโรคให้ สสอ. แล้วบันทึกผลของงานนั้น
4. หน่วยบริการรับงาน บันทึกผลพร้อมรูป และระบบแสดงผลการเทียบเป้าของแต่ละรอบ
5. หน่วยบริการอีกแห่งเปิดลิงก์ของงานนั้นไม่ได้ และไม่เห็นเหตุการณ์นั้น
6. ผู้ดูเห็นเหตุการณ์ ผู้ป่วย งาน ผล และรูปถ่ายเท่ากับผู้ดูแล และทุกคำขอแก้ไขจากผู้ดูถูกปฏิเสธ
7. Dashboard สาธารณะแสดงตัวเลขระดับตำบล ซ่อนช่องที่ต่ำกว่า 5 และแสดงยอดรวมที่มีช่องซ่อนอยู่เป็นช่วง
8. ผู้ดูแลส่งออก Excel ปิดเหตุการณ์ และเปิดใหม่ได้
9. ผู้ดูแลเปิดหน้าร่างรายงานสอบสวนของเหตุการณ์นั้น ดาวน์โหลดไฟล์ตั้งต้น ให้ AI ช่วยร่าง แล้วดาวน์โหลดไฟล์ Word ที่มีหกหัวข้อ มีตัวเลขตรงกับหน้าเหตุการณ์ และไม่มีชื่อผู้ป่วยกับบ้านเลขที่
10. หน่วยบริการ 2 แห่งทดลองใช้ด้วยข้อมูลสมมติ และ PO ยืนยันผลตาม[เกณฑ์ผ่านของการทดลองใช้](operations.md#เกณฑ์ผ่าน)
11. ชุดทดสอบที่สร้างจากชุดสำรองเปิดใช้ได้ และจำนวนแถวของทุกแท็บตรงกับตอนสำรอง

ข้อ 1–9 ทดสอบบนระบบที่ deploy โดย Claude Code ด้วย Playwright ขั้นที่ต้องใช้มือถือจริงทดสอบโดย PO ทั้งบน iPhone และ Android และไฟล์ Word ของข้อ 9 PO เปิดใน Word บนเครื่องของ สสอ. ([`operations.md` ข้อ 4](operations.md#4-การทดสอบเส้นทางเต็ม))
