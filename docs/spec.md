## 1. ระบบนี้คืออะไร

Smart SRRT v2 คือระบบติดตามเหตุการณ์โรคและภัยสุขภาพของ **สำนักงานสาธารณสุขอำเภอ (สสอ.) หนึ่งแห่ง** ใช้ตั้งแต่รับแจ้งข่าว ตรวจสอบ มอบหมายงานให้หน่วยบริการลงพื้นที่ รับผลกลับ ติดตาม จนปิดเหตุการณ์

ระบบนี้ไม่ใช่ระบบเวชระเบียน ไม่ใช่เครื่องมือวินิจฉัย และไม่ได้เชื่อมกับระบบรายงานของกระทรวง ข้อมูลที่ต้องส่งให้หน่วยงานอื่นใช้การส่งออกไฟล์

### ปัญหาของระบบเก่าที่ v2 ต้องแก้

| ระบบเก่า | v2 |
|---|---|
| สถานะของเหตุการณ์คำนวณจากช่องในฟอร์มยาวหนึ่งฟอร์ม ผู้ใช้ไม่รู้ว่าขั้นถัดไปคืออะไร | ทุกขั้นเป็นปุ่มที่กดได้ และบันทึกลงไทม์ไลน์ของเหตุการณ์ |
| มอบหมายงานได้เฉพาะผู้ใช้ที่ล็อกอิน แต่คนลงพื้นที่คือหน่วยบริการที่ไม่ได้ล็อกอิน | มอบหมายงานให้หน่วยบริการเป็นหน่วย และหน่วยบริการล็อกอินมาบันทึกผลเอง |
| โมดูลไข้เลือดออก (D331) แยกตาราง แยกสิทธิ์ และไม่เขียนผลกลับไปที่เหตุการณ์ | ทุกโรคอยู่ในเหตุการณ์เดียว ขั้นตอนเฉพาะโรคเป็น "ชุดโรค" ที่เพิ่มได้โดยไม่แก้ตาราง |
| ไม่มีส่วนที่เกี่ยวกับ LINE ซึ่งเป็นช่องทางประสานงานจริง | ระบบเตรียมข้อความ LINE พร้อมลิงก์ไปที่งาน ผู้ใช้กดส่งเอง |
| หน้าจอแสดงรหัส UUID และสถานะภาษาอังกฤษ | หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดงรหัสภายใน |

## 2. ผู้ใช้

| บทบาท (`role`) | ใคร | ทำอะไรได้ |
|---|---|---|
| ผู้ดูแล (`admin`) | เจ้าหน้าที่ สสอ. มีได้มากกว่าหนึ่งคน | ทุกอย่าง: รับแจ้ง ตรวจสอบ ประเมินเกณฑ์ มอบหมายงาน รับผล ปิดเหตุการณ์ จัดการผู้ใช้ หน่วยงาน หมู่บ้าน และค่าตั้งระบบ |
| ผู้ใช้หน่วยบริการ (`unit`) | เจ้าหน้าที่ของ รพ.สต. รพ. หรือ สสช. แต่ละคนผูกกับหน่วยหนึ่งแห่ง | แจ้งเหตุการณ์ รับงานที่มอบหมายให้หน่วยของตน บันทึกผล แนบรูป เห็นเฉพาะเรื่องที่หน่วยของตนแจ้งหรือได้รับมอบหมาย |
| ผู้ดู (`viewer`) | บุคลากรของ สสอ. ที่ไม่ได้บันทึกข้อมูล เช่น สาธารณสุขอำเภอ | เห็นเหตุการณ์ ผู้ป่วย งาน ผล รูปถ่าย และสรุป เท่ากับผู้ดูแล แก้ไขไม่ได้ ส่งออกได้เฉพาะตัวเลขสรุป และไม่เห็นหน้าตั้งค่า การจัดการผู้ใช้ กับบันทึกความปลอดภัย |
| บุคคลทั่วไป | ไม่ล็อกอิน | เห็นเฉพาะ Dashboard สาธารณะ (ข้อ 7) |

กฎการมองเห็นทั้งหมดบังคับที่ server หน้าจอซ่อนปุ่มเพื่อความสะดวกเท่านั้น ตารางสิทธิ์ละเอียดอยู่ใน [`schema.md` ข้อ 6](schema.md#6-กฎสิทธิ์การมองเห็น)

### การเข้าสู่ระบบ

- เข้าสู่ระบบด้วยบัญชี Google เท่านั้น ระบบไม่เก็บรหัสผ่าน
- อีเมลที่ไม่อยู่ในตารางผู้ใช้ หรือบัญชีที่ถูกระงับ เข้าระบบไม่ได้ ทั้งสองกรณีเห็นข้อความเดียวกัน: "บัญชีนี้ยังไม่มีสิทธิ์เข้าใช้ ติดต่อผู้ดูแลของ [ชื่อหน่วยงาน]" หน้าจอไม่มีปุ่มขอสิทธิ์ และไม่บอกว่าบัญชีถูกระงับ
- เครื่องหนึ่งเครื่องอยู่ในระบบได้ 7 วัน แล้วต้องยืนยันกับ Google ใหม่
- ผู้ใช้หนึ่งคนอยู่ในระบบได้หลายเครื่องพร้อมกัน ไม่จำกัดจำนวน การกดออกจากระบบมีผลกับเครื่องนั้นเครื่องเดียว
- เมื่อผู้ใช้เปิดลิงก์ของงานหรือเหตุการณ์ขณะยังไม่ได้ล็อกอิน ระบบพาไปหน้านั้นหลังล็อกอินสำเร็จ

### บัญชีผู้ใช้

- หนึ่งบัญชีเป็นของคนหนึ่งคน และผูกกับอีเมล Google ของคนนั้น หน้าเพิ่มผู้ใช้และคู่มือระบุให้ใช้อีเมลส่วนตัวของแต่ละคน ไม่ใช้อีเมลกลางของหน่วยงาน ระบบตรวจไม่ได้ว่าอีเมลใดเป็นอีเมลกลาง
- ผู้ดูแลเพิ่มผู้ใช้ด้วยชื่อ อีเมล Google บทบาท และหน่วยงาน ไม่มีหน้าสมัครเอง
- ระบบไม่ส่งข้อความหรืออีเมลถึงผู้ใช้ใหม่ และไม่เตรียมข้อความเชิญ เจ้าหน้าที่ สสอ. แจ้งผู้ใช้เอง
- ผู้ดูแลคนแรกมาจากอีเมลที่ตั้งไว้ในค่าตั้งของ Apps Script ระบบสร้างบัญชีนี้เมื่อตารางผู้ใช้ว่างเท่านั้น
- ผู้ดูแลแก้ชื่อ อีเมล บทบาท และหน่วยงานของบัญชีได้ ผู้ใช้แก้ข้อมูลบัญชีของตนเองไม่ได้
- การแก้บทบาทหรือหน่วยงานมีผลตั้งแต่คำขอถัดไป เมื่อผู้ใช้หน่วยบริการย้ายหน่วย ผู้ดูแลแก้หน่วยงานของบัญชีเดิม ผู้ใช้เลิกเห็นงานของหน่วยเดิมและเห็นงานของหน่วยใหม่ งานและผลการทำงานที่บันทึกไว้ยังเป็นของหน่วยเดิม และยังแสดงชื่อผู้บันทึก
- การแก้อีเมลทำให้บัญชีออกจากระบบบนทุกเครื่อง และผูกกับบัญชี Google ของอีเมลใหม่เมื่อล็อกอินครั้งถัดไป ประวัติของบัญชียังอยู่ครบ
- ไม่มีการลบบัญชี ผู้ดูแลระงับบัญชีได้ และเปิดใช้บัญชีที่ระงับใหม่ได้ บัญชีที่ถูกระงับถูกปฏิเสธตั้งแต่คำขอถัดไปบนทุกเครื่อง ชื่อของบัญชีที่ระงับยังแสดงในไทม์ไลน์
- ผู้ดูแลสั่งให้บัญชีใดก็ได้ออกจากระบบบนทุกเครื่องได้ เช่น เมื่อมือถือหาย
- ผู้ดูแลระงับหรือเปลี่ยนบทบาทของบัญชีตนเองไม่ได้ ต้องให้ผู้ดูแลอีกคนทำ และระบบปฏิเสธการระงับหรือเปลี่ยนบทบาทของผู้ดูแลคนสุดท้ายที่ยังใช้งานอยู่ ระบบจึงมีผู้ดูแลอย่างน้อยหนึ่งคนเสมอ
- รายการผู้ใช้แสดงชื่อ อีเมล บทบาท หน่วยงาน สถานะ และเวลาที่เข้าระบบล่าสุด บัญชีที่ยังไม่เคยเข้าแสดงว่า "ยังไม่เคยเข้า"

## 3. ขั้นตอนของเหตุการณ์

เหตุการณ์หนึ่งรายการคือเรื่องที่ได้รับแจ้งหนึ่งเรื่อง เช่น "ไข้เลือดออก หมู่ 5 ตำบล ก" เหตุการณ์มีผู้ป่วยได้หลายราย และมีงานที่มอบหมายได้หลายงาน แต่ละเหตุการณ์มีเลขที่สั้น ๆ ที่อ่านได้ เช่น `2569-0012` ใช้แสดงบนหน้าจอและในข้อความ LINE

```
รับแจ้ง → ตรวจสอบข่าว → ประเมินเกณฑ์ → มอบหมายงาน → รับผล → ติดตาม → ปิดเหตุการณ์
```

| ขั้น | ใครทำ | ผลที่เกิด | สถานะหลังทำ (`stage`) |
|---|---|---|---|
| รับแจ้ง | ผู้ดูแล หรือหน่วยบริการ | สร้างเหตุการณ์ใหม่ | รอตรวจสอบ (`received`) |
| ตรวจสอบข่าว | ผู้ดูแล | บันทึกวิธีตรวจสอบและผล | ตรวจสอบแล้วจริง (`verified`) หรือ ตรวจสอบแล้วไม่จริง (`not_confirmed`) |
| ประเมินเกณฑ์ | ผู้ดูแล | บันทึกว่าเข้าเกณฑ์สอบสวนโรคหรือไม่ | กำลังดำเนินการ (`responding`) |
| มอบหมายงาน | ผู้ดูแล | สร้างงานให้หน่วยบริการ พร้อมกำหนดเสร็จ และเตรียมข้อความ LINE | ไม่เปลี่ยน |
| รับงานและบันทึกผล | หน่วยบริการ | บันทึกเวลาที่ทำจริง ผล และรูปถ่าย | ไม่เปลี่ยน |
| รับผล | ผู้ดูแล | ทำเครื่องหมายว่าตรวจผลแล้ว | ไม่เปลี่ยน |
| ติดตาม | ผู้ดูแล และหน่วยบริการ | ทำซ้ำสามขั้นก่อนหน้าสำหรับงานรอบถัดไป และเพิ่มผู้ป่วยรายใหม่เมื่อพบ | ไม่เปลี่ยน |
| ปิดเหตุการณ์ | ผู้ดูแล | บันทึกสรุป ระบบเตือนถ้ายังมีงานค้าง | ปิดแล้ว (`closed`) |
| เปิดใหม่ | ผู้ดูแล | ต้องระบุเหตุผล | กำลังดำเนินการ (`responding`) |

กฎของขั้นตอน

- ทุกการกระทำเพิ่มหนึ่งแถวในไทม์ไลน์ของเหตุการณ์ พร้อมผู้ทำ เวลาที่ทำจริง และเวลาที่บันทึก
- เวลาที่ทำจริงผู้ใช้กรอกเอง มีทั้งวันที่และเวลา ค่าตั้งต้นคือเวลาปัจจุบัน เวลาที่บันทึกระบบใส่ให้ หน้าจอแสดงให้เห็นเมื่อสองค่านี้ห่างกันมาก เพื่อให้รู้ว่าเป็นการบันทึกย้อนหลัง
- การเทียบกับกำหนดเสร็จและเป้าเวลาทุกจุดใช้เวลาที่ทำจริง
- ระบบไม่ปิดเหตุการณ์เอง
- การแก้ไขข้อมูลตรวจค่า revision ก่อนบันทึก ถ้ามีคนแก้ไปก่อน ระบบปฏิเสธและให้โหลดข้อมูลใหม่
- เหตุการณ์ที่ตรวจสอบแล้วไม่จริงจบที่สถานะ `not_confirmed` และไม่ถูกนับในสรุปใด ๆ

### ผู้ป่วยในเหตุการณ์

- ผู้ดูแลเพิ่มผู้ป่วยทีละราย ผู้ป่วยรายใหม่ในพื้นที่และช่วงเวลาเดียวกันเพิ่มเข้าเหตุการณ์เดิม
- ข้อมูลที่เก็บ: ชื่อ-สกุล อายุ เพศ บ้านเลขที่ หมู่บ้าน วันเริ่มป่วย การวินิจฉัย เวลาที่วินิจฉัย สถานที่รักษา
- ระบบไม่เก็บเลขบัตรประชาชนและ HN
- ชื่อและบ้านเลขที่เห็นได้เฉพาะบุคลากรของ สสอ. (ผู้ดูแลและผู้ดู) และหน่วยบริการที่ได้รับมอบหมายงานของผู้ป่วยรายนั้น

### งานที่มอบหมาย

- งานหนึ่งงานผูกกับเหตุการณ์เสมอ และเลือกผูกกับผู้ป่วยรายใดรายหนึ่งได้
- ระบบเสนอหน่วยบริการที่รับผิดชอบหมู่บ้านของเหตุการณ์หรือของผู้ป่วยให้อัตโนมัติ ผู้ดูแลเปลี่ยนได้
- งานมีชนิด คำสั่งเพิ่มเติม กำหนดเสร็จ และสถานะ: มอบหมายแล้ว (`assigned`) → รับงานแล้ว (`accepted`) → บันทึกผลแล้ว (`done`)
- ชุดโรคกำหนดชนิดงานและแบบบันทึกผลของตัวเอง (ข้อ 5) โรคที่ไม่มีชุดโรคใช้ชนิดงานกลาง ([ข้อ 11](#11-ข้อเสนอที่รอ-po-ยืนยัน))

## 4. หน้าจอหลัก

### ผู้ดูแล: "งานวันนี้"

หน้าแรกเป็นรายการสิ่งที่ต้องทำ เรียงตามความเร่งด่วน แต่ละรายการมีปุ่มเดียวสำหรับขั้นถัดไป

1. เหตุการณ์ที่รอตรวจสอบ
2. เหตุการณ์ที่รอประเมินเกณฑ์
3. เหตุการณ์ที่เข้าเกณฑ์แต่ยังไม่ได้มอบหมายงาน
4. งานที่เกินกำหนด และงานที่ใกล้ครบกำหนด พร้อมจำนวนวันที่ค้าง และปุ่มเตรียมข้อความ LINE เพื่อติดตาม
5. ผลจากหน่วยบริการที่ยังไม่ได้ตรวจ
6. เหตุการณ์ที่ไม่มีงานค้างแล้ว รอปิด

หน้าอื่น: รายการเหตุการณ์ทั้งหมดพร้อมตัวกรอง หน้าเหตุการณ์ (ข้อมูล ผู้ป่วย งาน ไทม์ไลน์) สรุปภาพรวม ส่งออกข้อมูล ตั้งค่า (ผู้ใช้ หน่วยงาน หมู่บ้าน ประชากร รายการโรค ชุดโรค ชื่อและโลโก้หน่วยงาน)

### หน่วยบริการ: "งานของหน่วย"

ออกแบบสำหรับมือถือเป็นหลัก เพราะเปิดจากลิงก์ใน LINE

1. งานที่ต้องทำ เรียงตามกำหนดเสร็จ
2. ปุ่ม "แจ้งเหตุการณ์"
3. เรื่องที่หน่วยของตนแจ้งไว้ และสถานะปัจจุบัน

หน้างาน: รายละเอียดงาน ข้อมูลผู้ป่วยที่เกี่ยวข้อง ปุ่มรับงาน แบบบันทึกผล และช่องแนบรูป

### ข้อมูลตั้งต้น

ผู้ดูแลจัดการข้อมูลเหล่านี้ในหน้าตั้งค่า ที่มาของข้อมูลชุดแรกอยู่ใน [`schema.md` ข้อ 4](schema.md#4-ข้อมูลตั้งต้น)

- **หน่วยบริการ** มีสามชนิด: รพ.สต. รพ. และ สสช. ทุกชนิดรับงานและมีสิทธิ์เหมือนกัน องค์กรปกครองส่วนท้องถิ่นไม่มีบัญชีในระบบ หน่วยบริการเป็นผู้ประสานและบันทึกผลเอง
- **หมู่บ้าน** รายการตำบล หมู่ที่ และชื่อหมู่บ้านมาจากสถิติทะเบียนราษฎร์ของกรมการปกครอง ทุกหมู่บ้านมีหน่วยที่รับผิดชอบหนึ่งแห่ง ตำบลหนึ่งมีได้หลายหน่วยบริการ แบ่งตามหมู่ที่ ผู้ดูแลกำหนดหน่วยที่รับผิดชอบได้ทีละหลายหมู่บ้าน และหน้าตั้งค่าแสดงหมู่บ้านที่ยังไม่มีหน่วยที่รับผิดชอบ
- **รายการโรค** แต่ละโรคอยู่ในกลุ่มโรคหนึ่งกลุ่ม การแจ้งเหตุการณ์ต้องเลือกโรคจากรายการ ไม่มีช่องพิมพ์ชื่อโรคเอง ผู้ที่ไม่พบโรคในรายการเลือก "อื่น ๆ" แล้วบรรยาย ผู้ดูแลแก้เป็นโรคที่ถูกต้องตอนตรวจสอบข่าว และเพิ่มโรคใหม่ได้เอง
- **ประชากร** เก็บจำนวนชาย หญิง รวม และจำนวนบ้านของแต่ละหมู่บ้านแยกตามปี จากสถิติชุดเดียวกัน การแก้ตัวเลขของปีหนึ่งไม่เปลี่ยนตัวเลขของปีอื่น
- **ชื่อและโลโก้หน่วยงาน** แสดงที่หน้าล็อกอิน แถบบนของทุกหน้า Dashboard สาธารณะ และหัวไฟล์ที่ส่งออก โลโก้ไม่บังคับ
- **ไม่มีการลบ** หน่วยบริการ หมู่บ้าน และโรคที่ไม่ใช้แล้วถูกเลิกใช้ รายการที่เลิกใช้เลือกไม่ได้ในเหตุการณ์และงานใหม่ และยังแสดงในเหตุการณ์เก่า
- ระบบปฏิเสธการเลิกใช้หน่วยบริการที่ยังมีงานที่ไม่เสร็จ บัญชีที่ยังไม่ถูกระงับ หรือหมู่บ้านในความรับผิดชอบ และบอกว่าต้องย้ายอะไรก่อน
- เมื่อผู้ดูแลแก้ชื่อหน่วยบริการ หมู่บ้าน หรือโรค ทุกหน้ารวมถึงเหตุการณ์เก่าแสดงชื่อปัจจุบัน
- ผู้ดูแลเพิ่มและแก้หมู่บ้านทีละรายการบนหน้าจอได้ เช่น แก้ชื่อให้ตรงกับที่ใช้ในพื้นที่

### ข้อความ LINE

ระบบไม่ส่งข้อความเอง ระบบเตรียมข้อความ แล้วผู้ใช้กด "คัดลอก" หรือ "เปิด LINE" เพื่อเลือกกลุ่มและส่ง

- ผู้ดูแลได้ข้อความหลังมอบหมายงาน และเมื่อต้องการติดตามงานค้าง
- หน่วยบริการได้ข้อความหลังแจ้งเหตุการณ์หรือบันทึกผล เพื่อแจ้ง สสอ.
- ข้อความมี: เลขที่เหตุการณ์ โรค หมู่บ้าน งานที่ต้องทำ กำหนดเสร็จ และลิงก์ไปที่งานหรือเหตุการณ์
- ข้อความไม่มีชื่อผู้ป่วยและบ้านเลขที่ ผู้รับต้องเปิดลิงก์และล็อกอินจึงจะเห็น
- เมื่อผู้ดูแลกดยืนยันว่าส่งแล้ว ระบบบันทึกเวลาที่แจ้งหน่วยบริการไว้ที่งาน ค่าตั้งต้นคือเวลาที่กดยืนยัน ผู้ดูแลแก้ได้เมื่อแจ้งไว้ก่อนหน้าด้วยช่องทางอื่น เช่น โทรศัพท์

### รูปถ่าย

- แนบได้เฉพาะรูปถ่ายของงานในพื้นที่ เช่น การพ่นสารเคมี หรือภาชนะที่พบลูกน้ำ ไม่รับไฟล์เอกสาร
- หน้าแนบรูปและช่องข้อความอิสระทุกช่องมีคำเตือน: ห้ามถ่ายเอกสารที่มีชื่อผู้ป่วย และห้ามถ่ายใบหน้าผู้ป่วย
- ระบบย่อรูปในเครื่องของผู้ใช้ก่อนส่ง การย่อนี้ลบข้อมูลที่ฝังมากับรูป เช่น พิกัดสถานที่ถ่าย
- รูปเก็บใน Google Drive โฟลเดอร์ส่วนตัวของระบบ ไม่มีลิงก์สาธารณะ เปิดดูได้ผ่านระบบตามสิทธิ์เท่านั้น

## 5. ชุดโรค

ทุกโรคใช้ขั้นตอนในข้อ 3 เหมือนกัน **ชุดโรค** (disease pack) เพิ่มสี่อย่างให้โรคที่มีแนวทางเฉพาะ: ชนิดงาน เป้าเวลา แบบบันทึกผล และรอบการทำงาน ชุดโรคเป็นคำนิยามในโค้ด การเพิ่มโรคใหม่ไม่เปลี่ยนตาราง ([ADR-0005](adr/0005-fixed-core-tables-and-disease-packs.md))

ในหน้าตั้งค่า ผู้ดูแลเปิดปิดชุดโรค แก้เป้าเวลา และแก้จำนวนวันของแต่ละรอบได้ ระบบบันทึกผู้แก้และวันที่แก้ ส่วนชนิดงานและช่องในแบบบันทึกผลแก้ได้ในโค้ดเท่านั้น

### ชุดไข้เลือดออก (รุ่นแรก)

ชุดนี้ทำตาม **มาตรการควบคุมโรคติดต่อนำโดยยุงลาย 3-3-1-7-14-21-28** ของกองโรคติดต่อนำโดยแมลง กรมควบคุมโรค

ที่มา: [รายงานพยากรณ์โรคไข้เลือดออก ปี 2563](https://ddc.moph.go.th/uploads/publish/1026820250203023324.pdf) หัวข้อ 3.2 หน้า 51 จัดทำโดยกองโรคติดต่อนำโดยแมลง สำนักงานป้องกันควบคุมโรคที่ 1–12 และสถาบันป้องกันควบคุมโรคเขตเมือง เผยแพร่มกราคม 2563 เอกสารนั้นระบุว่ารายละเอียดของบางมาตรการอาจเปลี่ยน เพราะอยู่ระหว่างการประเมินประสิทธิผล PO ยืนยันฉบับที่หน่วยงานใช้จริงก่อนเริ่มช่วงที่ 4 ของ [roadmap](roadmap.md)

#### รอบการทำงานตามมาตรการ

ตารางนี้คัดจากเอกสารต้นฉบับ วันที่ 0 คือวันที่พบผู้ป่วย

| วัน | งาน | พื้นที่ | เป้าหมายตามมาตรการ |
|---|---|---|---|
| 0 | รายงานโรคให้ รพ.สต. หรือสถานบริการสาธารณสุขในพื้นที่ทราบ | — | ภายใน 3 ชั่วโมง |
| 0 | สอบสวน ทำลายแหล่งเพาะพันธุ์ยุง และฉีดสเปรย์กระป๋องกำจัดยุงตัวเต็มวัย | บ้านผู้ป่วย | ภายใน 3 ชั่วโมงหลังได้รับรายงาน |
| 1 และ 3 | สำรวจและกำจัดลูกน้ำยุงลาย และพ่นสารเคมีกำจัดยุงตัวเต็มวัย | รัศมี 100 เมตรของบ้านผู้ป่วย และจุดที่สงสัยเป็นแหล่งโรค | — |
| 1 และ 3 | ทำประชาคม เพื่อชี้แจงสถานการณ์ ให้สุขศึกษา และกำหนดมาตรการร่วมกันในชุมชน | ชุมชน | — |
| 7 | สำรวจและกำจัดลูกน้ำยุงลาย และพ่นสารเคมีกำจัดยุงตัวเต็มวัย | รัศมี 100 เมตรของบ้านผู้ป่วย และจุดที่สงสัยเป็นแหล่งโรค | HI และ CI ในบ้านผู้ป่วยและในรัศมี 100 เมตรเป็นศูนย์ |
| 14 | สำรวจและกำจัดลูกน้ำยุงลาย | หมู่บ้านที่เกิดโรค ตำบลที่พบผู้ป่วยหลายหมู่บ้านให้ทำทั้งตำบล | HI ของหมู่บ้านที่พบผู้ป่วยไม่เกินร้อยละ 5 |
| 21 | สำรวจและกำจัดลูกน้ำยุงลาย | หมู่บ้านที่เกิดโรค | HI ของหมู่บ้านที่พบผู้ป่วยไม่เกินร้อยละ 5 และ CI ของสถานพยาบาล โรงเรียน ศาสนสถาน โรงแรม โรงงานในตำบลเป็นศูนย์ |
| 28 เป็นต้นไป | คงการสำรวจและกำจัดลูกน้ำยุงลายในชุมชนทุก 7 วันโดยชุมชนมีส่วนร่วม และคงการพ่นสารเคมีเสริมทุก 7 วันหากยังมีผู้ป่วยต่อเนื่อง | ชุมชน | — |

หมายเหตุของมาตรการ

- ถ้าพบผู้ป่วยตั้งแต่ 3 รายใน 28 วันในกลุ่มบ้านหรือหมู่บ้านเดียวกัน ให้พ่นสารเคมีทั้งกลุ่มบ้านหรือหมู่บ้านนั้น เพิ่มจากรัศมี 100 เมตร
- การพ่นในบ้านผู้ป่วยและรอบบ้านในรัศมี 100 เมตร ต้องเข้าไปพ่นภายในบ้านให้ครบทุกหลังคาเรือน

#### สิ่งที่ระบบทำ

- เมื่อเพิ่มผู้ป่วยในเหตุการณ์ไข้เลือดออก ระบบเสนองานของวันที่ 0, 1, 3, 7, 14 และ 21 พร้อมกำหนดเสร็จ ผู้ดูแลตรวจและยืนยันก่อนสร้าง
- งานควบคุมโรคของวันที่ 0, 1, 3 และ 7 ผูกกับผู้ป่วย งานทำประชาคม และงานของวันที่ 14 กับ 21 ผูกกับเหตุการณ์
- ตั้งแต่วันที่ 28 ระบบเตือนให้ผู้ดูแลเพิ่มรอบสำรวจลูกน้ำถัดไปทุก 7 วัน และเตือนเรื่องการพ่นเสริมเฉพาะเมื่อมีผู้ป่วยรายใหม่ ระบบไม่สร้างงานเอง
- เมื่อหมู่บ้านเดียวกันมีผู้ป่วยตั้งแต่ 3 รายใน 28 วัน ระบบแสดงคำเตือนตามหมายเหตุข้อแรกของมาตรการ
- งานพ่นสารเคมีแสดงหมายเหตุข้อที่สองของมาตรการเป็นคำแนะนำ
- ระบบเทียบเวลาที่ทำจริงและผลกับเป้าหมายของแต่ละรอบ ผลการเทียบมี 4 แบบ: ถึงเป้า ไม่ถึงเป้า ยังไม่ครบกำหนด และประเมินไม่ได้ (เมื่อขาดค่าที่ต้องใช้) ระบบไม่เดาค่าที่ขาด
- ระบบคำนวณ HI = บ้านที่พบลูกน้ำ ÷ บ้านที่สำรวจ × 100 และ CI = ภาชนะที่พบลูกน้ำ ÷ ภาชนะที่สำรวจ × 100 ถ้าตัวหารเป็นศูนย์ ระบบไม่แสดงค่า

#### งานและแบบบันทึกผล

| งาน | รอบ | ผูกกับผู้ป่วย | ช่องในแบบบันทึกผล |
|---|---|---|---|
| ควบคุมโรคในบ้านผู้ป่วย | วันที่ 0 | ใช่ | เวลาที่ทำ สอบสวนแล้วหรือไม่ ทำลายแหล่งเพาะพันธุ์แล้วหรือไม่ ฉีดสเปรย์แล้วหรือไม่ หมายเหตุ |
| สำรวจ กำจัดลูกน้ำ และพ่นสารเคมีรัศมี 100 เมตร | วันที่ 1, 3, 7 | ใช่ | เวลาที่ทำ จำนวนบ้านที่สำรวจ จำนวนบ้านที่พบลูกน้ำ จำนวนภาชนะที่สำรวจ จำนวนภาชนะที่พบลูกน้ำ พ่นสารเคมีหรือไม่ หน่วยงานที่พ่น จำนวนหลังคาเรือนที่พ่น |
| ทำประชาคม | วันที่ 1 ถึง 3 | ไม่ | วันที่ทำ จำนวนผู้เข้าร่วม มาตรการที่ชุมชนตกลง |
| สำรวจและกำจัดลูกน้ำในหมู่บ้าน | วันที่ 14, 21 และรอบถัดไป | ไม่ | เวลาที่ทำ จำนวนบ้านที่สำรวจ จำนวนบ้านที่พบลูกน้ำ จำนวนภาชนะที่สำรวจ จำนวนภาชนะที่พบลูกน้ำ |
| สำรวจสถานที่ในตำบล | วันที่ 21 | ไม่ | ชนิดสถานที่ จำนวนสถานที่ จำนวนภาชนะที่สำรวจ จำนวนภาชนะที่พบลูกน้ำ |

#### ข้อตีความที่ PO ต้องยืนยัน

มาตรการไม่ได้ระบุเรื่องเหล่านี้ไว้ชัด เอกสารนี้จึงเสนอวิธีที่ระบบจะทำ PO ยืนยันทั้งหมดก่อนเริ่มช่วงที่ 4 ของ roadmap

1. วันที่ 0 ใช้วันที่ผู้ป่วยได้รับการวินิจฉัย ถ้าไม่มีค่านี้ ใช้วันที่ได้รับแจ้งเหตุการณ์
2. 3 ชั่วโมงแรกเริ่มนับจากเวลาที่วินิจฉัย และจบที่เวลาที่แจ้งหน่วยบริการ
3. เมื่อหน่วยบริการเป็นผู้แจ้งเหตุการณ์เอง เวลาที่หน่วยบริการได้รับรายงานคือเวลาที่หน่วยบริการแจ้งเหตุการณ์นั้น
4. กำหนดเสร็จของงานวันที่ 1 คือ 24 ชั่วโมงหลังหน่วยบริการได้รับรายงาน ตรงกับที่[บทความของ สคร.12 สงขลา](https://he01.tci-thaijo.org/index.php/JDPC3/article/download/267722/181396/1147564)บรรยายว่า "ภายใน 1 วันหลังได้รับแจ้ง"
5. กำหนดเสร็จของงานวันที่ 3, 7, 14 และ 21 คือสิ้นวันนั้น
6. งานของวันที่ 14 และ 21 นับจากวันที่ 0 ของผู้ป่วยรายล่าสุดในหมู่บ้านนั้น
7. การสำรวจ CI ของสถานที่ในตำบลในวันที่ 21 เป็นงานแยกจากการสำรวจหมู่บ้าน
8. งานพ่นสารเคมีมอบให้หน่วยบริการเป็นผู้ประสาน หน่วยงานที่พ่นจริง เช่น องค์กรปกครองส่วนท้องถิ่น บันทึกไว้ในแบบบันทึกผล และไม่ต้องมีบัญชีในระบบ
9. การเตือนให้เพิ่มรอบทุก 7 วันหยุดเมื่อผู้ดูแลปิดเหตุการณ์
10. ระบบแนะนำให้ปิดเหตุการณ์เมื่องานถึงวันที่ 21 บันทึกผลครบ และผ่านไป 28 วันนับจากวันที่ 0 ของผู้ป่วยรายล่าสุดโดยไม่มีผู้ป่วยรายใหม่

ข้อ 4, 5 และจำนวนวันของแต่ละรอบ ผู้ดูแลแก้ได้ในหน้าตั้งค่า

#### ส่วนของมาตรการที่รุ่นแรกไม่ครอบคลุม

ผู้ดูแลยังสร้างงานเองได้ทุกกรณี แต่ระบบไม่เสนอและไม่เตือนให้

- การขยายเป็นทั้งตำบลเมื่อพบผู้ป่วยหลายหมู่บ้านในตำบลเดียวกัน
- การประเมินพื้นที่ระบาดต่อเนื่องโดยสำนักงานสาธารณสุขจังหวัด
- การดำเนินการแบบทั้งหมู่บ้านเมื่อพื้นที่ระบาดต่อเนื่องจนทำตามมาตรการรายผู้ป่วยไม่ได้

## 6. สรุปภาพรวมและการส่งออก

- ผู้ดูแลและผู้ดูเห็นสรุป: จำนวนเหตุการณ์และผู้ป่วยตามโรค เดือน และพื้นที่ สถานะงาน และร้อยละที่ถึงเป้าของชุดโรค
- ผู้ดูแลส่งออกรายการเหตุการณ์ ผู้ป่วย และงานตามช่วงวันที่เป็นไฟล์ Excel ได้ ช่องเฉพาะโรคแตกเป็นคอลัมน์
- ผู้ดูส่งออกได้เฉพาะตัวเลขสรุป
- ทุกการส่งออกบันทึกใน audit log

## 7. Dashboard สาธารณะ

เปิดดูได้โดยไม่ต้องล็อกอิน มีกฎดังนี้

- แสดงเฉพาะจำนวนเหตุการณ์และจำนวนผู้ป่วยรวมตามโรค เดือน และตำบล ไม่ลงถึงระดับหมู่บ้าน
- นับเฉพาะเหตุการณ์ที่ตรวจสอบแล้วว่าจริง คือมี `stage` เป็น `verified`, `responding` หรือ `closed`
- ช่องที่มีจำนวน 1–4 แสดงเป็น "<5"
- ยอดรวมต้องไม่ทำให้คำนวณย้อนกลับหาช่องที่ซ่อนได้
- ไม่มีรายละเอียดรายเหตุการณ์ รายผู้ป่วย ชื่อ สถานที่ หรือวันเริ่มป่วยรายคน
- คำตอบของหน้านี้เก็บ cache ไว้ เพื่อไม่ให้การเรียกถี่ ๆ ใช้โควตาของระบบ

## 8. ข้อกำหนดทั่วไป

- หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดง UUID หรือรหัสสถานะภาษาอังกฤษ
- หน้าจอของหน่วยบริการใช้งานได้บนมือถือ และแต่ละงานมีลิงก์ของตัวเอง
- การบันทึกทุกครั้งกันการส่งซ้ำ กดปุ่มซ้ำหรือสัญญาณหลุดแล้วส่งใหม่ต้องไม่สร้างรายการซ้ำ
- หลังบันทึกสำเร็จ หน้าจอแสดงข้อมูลล่าสุดทันที ผู้ใช้ไม่ต้องโหลดใหม่เอง
- หน้าจอหลักแต่ละหน้าโหลดข้อมูลด้วยคำขอเดียว เป้าหมายคือพร้อมใช้ภายใน 3 วินาทีบนมือถือ ค่านี้เป็นเป้าที่ต้องวัดจริงตั้งแต่ช่วงที่ 0 ของ roadmap ยังไม่ใช่ผลที่พิสูจน์แล้ว
- ปุ่มที่ผู้ใช้ไม่มีสิทธิ์จะไม่แสดง
- ชื่อปุ่มบอกทั้งการกระทำและสิ่งที่ถูกกระทำ เช่น "ปิดเหตุการณ์" และการกระทำที่ต่างกันใช้คำต่างกัน
- การกระทำที่มีผลมาก เช่น ปิดเหตุการณ์ หรือยกเลิก มีหน้าต่างยืนยันแยกที่บอกผลที่จะเกิด ปุ่มยืนยันไม่ใช้ปุ่มเดียวกับปุ่มบันทึก
- คำที่แสดงบนหน้าจอใช้ตาม [`GLOSSARY.md`](../GLOSSARY.md)
- ข้อมูลไม่ถูกลบ
- สำรองไฟล์ฐานข้อมูลอัตโนมัติทุกสัปดาห์ เก็บย้อนหลัง 8 ชุด
- Log ของระบบไม่มีชื่อผู้ป่วย ข้อความบรรยายเหตุการณ์ หรือ token

### ความปลอดภัย

- server ตรวจค่าที่รับเข้าทุกช่อง ทั้งชนิด ความยาว และค่าที่อนุญาต โดยไม่พึ่งการตรวจของหน้าเว็บ
- ค่าที่ผู้ใช้กรอกไม่ถูกตีความเป็นสูตร ทั้งในไฟล์ฐานข้อมูลและไฟล์ที่ส่งออก
- หน้าเว็บโหลดสคริปต์จากที่อยู่ของตัวเองและจากบริการเข้าสู่ระบบของ Google เท่านั้น และไม่ยอมให้เว็บอื่นฝังหน้าไว้ในกรอบ
- เมื่อผู้ดูแลเปิดหน้าตั้งค่า ระบบตรวจว่าไฟล์ฐานข้อมูลและโฟลเดอร์รูปถ่ายไม่ได้ถูกแชร์ออกไป และเตือนเมื่อพบการแชร์
- เมื่อเกิดข้อผิดพลาด ผู้ใช้เห็นข้อความภาษาไทยพร้อมรหัสอ้างอิง ซึ่งใช้ค้นใน log ได้

### ข้อจำกัดที่ทราบ

- ต้องมีอินเทอร์เน็ต รุ่นแรกยังบันทึกแบบออฟไลน์ไม่ได้
- ทั้งระบบพึ่งบริการของ Google ถ้า Google ขัดข้อง ระบบใช้ไม่ได้
- API ของ Apps Script มองไม่เห็น IP ของผู้เรียก จึงจำกัดการเรียกถี่ ๆ เป็นราย IP ไม่ได้ ระบบลดผลกระทบด้วยการปฏิเสธคำขอที่ไม่มี session ก่อนอ่านฐานข้อมูล และ cache คำตอบสาธารณะ
- ทั้งระบบรับคำขอพร้อมกันได้จำกัด ([`schema.md` ข้อ 7](schema.md#7-ขนาดที่ออกแบบรองรับ)) การเรียกถี่ ๆ จากภายนอกจึงทำให้ผู้ใช้จริงใช้งานไม่ได้ชั่วคราว
- session token เก็บในเบราว์เซอร์ของผู้ใช้ เพราะ Apps Script ตั้ง cookie ที่สคริปต์อ่านไม่ได้ให้ไม่ได้ ระบบลดความเสี่ยงด้วยข้อจำกัดการโหลดสคริปต์ในหัวข้อความปลอดภัย
- ข้อมูลอยู่ในบัญชี Gmail ส่วนตัวของ PO ซึ่ง PO ยอมรับความเสี่ยงแล้ว ([ADR-0001](adr/0001-rebuild-on-apps-script-and-sheets.md))

## 10. เกณฑ์ยอมรับของรุ่นแรก

รุ่นแรกผ่านเมื่อทำเส้นทางนี้ได้ครบด้วยข้อมูลสมมติ บนระบบที่ deploy จริง

1. ผู้ดูแลเพิ่มหน่วยบริการ หมู่บ้าน และผู้ใช้ของหน่วยบริการ
2. หน่วยบริการเปิดลิงก์จาก LINE บนมือถือ ล็อกอินด้วย Google และแจ้งเหตุการณ์ไข้เลือดออก
3. ผู้ดูแลเห็นเรื่องในงานวันนี้ ตรวจสอบ ประเมินเกณฑ์ เพิ่มผู้ป่วย และมอบหมายงานของชุดไข้เลือดออก
4. หน่วยบริการรับงาน บันทึกผลพร้อมรูป และระบบแสดงผลการเทียบเป้าของแต่ละรอบ
5. หน่วยบริการอีกแห่งเปิดลิงก์ของงานนั้นไม่ได้ และไม่เห็นเหตุการณ์นั้น
6. ผู้ดูเห็นเหตุการณ์ ผู้ป่วย งาน ผล และรูปถ่ายเท่ากับผู้ดูแล และทุกคำขอแก้ไขจากผู้ดูถูกปฏิเสธ
7. Dashboard สาธารณะแสดงตัวเลขระดับตำบล และซ่อนช่องที่ต่ำกว่า 5
8. ผู้ดูแลส่งออก Excel ปิดเหตุการณ์ และเปิดใหม่ได้
9. หน่วยบริการ 1–2 แห่งทดลองใช้ด้วยข้อมูลสมมติ และ PO ยืนยันผล

การเริ่มใช้ข้อมูลจริงเป็นการอนุมัติแยกของ PO หลังข้อ 9 ([roadmap ช่วงที่ 6](roadmap.md))

## 11. ข้อเสนอที่รอ PO ยืนยัน

เรื่องเหล่านี้ PO ยังไม่ได้ตัดสินโดยตรง เอกสารชุดนี้ใส่วิธีที่เสนอไว้เพื่อให้ระบบครบ แต่ละข้อต้องได้รับการยืนยันก่อนเริ่มช่วงของ roadmap ที่ระบุ

| ข้อเสนอ | ยืนยันก่อน |
|---|---|
| ผู้ดูแลยกเลิกเหตุการณ์ที่บันทึกผิดได้ โดยระบุเหตุผล เหตุการณ์เปลี่ยนเป็นสถานะยกเลิก (`void`) และข้อมูลไม่ถูกลบ | ช่วงที่ 2 |
| ผู้ดูแลแก้ผลการตรวจสอบของเหตุการณ์ที่บันทึกว่าไม่จริงได้ โดยระบุเหตุผล | ช่วงที่ 2 |
| หน่วยบริการแก้เรื่องที่ตนแจ้งไม่ได้หลังส่ง ผู้ดูแลเป็นผู้แก้ข้อมูลของเหตุการณ์ | ช่วงที่ 3 |
| ผู้ดูแลยกเลิกงานได้ โดยระบุเหตุผล งานเปลี่ยนเป็นสถานะยกเลิก (`cancelled`) และหน่วยบริการเลิกเห็นเหตุการณ์จากงานนั้น | ช่วงที่ 3 |
| หน่วยบริการเห็นเหตุการณ์จากการแจ้งเองหรือการได้รับมอบหมายงานเท่านั้น การเป็นหน่วยที่รับผิดชอบหมู่บ้านไม่ได้ทำให้เห็นเหตุการณ์ในหมู่บ้านนั้นเอง | ช่วงที่ 3 |
| ชนิดงานกลางสำหรับโรคที่ไม่มีชุดโรค: สอบสวนโรค ควบคุมโรค ติดตามผู้สัมผัส และอื่น ๆ ใช้แบบบันทึกผลกลางที่มีเวลาที่ทำ สรุปผล และหมายเหตุ | ช่วงที่ 3 |
| ข้อตีความ 10 ข้อของชุดไข้เลือดออก และฉบับของมาตรการที่ใช้ (ข้อ 5) | ช่วงที่ 4 |
| ไม่ทำคลังเอกสารสาธารณะและสถิติการเข้าชมของระบบเก่า | ช่วงที่ 5 |
| หน้าจอของผู้ดูแลและผู้ดูออกแบบสำหรับคอมพิวเตอร์ที่สำนักงานเป็นหลัก และใช้บนมือถือได้ | ช่วงที่ 2 |
| ขนาดที่ออกแบบรองรับ ([`schema.md` ข้อ 7](schema.md#7-ขนาดที่ออกแบบรองรับ)) | ช่วงที่ 2 |
| ช่องข้อมูลของเหตุการณ์และผู้ป่วยครบตามที่ สสอ. ต้องใช้รายงานต่อหรือไม่ ระบบเก่ามีช่องที่ v2 ยังไม่มี เช่น ประเภทเหตุการณ์ การประเมินความเสี่ยง และหน่วยงานที่แจ้งเตือน | ช่วงที่ 2 |
| นิยามของตัวชี้วัดในหน้าสรุป เช่น ความครบถ้วนของการสอบสวน ยังไม่มีข้อเสนอ | ช่วงที่ 5 |
| ผู้ดูส่งออกได้เฉพาะตัวเลขสรุป และไม่เห็นหน้าตั้งค่า การจัดการผู้ใช้ กับบันทึกความปลอดภัย | ช่วงที่ 5 |
