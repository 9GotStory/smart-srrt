## 1. ระบบนี้คืออะไร

Smart SRRT v2 คือระบบติดตามเหตุการณ์โรคและภัยสุขภาพของ **สำนักงานสาธารณสุขอำเภอ (สสอ.) หนึ่งแห่ง** ใช้ตั้งแต่รับแจ้งข่าว ตรวจสอบ มอบหมายงานให้ รพ.สต. ลงพื้นที่ รับผลกลับ ติดตาม จนปิดเหตุการณ์

ระบบนี้ไม่ใช่ระบบเวชระเบียน ไม่ใช่เครื่องมือวินิจฉัย และไม่ได้เชื่อมกับระบบรายงานของกระทรวง ข้อมูลที่ต้องส่งต่อหน่วยงานอื่นใช้การส่งออกไฟล์

### ปัญหาของระบบเดิมที่ v2 ต้องแก้

| ระบบเดิม | v2 |
|---|---|
| สถานะของเหตุการณ์คำนวณจากช่องในฟอร์มยาวหนึ่งฟอร์ม ผู้ใช้ไม่รู้ว่าขั้นถัดไปคืออะไร | ทุกขั้นเป็นปุ่มที่กดได้ และบันทึกลงไทม์ไลน์ของเหตุการณ์ |
| มอบหมายงานได้เฉพาะผู้ใช้ที่ล็อกอิน แต่คนลงพื้นที่คือ รพ.สต. ที่ไม่ได้ล็อกอิน | มอบหมายงานให้ รพ.สต. เป็นหน่วย และ รพ.สต. ล็อกอินมาบันทึกผลเอง |
| โมดูลไข้เลือดออก (D331) แยกตาราง แยกสิทธิ์ และไม่เขียนผลกลับไปที่เหตุการณ์ | ทุกโรคอยู่ในเหตุการณ์เดียว ขั้นตอนเฉพาะโรคเป็น "ชุดโรค" ที่เพิ่มได้โดยไม่แก้ตาราง |
| ไม่มีส่วนที่เกี่ยวกับ LINE ซึ่งเป็นช่องทางประสานงานจริง | ระบบเตรียมข้อความ LINE พร้อมลิงก์ไปที่งาน ผู้ใช้กดส่งเอง |
| หน้าจอแสดงรหัส UUID และสถานะภาษาอังกฤษ | หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดงรหัสภายใน |

## 2. ผู้ใช้

| บทบาท (`role`) | ใคร | ทำอะไรได้ |
|---|---|---|
| ผู้ดูแล (`admin`) | เจ้าหน้าที่ สสอ. มีได้มากกว่าหนึ่งคน | ทุกอย่าง: รับแจ้ง ตรวจสอบ ประเมินเกณฑ์ มอบหมายงาน รับผล ปิดเหตุการณ์ จัดการผู้ใช้ หน่วยงาน หมู่บ้าน และค่าตั้งระบบ |
| รพ.สต. (`unit`) | เจ้าหน้าที่ รพ.สต. แต่ละคนผูกกับหน่วยหนึ่งแห่ง | แจ้งเหตุการณ์ รับงานที่มอบหมายให้หน่วยของตน บันทึกผล แนบรูป เห็นเฉพาะเรื่องที่หน่วยของตนแจ้งหรือได้รับมอบหมาย |
| ผู้ดู (`viewer`) | เช่น สาธารณสุขอำเภอ | เปิดดูเหตุการณ์ สถานะงาน และตัวเลขสรุป แก้ไขไม่ได้ ไม่เห็นชื่อและบ้านเลขที่ของผู้ป่วย |
| บุคคลทั่วไป | ไม่ล็อกอิน | เห็นเฉพาะ Dashboard สาธารณะ (ข้อ 7) |

กฎการมองเห็นทั้งหมดบังคับที่ server หน้าจอซ่อนปุ่มเพื่อความสะดวกเท่านั้น ตารางสิทธิ์ละเอียดอยู่ใน [`schema.md` ข้อ 6](schema.md#6-กฎสิทธิ์การมองเห็น)

### การเข้าสู่ระบบ

- เข้าสู่ระบบด้วยบัญชี Google เท่านั้น ระบบไม่เก็บรหัสผ่าน
- ผู้ดูแลเพิ่มผู้ใช้ด้วยชื่อ อีเมล Google บทบาท และหน่วยงาน ไม่มีหน้าสมัครเอง
- อีเมลที่ไม่อยู่ในตารางผู้ใช้ หรือบัญชีที่ถูกระงับ เข้าระบบไม่ได้
- เครื่องหนึ่งเครื่องอยู่ในระบบได้ 7 วัน แล้วต้องยืนยันกับ Google ใหม่
- ผู้ดูแลระงับบัญชีได้ บัญชีที่ถูกระงับถูกปฏิเสธตั้งแต่คำขอถัดไปบนทุกเครื่อง
- ผู้ดูแลสั่งให้บัญชีใดก็ได้ออกจากระบบบนทุกเครื่องได้ เช่น เมื่อมือถือหาย

## 3. ขั้นตอนของเหตุการณ์

เหตุการณ์หนึ่งรายการคือเรื่องที่ได้รับแจ้งหนึ่งเรื่อง เช่น "ไข้เลือดออก หมู่ 5 ตำบล ก" เหตุการณ์มีผู้ป่วยได้หลายราย และมีงานที่มอบหมายได้หลายงาน

```
รับแจ้ง → ตรวจสอบข่าว → ประเมินเกณฑ์ → มอบหมายงาน → รับผล → ติดตาม → ปิดเหตุการณ์
```

| ขั้น | ใครทำ | ผลที่เกิด | สถานะหลังทำ (`stage`) |
|---|---|---|---|
| รับแจ้ง | ผู้ดูแล หรือ รพ.สต. | สร้างเหตุการณ์ใหม่ | รอตรวจสอบ (`received`) |
| ตรวจสอบข่าว | ผู้ดูแล | บันทึกวิธีตรวจสอบและผล | ตรวจสอบแล้วจริง (`verified`) หรือ ตรวจสอบแล้วไม่จริง (`not_confirmed`) |
| ประเมินเกณฑ์ | ผู้ดูแล | บันทึกว่าเข้าเกณฑ์สอบสวนโรคหรือไม่ | กำลังดำเนินการ (`responding`) |
| มอบหมายงาน | ผู้ดูแล | สร้างงานให้ รพ.สต. พร้อมกำหนดเสร็จ และเตรียมข้อความ LINE | ไม่เปลี่ยน |
| รับงานและบันทึกผล | รพ.สต. | บันทึกเวลาที่ทำจริง ผล และรูปถ่าย | ไม่เปลี่ยน |
| รับผล | ผู้ดูแล | ทำเครื่องหมายว่าตรวจผลแล้ว | ไม่เปลี่ยน |
| ปิดเหตุการณ์ | ผู้ดูแล | บันทึกสรุป ระบบเตือนถ้ายังมีงานค้าง | ปิดแล้ว (`closed`) |
| เปิดใหม่ | ผู้ดูแล | ต้องระบุเหตุผล | กำลังดำเนินการ (`responding`) |
| ยกเลิก | ผู้ดูแล | ใช้เมื่อบันทึกผิด ต้องระบุเหตุผล ข้อมูลไม่ถูกลบ | ยกเลิก (`void`) |

กฎของขั้นตอน

- ทุกการกระทำเพิ่มหนึ่งแถวในไทม์ไลน์ของเหตุการณ์ พร้อมผู้ทำ เวลาที่ทำจริง และเวลาที่บันทึก
- เวลาที่ทำจริงผู้ใช้กรอกเอง มีทั้งวันที่และเวลา เวลาที่บันทึกระบบใส่ให้ หน้าจอแสดงให้เห็นเมื่อสองค่านี้ห่างกันมาก เพื่อให้รู้ว่าเป็นการบันทึกย้อนหลัง
- ระบบไม่ปิดเหตุการณ์เอง สำหรับเหตุการณ์ที่มีชุดโรค ระบบแนะนำให้ปิดเมื่อครบรอบติดตามและไม่มีผู้ป่วยรายใหม่
- การแก้ไขข้อมูลตรวจค่า revision ก่อนบันทึก ถ้ามีคนแก้ไปก่อน ระบบปฏิเสธและให้โหลดข้อมูลใหม่
- ผู้ดูแลแก้ผลการตรวจสอบของเหตุการณ์ที่บันทึกว่าไม่จริงได้ โดยต้องระบุเหตุผล
- รพ.สต. แก้เรื่องที่ตนแจ้งไม่ได้หลังส่ง ผู้ดูแลเป็นผู้แก้ข้อมูลของเหตุการณ์

### ผู้ป่วยในเหตุการณ์

- ผู้ดูแลเพิ่มผู้ป่วยทีละราย ผู้ป่วยรายใหม่ในพื้นที่และช่วงเวลาเดียวกันเพิ่มเข้าเหตุการณ์เดิม
- ข้อมูลที่เก็บ: ชื่อ-สกุล อายุ เพศ บ้านเลขที่ หมู่บ้าน วันเริ่มป่วย การวินิจฉัย เวลาที่วินิจฉัย สถานที่รักษา
- ระบบไม่เก็บเลขบัตรประชาชนและ HN
- ชื่อและบ้านเลขที่เห็นได้เฉพาะผู้ดูแล และ รพ.สต. ที่ได้รับมอบหมายงานของผู้ป่วยรายนั้น

### งานที่มอบหมาย

- งานหนึ่งงานผูกกับเหตุการณ์เสมอ และเลือกผูกกับผู้ป่วยรายใดรายหนึ่งได้
- ระบบเสนอ รพ.สต. ที่รับผิดชอบหมู่บ้านของเหตุการณ์หรือของผู้ป่วยให้อัตโนมัติ ผู้ดูแลเปลี่ยนได้
- งานมีชนิด คำสั่งเพิ่มเติม กำหนดเสร็จ และสถานะ: มอบหมายแล้ว (`assigned`) → รับงานแล้ว (`accepted`) → รายงานผลแล้ว (`done`) หรือ ยกเลิก (`cancelled`)
- ชนิดงานกลางที่ใช้ได้ทุกโรค: สอบสวนโรค ควบคุมโรค ติดตามผู้สัมผัส อื่น ๆ ชุดโรคเพิ่มชนิดงานของตัวเองได้ (ข้อ 5)

## 4. หน้าจอหลัก

### ผู้ดูแล: "งานวันนี้"

หน้าแรกเป็นรายการสิ่งที่ต้องทำ เรียงตามความเร่งด่วน แต่ละรายการมีปุ่มเดียวสำหรับขั้นถัดไป

1. เหตุการณ์ที่รอตรวจสอบ
2. เหตุการณ์ที่รอประเมินเกณฑ์
3. เหตุการณ์ที่เข้าเกณฑ์แต่ยังไม่ได้มอบหมายงาน
4. งานที่เกินกำหนด และงานที่ใกล้ครบกำหนด พร้อมจำนวนวันที่ค้าง และปุ่มเตรียมข้อความ LINE เพื่อติดตาม
5. ผลจาก รพ.สต. ที่ยังไม่ได้ตรวจ
6. เหตุการณ์ที่ไม่มีงานค้างแล้ว รอปิด

หน้าอื่น: รายการเหตุการณ์ทั้งหมดพร้อมตัวกรอง หน้าเหตุการณ์ (ข้อมูล ผู้ป่วย งาน ไทม์ไลน์) สรุปภาพรวม ส่งออกข้อมูล ตั้งค่า (ผู้ใช้ หน่วยงาน หมู่บ้าน รายการโรค เป้าเวลาของชุดโรค ชื่อและโลโก้หน่วยงาน)

### รพ.สต.: "งานของหน่วย"

ออกแบบสำหรับมือถือเป็นหลัก เพราะเปิดจากลิงก์ใน LINE

1. งานที่ต้องทำ เรียงตามกำหนดเสร็จ
2. ปุ่ม "แจ้งเหตุการณ์"
3. เรื่องที่หน่วยของตนแจ้งไว้ และสถานะปัจจุบัน

หน้างาน: รายละเอียดงาน ข้อมูลผู้ป่วยที่เกี่ยวข้อง ปุ่มรับงาน แบบบันทึกผล และช่องแนบรูป

### ข้อความ LINE

ระบบไม่ส่งข้อความเอง ระบบเตรียมข้อความ แล้วผู้ใช้กด "คัดลอก" หรือ "เปิด LINE" เพื่อเลือกกลุ่มและส่ง

- ผู้ดูแลได้ข้อความหลังมอบหมายงาน และเมื่อต้องการติดตามงานค้าง
- รพ.สต. ได้ข้อความหลังแจ้งเหตุการณ์หรือบันทึกผล เพื่อแจ้ง สสอ.
- ข้อความมี: โรค หมู่บ้าน งานที่ต้องทำ กำหนดเสร็จ และลิงก์ไปที่งานหรือเหตุการณ์
- ข้อความไม่มีชื่อผู้ป่วยและบ้านเลขที่ ผู้รับต้องเปิดลิงก์และล็อกอินจึงจะเห็น
- เมื่อผู้ดูแลกดยืนยันว่าส่งแล้ว ระบบบันทึกเวลาที่แจ้ง รพ.สต. ไว้ที่งาน ค่าตั้งต้นคือเวลาที่กดยืนยัน ผู้ดูแลแก้ได้เมื่อแจ้งไว้ก่อนหน้าด้วยช่องทางอื่น เช่น โทรศัพท์

### รูปถ่าย

- แนบได้เฉพาะรูปถ่ายของงานในพื้นที่ เช่น การพ่นสารเคมี หรือภาชนะที่พบลูกน้ำ ไม่รับไฟล์เอกสาร
- หน้าแนบรูปและช่องข้อความอิสระทุกช่องมีคำเตือน: ห้ามถ่ายเอกสารที่มีชื่อผู้ป่วย และห้ามถ่ายใบหน้าผู้ป่วย
- ระบบย่อรูปในเครื่องของผู้ใช้ก่อนส่ง
- รูปเก็บใน Google Drive โฟลเดอร์ส่วนตัวของระบบ ไม่มีลิงก์สาธารณะ เปิดดูได้ผ่านระบบตามสิทธิ์เท่านั้น

## 5. ชุดโรค

ทุกโรคใช้ขั้นตอนในข้อ 3 เหมือนกัน **ชุดโรค** (disease pack) เพิ่มสามอย่างให้โรคที่มีแนวทางเฉพาะ: ชนิดงาน เป้าเวลา และแบบบันทึกผล ชุดโรคเป็นคำนิยามในโค้ด การเพิ่มโรคใหม่ไม่เปลี่ยนตาราง ([ADR-0005](adr/0005-fixed-core-tables-and-disease-packs.md))

ผู้ดูแลเปิดปิดชุดโรคและแก้เป้าเวลาได้ในหน้าตั้งค่า ระบบบันทึกผู้แก้และวันที่แก้

### ชุดไข้เลือดออก (รุ่นแรก)

เป้าเวลาตั้งต้นตามมาตรการ 3-3-1

| เป้า | เริ่มนับจาก | ถึง | ค่าตั้งต้น |
|---|---|---|---|
| แจ้ง รพ.สต. ในพื้นที่ | เวลาที่ผู้ป่วยได้รับการวินิจฉัย | เวลาที่แจ้ง รพ.สต. | 3 ชั่วโมง |
| ควบคุมยุงพาหะในบ้านผู้ป่วย (พ่นสเปรย์ กำจัดแหล่งน้ำขัง) | เวลาที่ รพ.สต. ได้รับแจ้ง | เวลาที่ทำจริง | 3 ชั่วโมง |
| ควบคุมยุงพาหะในรัศมี 100 เมตรจากบ้านผู้ป่วยและจุดที่สงสัยเป็นแหล่งโรค | เวลาที่ รพ.สต. ได้รับแจ้ง | เวลาที่ทำจริง | 1 วัน |

ที่มาของค่าตั้งต้น: บทความของ สคร.12 สงขลา ใน[วารสารโรคและภัยสุขภาพ สคร.3 ปีที่ 18 ฉบับที่ 1 (2567)](https://he01.tci-thaijo.org/index.php/JDPC3/article/download/267722/181396/1147564) และ[รายงานวิจัยของกรมควบคุมโรค](https://ddc.moph.go.th/uploads/ckeditor2//files/19.ศศิธร.pdf) ซึ่งอ้างกองโรคติดต่อนำโดยแมลง (2564) ทั้งสองเป็นแหล่งทุติยภูมิ **ยังไม่ได้ตรวจกับแนวทางต้นฉบับของกองโรคติดต่อนำโดยแมลง** และสองแหล่งนี้บรรยายขอบเขตของ "3 ชั่วโมงที่สอง" ต่างกันเล็กน้อย (ในบ้านผู้ป่วย เทียบกับรัศมี 100 เมตร) ตารางนี้ใช้ตามบทความแรก

งานและแบบบันทึกผลของชุดนี้

| งาน | ผูกกับผู้ป่วย | ช่องในแบบบันทึกผล |
|---|---|---|
| ควบคุมยุงพาหะในบ้านผู้ป่วย | ใช่ | เวลาที่ทำ สิ่งที่ทำ (พ่นสเปรย์ กำจัดแหล่งน้ำขัง) หมายเหตุ |
| ควบคุมยุงพาหะรัศมี 100 เมตร | ใช่ | เวลาที่ทำ หน่วยงานที่พ่น จำนวนหลังคาเรือน หมายเหตุ |
| สำรวจลูกน้ำยุงลาย | ไม่บังคับ | เวลาที่สำรวจ จำนวนบ้านที่สำรวจ จำนวนบ้านที่พบลูกน้ำ จำนวนภาชนะที่สำรวจ จำนวนภาชนะที่พบลูกน้ำ |

- ระบบคำนวณ HI = บ้านที่พบลูกน้ำ ÷ บ้านที่สำรวจ × 100 และ CI = ภาชนะที่พบลูกน้ำ ÷ ภาชนะที่สำรวจ × 100 ถ้าตัวหารเป็นศูนย์ ระบบไม่แสดงค่า
- รอบสำรวจลูกน้ำติดตาม ค่าตั้งต้นคือวันที่ 3, 7, 14, 21 และ 28 นับจากวันที่ รพ.สต. ได้รับแจ้ง **ทั้งจำนวนวันและจุดเริ่มนับยังไม่มีแหล่งอ้างอิง** เป็นค่าที่เสนอให้ PO ยืนยัน และผู้ดูแลแก้ได้
- เมื่อ รพ.สต. เป็นผู้แจ้งเหตุการณ์เอง เวลาที่ รพ.สต. ได้รับแจ้งคือเวลาที่ รพ.สต. แจ้งเหตุการณ์นั้น
- งานควบคุมยุงพาหะรัศมี 100 เมตรมอบให้ รพ.สต. เป็นผู้ประสาน หน่วยงานที่พ่นจริง เช่น องค์กรปกครองส่วนท้องถิ่น บันทึกไว้ในแบบบันทึกผล และไม่ต้องมีบัญชีในระบบ
- ผลการเทียบเป้ามี 4 แบบ: ทันเป้า เกินเป้า ยังไม่ครบกำหนด และประเมินไม่ได้ (เมื่อขาดเวลาที่ต้องใช้คำนวณ) ระบบไม่เดาค่าที่ขาด

## 6. สรุปภาพรวมและการส่งออก

- ผู้ดูแลและผู้ดูเห็นสรุป: จำนวนเหตุการณ์และผู้ป่วยตามโรค เดือน และพื้นที่ สถานะงาน และร้อยละที่ทันเป้าของชุดโรค
- ผู้ดูแลส่งออกรายการเหตุการณ์ ผู้ป่วย และงานตามช่วงวันที่เป็นไฟล์ Excel ได้ ช่องเฉพาะโรคแตกเป็นคอลัมน์
- ผู้ดูส่งออกได้เฉพาะตัวเลขสรุป
- ทุกการส่งออกบันทึกใน audit log

## 7. Dashboard สาธารณะ

เปิดดูได้โดยไม่ต้องล็อกอิน มีกฎดังนี้

- แสดงเฉพาะจำนวนเหตุการณ์และจำนวนผู้ป่วยรวมตามโรค เดือน และตำบล ไม่ลงถึงระดับหมู่บ้าน
- นับเฉพาะเหตุการณ์ที่ตรวจสอบแล้วว่าจริง (`verified`, `responding`, `closed`)
- ช่องที่มีจำนวน 1–4 แสดงเป็น "<5"
- ยอดรวมต้องไม่ทำให้คำนวณย้อนกลับหาช่องที่ซ่อนได้
- ไม่มีรายละเอียดรายเหตุการณ์ รายผู้ป่วย ชื่อ สถานที่ หรือวันเริ่มป่วยรายคน
- คำตอบของหน้านี้เก็บ cache ไว้ เพื่อไม่ให้การเรียกถี่ ๆ ใช้โควตาของระบบ

## 8. ข้อกำหนดทั่วไป

- หน้าจอเป็นภาษาไทยทั้งหมด ไม่แสดง UUID หรือรหัสสถานะภาษาอังกฤษ
- หน้าจอของ รพ.สต. ใช้งานได้บนมือถือ และแต่ละงานมีลิงก์ของตัวเอง
- การบันทึกทุกครั้งกันการส่งซ้ำ กดปุ่มซ้ำหรือสัญญาณหลุดแล้วส่งใหม่ต้องไม่สร้างรายการซ้ำ
- หลังบันทึกสำเร็จ หน้าจอแสดงข้อมูลล่าสุดทันที ผู้ใช้ไม่ต้องโหลดใหม่เอง
- ปุ่มที่ผู้ใช้ไม่มีสิทธิ์จะไม่แสดง
- ข้อมูลไม่ถูกลบ การยกเลิกเปลี่ยนสถานะเป็นยกเลิกและเก็บแถวเดิมไว้
- สำรองไฟล์ฐานข้อมูลอัตโนมัติทุกสัปดาห์ เก็บย้อนหลัง 8 ชุด
- Log ของระบบไม่มีชื่อผู้ป่วย ข้อความบรรยายเหตุการณ์ หรือ token

### ข้อจำกัดที่ทราบ

- ต้องมีอินเทอร์เน็ต รุ่นแรกยังบันทึกแบบออฟไลน์ไม่ได้
- ทั้งระบบพึ่งบริการของ Google ถ้า Google ขัดข้อง ระบบใช้ไม่ได้
- API ของ Apps Script มองไม่เห็น IP ของผู้เรียก จึงจำกัดการเรียกถี่ ๆ เป็นราย IP ไม่ได้ ระบบลดผลกระทบด้วยการปฏิเสธคำขอที่ไม่มี session ก่อนอ่านฐานข้อมูล และ cache คำตอบสาธารณะ
- ข้อมูลอยู่ในบัญชี Gmail ส่วนตัวของ PO ซึ่ง PO ยอมรับความเสี่ยงแล้ว ([ADR-0001](adr/0001-rebuild-on-apps-script-and-sheets.md))

## 10. เกณฑ์ยอมรับของรุ่นแรก

รุ่นแรกผ่านเมื่อทำเส้นทางนี้ได้ครบด้วยข้อมูลสมมติ บนระบบที่ deploy จริง

1. ผู้ดูแลเพิ่ม รพ.สต. หมู่บ้าน และผู้ใช้ของ รพ.สต.
2. รพ.สต. เปิดลิงก์จาก LINE บนมือถือ ล็อกอินด้วย Google และแจ้งเหตุการณ์ไข้เลือดออก
3. ผู้ดูแลเห็นเรื่องในงานวันนี้ ตรวจสอบ ประเมินเกณฑ์ เพิ่มผู้ป่วย และมอบหมายงานของชุดไข้เลือดออก
4. รพ.สต. รับงาน บันทึกผลพร้อมรูป และระบบแสดงผลการเทียบเป้า 3-3-1
5. รพ.สต. อีกแห่งเปิดลิงก์ของงานนั้นไม่ได้ และไม่เห็นเหตุการณ์นั้น
6. ผู้ดูเห็นเหตุการณ์และสรุป แต่ไม่เห็นชื่อและบ้านเลขที่
7. Dashboard สาธารณะแสดงตัวเลขระดับตำบล และซ่อนช่องที่ต่ำกว่า 5
8. ผู้ดูแลส่งออก Excel ปิดเหตุการณ์ และเปิดใหม่ได้
9. รพ.สต. 1–2 แห่งทดลองใช้ด้วยข้อมูลสมมติ และ PO ยืนยันผล

การเริ่มใช้ข้อมูลจริงเป็นการอนุมัติแยกของ PO หลังข้อ 9 ([roadmap ช่วงที่ 6](roadmap.md))
