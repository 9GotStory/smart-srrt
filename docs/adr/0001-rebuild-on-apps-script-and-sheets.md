# ADR-0001: สร้างใหม่ทั้งหมดบน Apps Script และ Google Sheets เดิม

* สถานะ: Accepted (PO อนุมัติผ่านการ Merge ของ PR #276)
* วันที่: 2026-11-16
* แก้ไข: 2026-11-17 เพิ่มหัวข้อ "ปรับเมื่อ 17 พฤศจิกายน 2026" เมื่อลงรายละเอียดการสำรองและการเริ่มใช้ข้อมูลจริง ตาม[ผลการค้น](../research/backup-environment-facts.md)

## บริบท

การทดสอบระบบเก่าบน browser เมื่อ 12 พฤศจิกายน 2026 ผ่านทุกข้อในด้านการทำงาน แต่ Product Owner (PO) พบว่าหน้าจอใช้งานไม่ได้จริง สาเหตุอยู่ที่โครงสร้าง ไม่ใช่ที่หน้าจออย่างเดียว

- สถานะของเหตุการณ์คำนวณจากช่องในฟอร์มยาวหนึ่งฟอร์ม ไม่มีขั้นตอนให้กด
- ระบบมอบหมายงานให้ได้เฉพาะผู้ใช้ที่ล็อกอิน แต่คนลงพื้นที่คือ รพ.สต.
- โมดูลไข้เลือดออก (D331) มี 7 ตารางและสิทธิ์รายเหตุการณ์ของตัวเอง อ่านข้อมูลเหตุการณ์ทางเดียว และทำให้ต้องบันทึกเรื่องเดียวกันสองที่
- การอนุมัติหลายชั้นของ D331 ออกแบบสำหรับองค์กรที่มีหลายฝ่ายลงนาม แต่ PO เป็นทั้งเจ้าของระบบและผู้ใช้งาน

PO ยืนยันว่าระบบยังอยู่ในช่วงพัฒนาและยังไม่มีข้อมูลจริง เอกสารของระบบเก่าระบุว่าไม่มีชุดใช้งานจริง

## การตัดสินใจ

1. สร้างโครงสร้างข้อมูล server และหน้าเว็บใหม่ทั้งหมด ตาม [`../spec.md`](../spec.md) และ [`../schema.md`](../schema.md)
2. ใช้ Google Apps Script และ Google Sheets เป็น backend ต่อ ในบัญชี Gmail ส่วนตัวของ PO
3. ใช้ Apps Script project และไฟล์ Sheet เดิม ก่อนใช้ ให้คัดลอกไฟล์ Sheet เป็นชุดสำรอง ลบแท็บของระบบเก่า และเก็บเฉพาะข้อมูลที่ใช้ต่อ
4. ไม่ย้ายเหตุการณ์และผู้ใช้จากระบบเก่า
5. เขียนใน repository เดิม ทำ tag `legacy-v1` ที่ commit สุดท้ายของระบบเก่า แล้วลบโค้ด การทดสอบ เครื่องมือ CI และเอกสารของระบบเก่าออกจากสาขาหลัก ใน PR เดียวกับเอกสารชุดนี้
6. ยกเลิกงาน D331 F04–F08 และการตัดสินใจที่ค้างของ D331 (D2/P1/P2/S1/S2/C1/C2)

## ผลที่ตามมา

- ระบบเก่าหยุดให้บริการเมื่อ deploy ระบบใหม่ครั้งแรก กู้คืนได้จากประวัติเวอร์ชันของ Apps Script และ tag `legacy-v1`
- ไม่มีค่าใช้จ่ายเพิ่ม และไม่มีเซิร์ฟเวอร์ให้ดูแล
- ข้อจำกัดของ Apps Script ยังอยู่: คำขอหนึ่งครั้งใช้เวลาเป็นวินาที และมีโควตารายวันของบัญชี
- **ความเสี่ยงที่ PO ยอมรับเมื่อ 16 พฤศจิกายน 2026:** ข้อมูลสุขภาพอยู่ในบัญชี Gmail ส่วนตัว ถ้าเข้าบัญชีไม่ได้หรือเจ้าของบัญชีย้ายงาน ระบบและข้อมูลไปกับบัญชี มาตรการลดความเสี่ยงคือสำรองข้อมูลทุกสัปดาห์ และเพิ่มบัญชี Google สำรองก่อนเริ่มใช้ข้อมูลจริง
- ฐานของการเก็บข้อมูลผู้ป่วยตามที่ PO ระบุ: ใช้เพื่อการเฝ้าระวังและควบคุมโรค ซึ่งเป็นการให้บริการด้านสุขภาพของหน่วยงานสาธารณสุข

### ปรับเมื่อ 17 พฤศจิกายน 2026

- **การสำรองทุกสัปดาห์อย่างเดียวไม่ลดความเสี่ยงของบัญชี** ชุดสำรอง ประวัติเวอร์ชัน และถังขยะอยู่ในบัญชีเดียวกับระบบ เมื่อเข้าบัญชีไม่ได้หรือบัญชีถูกลบ ทั้งหมดไปด้วยกัน มาตรการที่แก้แล้วคือบัญชีสำรองของบุคลากร สสอ. อีกคนหนึ่ง ซึ่งอ่านโฟลเดอร์ของระบบได้ และคัดลอกชุดสำรองไปเป็นไฟล์ของตัวเองทุกสัปดาห์ ([spec ข้อ 8](../spec.md#บัญชีสำรอง))
- **ความเสี่ยงที่ PO ยอมรับเพิ่ม** การกู้คืนเสียข้อมูลได้ถึง 7 วัน และเมื่อบัญชีเจ้าของถูกลบ รูปถ่ายหาย
- **เจ้าของบัญชีย้ายงาน** Google ไม่ให้โอน deployment งานตามเวลา และค่าตั้งของ Apps Script ไปบัญชีอื่น การเปลี่ยนเจ้าของจึงเป็นการสร้างชุดใหม่ในบัญชีใหม่แล้วกู้คืนข้อมูล ที่อยู่ของ API เปลี่ยน ซึ่งขัดกับเหตุผลของข้อ 3 ที่ต้องการ ID เดิม ([`operations.md` ข้อ 11](../operations.md#11-ย้ายระบบไปบัญชีอื่น))
- **การกู้ระบบเก่า** Apps Script ไม่กู้ version เก่าให้เอง ต้องส่งโค้ดจาก tag `legacy-v1` ขึ้นไปใหม่ ประโยคในผลที่ตามมาข้อแรกจึงหมายถึงการทำด้วยมือ
- **การกู้คืนเปลี่ยน ID ของไฟล์ฐานข้อมูล** ระบบชี้ไปที่สำเนาของชุดสำรองแทนการเขียนทับไฟล์เดิม ที่อยู่ของระบบที่ผู้ใช้เปิดไม่เปลี่ยน ([spec ข้อ 8](../spec.md#กู้คืน))
- **ที่เก็บข้อมูล** การค้นไม่พบข้อความที่กล่าวถึงบัญชีส่วนบุคคลหรือห้ามบริการคลาวด์ของต่างประเทศโดยเจาะจง แต่ยังอ่านพระราชบัญญัติการรักษาความมั่นคงปลอดภัยไซเบอร์ พ.ศ. 2562 และนโยบายความมั่นคงปลอดภัยสารสนเทศของกระทรวงสาธารณสุขไม่ได้ เรื่องนี้เป็น **Not Verified** และ PO ถามสำนักงานสาธารณสุขจังหวัดก่อนเริ่มใช้ข้อมูลจริง ([ผลการค้น ส่วนที่ 3](../research/data-retention-governance-facts.md))

## ทางเลือกที่ไม่เลือก

- **ออกแบบเฉพาะหน้าจอใหม่บน server เดิม** ไม่เลือก เพราะการมอบหมายงานให้ รพ.สต. และการรวมไข้เลือดออกเข้ากับเหตุการณ์ต้องเปลี่ยนโครงสร้างข้อมูล
- **ย้ายไปฐานข้อมูลและเซิร์ฟเวอร์จริง** ไม่เลือก เพราะมีค่าใช้จ่ายและงานดูแล ขณะที่ปริมาณงานระดับอำเภออยู่ในกำลังของ Sheets
- **สร้าง Apps Script project และไฟล์ Sheet ใหม่** ไม่เลือก PO ต้องการใช้ ID เดิมและมีลิงก์เดียว
- **ใช้บัญชี Google กลางของหน่วยงาน** ไม่เลือกในตอนนี้ PO เลือกบัญชีส่วนตัวและยอมรับความเสี่ยง
- **เขียนข้อมูลของชุดสำรองทับไฟล์เดิมเมื่อกู้คืน** ไม่เลือก Google Sheets ตีความค่าที่ขึ้นต้นด้วย `=` เป็นสูตรเมื่อเขียนกลับ และไฟล์ที่เสียถูกทับจนตรวจสาเหตุไม่ได้
- **สำรองทุกวัน** ไม่เลือก ชุดที่เกินค้างในถังขยะ 30 วัน จำนวนสำเนาที่มีข้อมูลผู้ป่วยจึงเพิ่มเป็นหลายสิบชุด ขณะที่ความเสี่ยงหลักคือการเสียบัญชี ซึ่งความถี่ไม่ช่วย
- **บัญชีสำรองเป็นบัญชีที่สองของ PO** ไม่เลือก เพราะไม่รอดจากกรณีที่ PO ย้ายงาน
