# ADR-0008: วิธีส่งมอบ และจุดที่ต้องขออนุมัติ

* สถานะ: Accepted (PO อนุมัติผ่านการ Merge ของ PR #276)
* วันที่: 2026-11-16
* แก้ไข: 2026-11-17 แก้ตารางจุดอนุมัติและข้อ 3 และเพิ่มข้อ 10 ถึง 14 เมื่อลงรายละเอียดการทดลองใช้และการเริ่มใช้ข้อมูลจริง
* แก้ไข: 2026-11-18 แก้แถวการเรียก Gemini เลื่อนเลขช่วงของการทดลองใช้จาก 6 เป็น 7 และเพิ่มข้อ 15 ถึง 16 เมื่อ PO ย้ายการร่างรายงานสอบสวนด้วย AI เข้ารุ่นแรก ([ADR-0009](0009-ai-drafts-the-investigation-report.md))

## บริบท

โครงการเดิมมีจุดอนุมัติจำนวนมาก: แผน, Issue, Merge, Backup, Deploy, Browser UAT และการตัดสินใจเชิงนโยบายของ D331 อีก 7 เรื่องที่รอผู้ลงนามซึ่งไม่มีตัวตนในบริบทของ สสอ. หนึ่งแห่ง ผลคือ D331 ค้างอยู่ที่ข้อมูลสมมติ

PO เป็นทั้งเจ้าของระบบและผู้ใช้งาน PO ยืนยันว่าระบบยังไม่มีข้อมูลจริง และเลือกใช้ระบบชุดเดียวในช่วงพัฒนา

## การตัดสินใจ

### จุดที่ PO ต้องอนุมัติ

| เรื่อง | เมื่อไร |
|---|---|
| แผนของแต่ละช่วงใน [roadmap](../roadmap.md) | ก่อนสร้าง Issue และเริ่มเขียนโค้ด |
| Merge | ทุก PR หลังตรวจโค้ดและ CI ผ่าน |
| Deploy ขึ้นชุดใช้งานจริง | ทุกครั้ง หลังเริ่มใช้ข้อมูลจริง ด้วยการสั่ง merge PR จาก `main` เข้า `release` |
| การเริ่มใช้ข้อมูลจริง | ครั้งเดียว ตามช่วงที่ 7 ของ roadmap ด้วยการสั่ง merge PR ที่บันทึกวันเริ่มใช้ |
| การเรียก Gemini จริง | สองครั้ง: ก่อนการเรียกครั้งแรกด้วยข้อมูลสมมติในช่วงที่ 6 ของ roadmap และก่อนเปิดการร่างรายงานด้วย AI ของชุดใช้งานจริง (ข้อ 15 และ 16) |
| การลบหรือล้างข้อมูลใน Sheet หรือ Drive | ทุกครั้ง หลังมีชุดสำรองที่ตรวจแล้ว ยกเว้นการหมุนชุดสำรองที่ระบบทำเอง (ข้อ 13) |

### ช่วงพัฒนา

1. มีระบบชุดเดียว ใช้ข้อมูลสมมติเท่านั้น
2. ตราบใดที่ระบบมีแต่ข้อมูลสมมติ การอนุมัติ Merge ของ PO ครอบคลุมการ Deploy ขึ้นชุดนี้และการตรวจบน browser ด้วย Playwright
3. ข้อมูลสมมติต้องแยกจากข้อมูลจริงได้ชัดเจน เช่น ชื่อผู้ป่วยที่เห็นได้ว่าสมมติ ข้อมูลสมมติหมายถึงเหตุการณ์ ผู้ป่วย งาน ผลการทำงาน และรูปถ่าย ส่วนหน่วยบริการ หมู่บ้าน และประชากรเป็นข้อมูลสาธารณะของหน่วยงานและเป็นของจริงได้ และบัญชีของผู้ทดลองใช้เป็นบัญชีของเจ้าหน้าที่จริง (แก้ไขเมื่อ 2026-11-17 ฉบับแรกเขียนว่าชื่อหน่วยงานและชื่อบุคคลต้องเป็นสมมติ)

### หลังเริ่มใช้ข้อมูลจริง

4. มีสองชุดที่แยกกัน: ชุดใช้งานจริง และชุดทดสอบและพัฒนาที่คัดลอกจากโครงสร้างและข้อมูลสมมติ
5. Claude Code ทำงานในชุดทดสอบเท่านั้น ไม่อ่านและไม่เขียนชุดใช้งานจริง
6. ข้อมูลจริงไม่ถูกคัดลอกมาที่ชุดทดสอบ การทดสอบ และ repository

### วิธีทำงาน

7. งานพัฒนาและตรวจโค้ดทำด้วย Claude Code ตาม [`CLAUDE.md`](../../CLAUDE.md)
8. ทุกช่วงเดินตามลำดับงานใน [`CLAUDE.md` ข้อ 5](../../CLAUDE.md) ซึ่งเป็นแหล่งอ้างอิงเดียวของลำดับนั้น
9. ห้าม push ตรงเข้า `main`

### ข้อที่เพิ่มเมื่อ 17 พฤศจิกายน 2026

รายละเอียดอยู่ใน [spec ข้อ 8](../spec.md#ชุดใช้งานจริงและชุดทดสอบ) และ [`operations.md`](../operations.md)

10. การอนุมัติการเริ่มใช้ข้อมูลจริงรวมการอนุมัติให้ล้างข้อมูลสมมติของชุดแรก Claude Code รันคำสั่งเริ่มใช้ข้อมูลจริงหนึ่งครั้งหลังการอนุมัติ ตรวจว่าระบบว่าง แล้วเลิกเข้าถึงชุดนั้นก่อนที่ข้อมูลจริงรายการแรกจะถูกกรอก
11. ชุดทดสอบถูกสร้างจากชุดสำรองของชุดแรกก่อนล้างข้อมูลสมมติ และแยกไฟล์ฐานข้อมูล Apps Script project โปรเจกต์ Cloudflare Pages และ OAuth client จากชุดใช้งานจริง
12. หลังเริ่มใช้ข้อมูลจริง `main` deploy ขึ้นชุดทดสอบเอง และชุดใช้งานจริงตาม branch `release` การอนุมัติ Merge เข้า `main` จึงไม่ทำให้อะไรขึ้นชุดใช้งานจริง
13. การหมุนชุดสำรอง คือการที่ระบบย้ายชุดสำรองที่เกิน 8 ชุดลงถังขยะของ Google Drive เป็นพฤติกรรมของระบบที่ PO อนุมัติครั้งเดียวที่นี่ ไม่ขออนุมัติรายครั้ง
14. ข้อ 5 หมายถึงสี่อย่างที่ Claude Code ไม่เปิด: ไฟล์ฐานข้อมูล โฟลเดอร์ใน Google Drive log ของ Apps Script และหน้าเว็บในฐานะผู้ใช้ การตรวจชุดใช้งานจริงหลัง Deploy ทำได้สองอย่าง คือหน้าล็อกอินเปิดได้ และคำขอตรวจรุ่นที่ไม่ต้องล็อกอิน การหาสาเหตุของข้อผิดพลาดใช้บรรทัดของ log ที่ PO คัดลอกให้

### ข้อที่เพิ่มเมื่อ 18 พฤศจิกายน 2026

รายละเอียดอยู่ใน [spec ข้อ 4](../spec.md#ร่างรายงานสอบสวน)

15. การอนุมัติการเรียก Gemini ด้วยข้อมูลสมมติทำครั้งเดียวตอนเริ่มช่วงที่ 6 ของ roadmap และครอบคลุมการเรียกจากชุดที่ใช้ข้อมูลสมมติและจากชุดทดสอบหลังจากนั้น การทดสอบอัตโนมัติและ CI ใช้คำตอบจำลอง ไม่เรียก Gemini และไม่มีกุญแจของ API
16. การเปิดการร่างรายงานด้วย AI ของชุดใช้งานจริงเป็นการอนุมัติแยกของ PO หลังเริ่มใช้ข้อมูลจริง คำสั่งเริ่มใช้ข้อมูลจริงปิดค่านี้ และลบกุญแจของ API ที่ใช้กับข้อมูลสมมติ การเปิดค่าในหน้าตั้งค่าอย่างเดียวจึงไม่ทำให้ข้อมูลจริงถูกส่ง PO ตั้งกุญแจของ Gemini ระดับชำระเงินในชุดใช้งานจริงและเปิดค่านี้ในหน้าตั้งค่าเอง หลังพิจารณาข้อที่ยังไม่ยืนยันใน [spec ข้อ 11](../spec.md#11-ข้อเสนอที่รอ-po-ยืนยัน) Claude Code ไม่เรียก Gemini ด้วยข้อมูลจริง

## ผลที่ตามมา

- ช่วงพัฒนาเดินเร็วขึ้น เพราะ Merge หนึ่งครั้งนำไปถึงระบบที่ลองใช้ได้
- การตัดสินใจที่ค้างของ D331 (D2/P1/P2/S1/S2/C1/C2) ถูกแทนด้วย ADR ชุดนี้ ซึ่ง PO เป็นผู้ตัดสิน
- ข้อ 2 หมดผลทันทีที่ PO อนุมัติการเริ่มใช้ข้อมูลจริง
- หลังเริ่มใช้ข้อมูลจริง การแก้ข้อผิดพลาดของชุดใช้งานจริงช้าลง เพราะ Claude Code เห็นเฉพาะบรรทัดของ log ที่ PO คัดลอกให้ และต้องทำซ้ำในชุดทดสอบ
- การแยกของข้อ 14 เป็นข้อตกลง ไม่ใช่กลไกทางเทคนิคทั้งหมด วิธีส่งโค้ด API ขึ้นชุดใช้งานจริงซึ่งกำหนดว่าเครื่องพัฒนาถือสิทธิ์ของชุดนั้นหรือไม่ ตัดสินในแผนของช่วงที่ 7
- ไม่มีผู้ตรวจอิสระนอกจาก PO ความถูกต้องพึ่งการทดสอบอัตโนมัติ การตรวจโค้ด และการทดลองใช้ของ รพ.สต. ก่อนเริ่มใช้จริง

## ทางเลือกที่ไม่เลือก

- **คงจุดอนุมัติเดิมทั้งหมด** ไม่เลือก ด้วยเหตุผลในบริบท
- **แยกชุดทดสอบกับชุดใช้งานจริงตั้งแต่วันแรก** เป็นข้อเสนอแรก PO เลือกใช้ชุดเดียวจนกว่าระบบจะผ่าน
- **ขออนุมัติ Deploy แยกทุกครั้งตั้งแต่ช่วงพัฒนา** ไม่เลือก เพราะชุดเดียวที่มีแต่ข้อมูลสมมติไม่มีความเสี่ยงที่จุดอนุมัตินี้ป้องกัน
