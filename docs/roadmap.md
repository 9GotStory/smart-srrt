# Smart SRRT v2 — ลำดับการสร้าง (Roadmap)

> สถานะ: **ร่างรอ Product Owner อนุมัติ** — 16 พฤศจิกายน 2026
> แต่ละช่วงจบด้วยระบบที่ใช้งานได้จริงบนชุดที่ deploy แล้ว ทุกช่วงใช้ข้อมูลสมมติจนถึงช่วงที่ 6

## วิธีทำงานของแต่ละช่วง

1. เสนอแผนของช่วงให้ PO อนุมัติ
2. PO สร้าง Issue ของช่วงด้วย `/to-spec`
3. พัฒนาแบบ test-first ใน branch แล้วเปิด PR
4. ตรวจโค้ด และ CI ผ่านที่ commit เดียวกัน
5. PO อนุมัติ Merge
6. Deploy และตรวจบน browser ด้วย Playwright ตามเกณฑ์เสร็จของช่วง ([ADR-0008](adr/0008-delivery-process-and-gates.md))

## ช่วงที่ 0 — เก็บของเก่า และวางโครง

| งาน | ผู้ทำ |
|---|---|
| ทำ tag `legacy-v1` ที่ commit สุดท้ายของระบบเก่า แล้วลบ `src/`, `tests/`, `tools/` และไฟล์ของระบบเก่าที่ root และย้ายเอกสารเก่าที่เหลือไป `docs/legacy/` | Claude Code |
| วางโครง `backend/` (Apps Script) และ `frontend/` (React) พร้อมการทดสอบและ CI ใหม่ | Claude Code |
| สร้าง OAuth client ใน Google Cloud และเชื่อม repository กับ Cloudflare Pages | PO ตามขั้นตอนที่เตรียมให้ |
| คัดลอกไฟล์ Sheet เป็นชุดสำรอง ตรวจว่าครบ แล้วลบแท็บเก่าและสร้างแท็บตาม [`schema.md`](schema.md) ทำเป็นขั้นสุดท้ายของช่วงนี้ ติดกับการ deploy API ของ v2 ครั้งแรก เพื่อไม่ให้ระบบเก่าค้างอยู่บนฐานข้อมูลที่ถูกล้างแล้ว | Claude Code หลัง PO ยืนยันอีกครั้งก่อนลบ |

เสร็จเมื่อ: หน้าเว็บเปล่าเปิดได้จากที่อยู่จริง เรียก API ได้คำตอบ และ CI ใหม่ผ่าน

ผลข้างเคียง: ระบบเก่าหยุดให้บริการ และกู้คืนได้จากประวัติเวอร์ชันของ Apps Script กับ tag `legacy-v1`

## ช่วงที่ 1 — เข้าสู่ระบบ ผู้ใช้ และหน่วยงาน

- ล็อกอินด้วย Google และตรวจอีเมลกับตาราง `users`
- ผู้ดูแลจัดการผู้ใช้ รพ.สต. และหมู่บ้าน
- session 7 วัน ออกจากระบบ ระงับบัญชี และสั่งออกจากระบบทุกเครื่อง

เสร็จเมื่อ: ผู้ใช้ในตารางเข้าได้ตามบทบาท อีเมลนอกตารางและบัญชีที่ระงับถูกปฏิเสธ และ**เปิดลิงก์จาก LINE บนมือถือจริงแล้วล็อกอินได้**

ถ้าข้อสุดท้ายไม่ผ่าน ให้หยุดและเสนอทางเลือกต่อ PO ก่อนทำช่วงถัดไป ([ADR-0003](adr/0003-google-sign-in-with-email-allowlist.md))

## ช่วงที่ 2 — เหตุการณ์ของผู้ดูแล

- รับแจ้ง ตรวจสอบข่าว ประเมินเกณฑ์ ปิด เปิดใหม่ ยกเลิก
- ผู้ป่วยในเหตุการณ์
- ไทม์ไลน์
- หน้า "งานวันนี้" ส่วนที่ 1–3

เสร็จเมื่อ: ผู้ดูแลเดินเหตุการณ์จากรับแจ้งถึงปิดได้ครบ การแก้ไขพร้อมกันสองหน้าจอถูกปฏิเสธด้วยข้อความที่เข้าใจได้ และการกดซ้ำไม่สร้างรายการซ้ำ

## ช่วงที่ 3 — งานของ รพ.สต.

- มอบหมายงาน และข้อความ LINE พร้อมลิงก์
- หน้า "งานของหน่วย" บนมือถือ รับงาน บันทึกผล แนบรูป
- รพ.สต. แจ้งเหตุการณ์
- หน้า "งานวันนี้" ส่วนที่ 4–5
- กฎสิทธิ์การมองเห็นของ `unit` ครบตาม [`schema.md` ข้อ 6](schema.md#6-กฎสิทธิ์การมองเห็น)

เสร็จเมื่อ: รพ.สต. ทำงานที่ได้รับจนจบบนมือถือ รพ.สต. อื่นเปิดลิงก์เดียวกันแล้วได้คำตอบว่าไม่พบ และข้อความ LINE ไม่มีชื่อผู้ป่วยกับบ้านเลขที่

## ช่วงที่ 4 — ชุดไข้เลือดออก

- โครงชุดโรค และชุดไข้เลือดออก
- เป้าเวลา 3-3-1 และผลการเทียบเป้า
- แบบบันทึกผล HI/CI และรอบติดตาม
- หน้าตั้งค่าเป้าเวลา

เสร็จเมื่อ: เหตุการณ์ไข้เลือดออกได้งานและกำหนดเสร็จตามชุดโรค ผลเทียบเป้าถูกต้องทั้ง 4 แบบ และมีการทดสอบที่พิสูจน์ว่าเพิ่มชุดโรคสมมติอีกชุดได้โดยไม่แก้ตาราง

ก่อนเริ่มช่วงนี้ PO ยืนยันค่าตั้งต้นของรอบติดตาม ([spec ข้อ 5](spec.md#5-ชุดโรค))

## ช่วงที่ 5 — ผู้ดู สรุป ส่งออก และ Dashboard สาธารณะ

- บทบาท `viewer`
- หน้าสรุปภาพรวม
- ส่งออก Excel
- Dashboard สาธารณะพร้อมการซ่อนค่าต่ำกว่า 5

เสร็จเมื่อ: ผู้ดูไม่ได้รับชื่อและบ้านเลขที่จาก API และ Dashboard สาธารณะคำนวณย้อนหาช่องที่ซ่อนไม่ได้

## ช่วงที่ 6 — ทดลองใช้ และเริ่มใช้จริง

1. สำรองข้อมูลอัตโนมัติทุกสัปดาห์
2. ทดสอบเส้นทางเต็มตาม[เกณฑ์ยอมรับของรุ่นแรก](spec.md#10-เกณฑ์ยอมรับของรุ่นแรก)
3. รพ.สต. 1–2 แห่งทดลองใช้ด้วยข้อมูลสมมติ แล้วแก้ตามผล
4. PO ยืนยันว่าผ่าน
5. คัดลอกโครงสร้างและข้อมูลสมมติออกเป็นชุดทดสอบและพัฒนา
6. PO เพิ่มบัญชี Google สำรองให้เข้าถึงโฟลเดอร์ของระบบ
7. ล้างข้อมูลสมมติในชุดแรก
8. **PO อนุมัติการเริ่มใช้ข้อมูลจริง**

หลังข้อ 8 Claude Code ทำงานในชุดทดสอบเท่านั้น และทุก Deploy ขึ้นชุดใช้งานจริงต้องขออนุมัติแยก
