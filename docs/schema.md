# Smart SRRT v2 — โครงสร้างข้อมูล (Schema)

> สถานะ: **Product Owner (PO) อนุมัติผ่านการ Merge ของ PR #276** — 16 พฤศจิกายน 2026
> เอกสารนี้เป็นแหล่งอ้างอิงเดียวของตาราง คอลัมน์ และกฎสิทธิ์การมองเห็น ความต้องการของระบบอยู่ใน [`spec.md`](spec.md) ส่วนที่เป็นข้อเสนอรอ PO ยืนยันรวมอยู่ใน [`spec.md` ข้อ 11](spec.md#11-ข้อเสนอที่รอ-po-ยืนยัน)

## 1. หลักการ

1. **ฐานข้อมูลคือ Google Sheet หนึ่งไฟล์** หนึ่งแท็บคือหนึ่งตาราง แถวแรกเป็นชื่อคอลัมน์
2. **แกนกลางตายตัว** ตารางในข้อ 3 ไม่เปลี่ยนเมื่อเพิ่มโรค ช่องข้อมูลอยู่ในแกนกลางได้ก็ต่อเมื่อทุกโรคใช้ช่องนั้น ช่องเฉพาะโรคอยู่ใน `task_results.data_json` ตามคำนิยามของชุดโรค (ข้อ 5)
3. **ตัวเชื่อมคือ ID** แถวอ้างถึงกันด้วย ID ไม่อ้างเลขแถว ทุกตารางใช้ UUID ยกเว้นสามตารางที่มีกุญแจตามธรรมชาติ: `diseases` ใช้ `disease_code`, `settings` ใช้ `key` และ `sessions` ใช้ `session_hash`
4. **ทุกเซลล์เป็นข้อความ** ทุกแท็บตั้งรูปแบบเป็น plain text เพื่อไม่ให้ Sheets แปลงค่าเอง เช่น บ้านเลขที่ `12/3` กลายเป็นวันที่ หรือรหัสที่ขึ้นต้นด้วยศูนย์เสียเลขศูนย์ ค่าจริงเท็จเก็บเป็น `true` หรือ `false`
5. **เวลา** เก็บเป็น ISO 8601 UTC เช่น `2026-11-16T04:30:00.000Z` คอลัมน์ลงท้ายด้วย `_at` วันที่ที่ไม่มีเวลาเก็บเป็น `YYYY-MM-DD` คอลัมน์ลงท้ายด้วย `_date` หน้าจอแสดงเป็นเวลาไทย
6. **เวลาสองแบบ** คอลัมน์ `_at` ของขั้นตอน เช่น `received_at`, `verified_at`, `notified_at` และ `performed_at` เก็บ**เวลาที่ทำจริง**ซึ่งผู้ใช้กรอก **เวลาที่บันทึก**ของการกระทำเดียวกันอยู่ใน `timeline.recorded_at` หรือ `task_results.recorded_at` ซึ่งระบบใส่ การเทียบกำหนดเสร็จและเป้าเวลาใช้เวลาที่ทำจริง คอลัมน์ `created_at`, `updated_at`, `uploaded_at` และ `logged_at` เป็นเวลาที่ระบบใส่
7. **ไม่ลบแถว** การยกเลิกเปลี่ยน `status` หรือ `stage` และเก็บแถวไว้ `timeline` และ `audit_log` เพิ่มได้อย่างเดียว ข้อยกเว้นเดียวคือ `sessions` ซึ่งลบแถวที่หมดอายุแล้วได้
8. **แก้ไขต้องตรวจ revision** ตารางที่แก้ไขได้มีคอลัมน์ `revision` การเขียนทำภายใต้ lock ตรวจว่า revision ที่ผู้ใช้ถืออยู่ตรงกับในตาราง แล้วเพิ่มค่าขึ้นหนึ่ง
9. **กันการส่งซ้ำ** ทุกคำขอสร้างข้อมูลมี `request_id` ที่ฝั่งหน้าเว็บสร้าง ถ้า `request_id` ซ้ำ server คืนแถวเดิมและไม่สร้างใหม่

ชื่อแท็บและชื่อคอลัมน์เป็นภาษาอังกฤษแบบ `snake_case` ข้อความที่ผู้ใช้เห็นเป็นภาษาไทยและอยู่ในหน้าเว็บ

## 2. ภาพรวมความเชื่อมโยง

```
units ──< users
  │
  ├──< villages
  │
  └──< tasks >── events ──< patients
          │         │
          │         └──< timeline
          └──< task_results ──< attachments

diseases ── events.disease_code
settings, sessions, audit_log
```

## 4. ข้อมูลที่นำมาจากไฟล์เดิม

ระบบใช้ Google Sheet ไฟล์เดิม ก่อนสร้างแท็บใหม่จะคัดลอกทั้งไฟล์เป็นชุดสำรอง แล้วลบแท็บของระบบเก่า ([roadmap ช่วงที่ 0](roadmap.md))

| ข้อมูลเดิม | นำมาใช้ต่อ |
|---|---|
| `AreaMaster` (หมู่บ้าน) | ใช่ แปลงเป็น `villages` และให้ PO ระบุ รพ.สต. ที่รับผิดชอบ |
| `MasterData` เฉพาะรายการโรค | ใช่ แปลงเป็น `diseases` |
| `SystemSettings` เฉพาะชื่อและโลโก้หน่วยงาน | ใช่ แปลงเป็น `settings` |
| เหตุการณ์ ผู้ใช้ แท็บ D331 ทั้ง 7 แท็บ log รายงาน ไฟล์แนบ คลังเอกสาร | ไม่ อยู่ในชุดสำรองเท่านั้น |

รายการนี้เป็นข้อเสนอ PO ยืนยันอีกครั้งก่อนลบแท็บจริง

## 5. ชุดโรค

ชุดโรคเป็นคำนิยามในโค้ดฝั่ง server มีการทดสอบกำกับ และมีโครงดังนี้

| ส่วน | เนื้อหา |
|---|---|
| `code`, `name_th` | รหัสและชื่อชุด |
| `task_types` | ชนิดงานของชุด: `code`, `name_th`, `form_code`, `per_patient` |
| `targets` | เป้าเวลา: `code`, `name_th`, คอลัมน์ที่เป็นจุดเริ่ม, คอลัมน์ที่เป็นจุดสิ้นสุด, ค่าตั้งต้นเป็นชั่วโมง |
| `forms` | แบบบันทึกผล: `code`, `version`, รายการช่อง (`key`, `label_th`, `type`, `required`, ขอบเขตค่า) |
| `rounds` | รอบการทำงาน: `code`, ชนิดงาน, จำนวนวันนับจากวันที่ 0 และเป้าหมายของผล เช่น HI ไม่เกินร้อยละ 5 |

กฎ

- การเพิ่มหรือแก้ชุดโรคไม่เปลี่ยนแท็บและคอลัมน์ใด ๆ
- เมื่อแก้ช่องของแบบบันทึก ให้เพิ่ม `version` แถวเก่าใน `task_results` ยังอ่านได้ด้วยคำนิยามรุ่นเดิม
- server ตรวจ `data_json` ตามคำนิยามก่อนบันทึก ค่าที่ไม่อยู่ในคำนิยามถูกปฏิเสธ
- ค่าที่ผู้ดูแลแก้ได้คือการเปิดปิดชุด เป้าเวลา และจำนวนวันของรอบ ค่าเหล่านี้อยู่ใน `settings` และทับค่าตั้งต้นในโค้ด

ค่าของชุดไข้เลือดออกอยู่ใน [`spec.md` ข้อ 5](spec.md#5-ชุดโรค)

## 6. กฎสิทธิ์การมองเห็น

server ตรวจทุกคำขอตามตารางนี้ คำขอที่อยู่นอกขอบเขตของผู้ใช้ได้คำตอบว่า "ไม่พบ" เหมือนกับรายการที่ไม่มีอยู่จริง

| ข้อมูล | `admin` | `unit` | `viewer` | ไม่ล็อกอิน |
|---|---|---|---|---|
| เหตุการณ์ | ทั้งหมด อ่านและแก้ | เฉพาะที่หน่วยของตนแจ้ง หรือมีงานของหน่วยตน อ่านอย่างเดียว | ทั้งหมด อ่านอย่างเดียว | ไม่ได้ |
| สร้างเหตุการณ์ | ได้ | ได้ ระบบใส่ `reporting_unit_id` เป็นหน่วยของตน | ไม่ได้ | ไม่ได้ |
| ผู้ป่วย รวม `full_name` และ `house_no` | ทั้งหมด อ่านและแก้ | เฉพาะผู้ป่วยที่ผูกกับงานของหน่วยตน อ่านอย่างเดียว | ทั้งหมด อ่านอย่างเดียว | ไม่ได้ |
| งาน | ทั้งหมด สร้าง แก้ ยกเลิก | เฉพาะงานของหน่วยตน รับงานและบันทึกผล | ทั้งหมด อ่านอย่างเดียว | ไม่ได้ |
| ผลการทำงานและรูป | ทั้งหมด | เฉพาะของงานของหน่วยตน | ทั้งหมด อ่านอย่างเดียว | ไม่ได้ |
| ไทม์ไลน์ | ทั้งหมด | รายการของงานของหน่วยตน และรายการเปลี่ยนสถานะของเหตุการณ์ | ทั้งหมด | ไม่ได้ |
| รายชื่อหน่วยงาน หมู่บ้าน และโรค | จัดการ | อ่าน | อ่าน | ไม่ได้ |
| ผู้ใช้ และค่าตั้งระบบ | จัดการ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| ส่งออก | ข้อมูลเต็ม | ไม่ได้ | ตัวเลขสรุป | ไม่ได้ |
| `audit_log` | อ่าน | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| ตัวเลขรวมสาธารณะ ([spec ข้อ 7](spec.md#7-dashboard-สาธารณะ)) | ได้ | ได้ | ได้ | ได้ |

กฎเพิ่มเติมของ `unit`

- เหตุการณ์ที่ รพ.สต. แจ้งเอง รพ.สต. เห็นข้อมูลที่ตนกรอกและสถานะปัจจุบัน ส่วนผู้ป่วยที่ผู้ดูแลเพิ่มภายหลังเห็นได้ตามกฎของผู้ป่วยข้างบน
- งานที่มี `status` เป็น `cancelled` ไม่ให้สิทธิ์เห็นเหตุการณ์และผู้ป่วย
- สิทธิ์คำนวณจากหน่วยปัจจุบันของผู้ใช้ทุกครั้ง การย้ายหน่วยมีผลทันที
- การเป็นหน่วยที่รับผิดชอบหมู่บ้านใน `villages.unit_id` ไม่ได้ให้สิทธิ์เห็นเหตุการณ์ในหมู่บ้านนั้น
