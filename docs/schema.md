# Smart SRRT v2 — โครงสร้างข้อมูล (Schema)

> สถานะ: **ร่างรอ Product Owner อนุมัติ** — 16 พฤศจิกายน 2026
> เอกสารนี้เป็นแหล่งอ้างอิงเดียวของตาราง คอลัมน์ และกฎสิทธิ์การมองเห็น ความต้องการของระบบอยู่ใน [`spec.md`](spec.md)

## 1. หลักการ

1. **ฐานข้อมูลคือ Google Sheet หนึ่งไฟล์** หนึ่งแท็บคือหนึ่งตาราง แถวแรกเป็นชื่อคอลัมน์
2. **แกนกลางตายตัว** ตารางในข้อ 3 ไม่เปลี่ยนเมื่อเพิ่มโรค ช่องข้อมูลอยู่ในแกนกลางได้ก็ต่อเมื่อทุกโรคใช้ช่องนั้น ช่องเฉพาะโรคอยู่ใน `task_results.data_json` ตามคำนิยามของชุดโรค (ข้อ 5)
3. **ตัวเชื่อมคือ ID** ทุกแถวมี UUID ของตัวเอง ไม่อ้างเลขแถว
4. **ทุกเซลล์เป็นข้อความ** ทุกแท็บตั้งรูปแบบเป็น plain text เพื่อไม่ให้ Sheets แปลงค่าเอง เช่น บ้านเลขที่ `12/3` กลายเป็นวันที่ หรือรหัสที่ขึ้นต้นด้วยศูนย์เสียเลขศูนย์
5. **เวลา** เก็บเป็น ISO 8601 UTC เช่น `2026-11-16T04:30:00.000Z` คอลัมน์ลงท้ายด้วย `_at` วันที่ที่ไม่มีเวลาเก็บเป็น `YYYY-MM-DD` คอลัมน์ลงท้ายด้วย `_date` หน้าจอแสดงเป็นเวลาไทย
6. **ไม่ลบแถว** การยกเลิกเปลี่ยน `status` หรือ `stage` และเก็บแถวไว้ `timeline` และ `audit_log` เพิ่มได้อย่างเดียว
7. **แก้ไขต้องตรวจ revision** ตารางที่แก้ไขได้มีคอลัมน์ `revision` การเขียนทำภายใต้ lock ตรวจว่า revision ที่ผู้ใช้ถืออยู่ตรงกับในตาราง แล้วเพิ่มค่าขึ้นหนึ่ง
8. **กันการส่งซ้ำ** ทุกคำขอสร้างข้อมูลมี `request_id` ที่ฝั่งหน้าเว็บสร้าง ถ้า `request_id` ซ้ำ server คืนแถวเดิมและไม่สร้างใหม่

ชื่อแท็บและชื่อคอลัมน์เป็นภาษาอังกฤษแบบ `snake_case` ข้อความที่ผู้ใช้เห็นเป็นภาษาไทยและอยู่ในหน้าเว็บ

## 2. ภาพรวมความเชื่อมโยง

```
units ──< users
  │
  ├──< villages
  │
  └──< tasks >── events ──< patients
          │         │
          │         └──< timeline
          └──< task_results ──< attachments

diseases ── events.disease_code
settings, sessions, audit_log
```

## 4. ข้อมูลที่นำมาจากไฟล์เดิม

ระบบใช้ Google Sheet ไฟล์เดิม ก่อนสร้างแท็บใหม่จะคัดลอกทั้งไฟล์เป็นชุดสำรอง แล้วลบแท็บของระบบเก่า ([roadmap ช่วงที่ 0](roadmap.md))

| ข้อมูลเดิม | นำมาใช้ต่อ |
|---|---|
| `AreaMaster` (หมู่บ้าน) | ใช่ แปลงเป็น `villages` และให้ PO ระบุ รพ.สต. ที่รับผิดชอบ |
| `MasterData` เฉพาะรายการโรค | ใช่ แปลงเป็น `diseases` |
| `SystemSettings` เฉพาะชื่อและโลโก้หน่วยงาน | ใช่ แปลงเป็น `settings` |
| เหตุการณ์ ผู้ใช้ แท็บ D331 ทั้ง 7 แท็บ log รายงาน ไฟล์แนบ คลังเอกสาร | ไม่ อยู่ในชุดสำรองเท่านั้น |

รายการนี้เป็นข้อเสนอ PO ยืนยันอีกครั้งก่อนลบแท็บจริง

## 5. ชุดโรค

ชุดโรคเป็นคำนิยามในโค้ดฝั่ง server มีการทดสอบกำกับ และมีโครงดังนี้

| ส่วน | เนื้อหา |
|---|---|
| `code`, `name_th` | รหัสและชื่อชุด |
| `task_types` | ชนิดงานของชุด: `code`, `name_th`, `form_code`, `per_patient`, `target_code` |
| `targets` | เป้าเวลา: `code`, `name_th`, จุดเริ่มนับ, จุดสิ้นสุด, ค่าตั้งต้นเป็นชั่วโมง |
| `forms` | แบบบันทึกผล: `code`, `version`, รายการช่อง (`key`, `label_th`, `type`, `required`, ขอบเขตค่า) |
| `followups` | รอบติดตาม: ชนิดงาน และจำนวนวันนับจากจุดเริ่ม |

กฎ

- การเพิ่มหรือแก้ชุดโรคไม่เปลี่ยนแท็บและคอลัมน์ใด ๆ
- เมื่อแก้ช่องของแบบบันทึก ให้เพิ่ม `version` แถวเก่าใน `task_results` ยังอ่านได้ด้วยคำนิยามรุ่นเดิม
- server ตรวจ `data_json` ตามคำนิยามก่อนบันทึก ค่าที่ไม่อยู่ในคำนิยามถูกปฏิเสธ
- ค่าที่ผู้ดูแลแก้ได้ (เปิดปิดชุด เป้าเวลา รอบติดตาม) อยู่ใน `settings` และทับค่าตั้งต้นในโค้ด

ค่าของชุดไข้เลือดออกอยู่ใน [`spec.md` ข้อ 5](spec.md#5-ชุดโรค)
