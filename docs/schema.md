# Smart SRRT v2 — โครงสร้างข้อมูล (Schema)

> สถานะ: **Product Owner (PO) อนุมัติผ่านการ Merge ของ PR #276** — 16 พฤศจิกายน 2026
> เอกสารนี้เป็นแหล่งอ้างอิงเดียวของตาราง คอลัมน์ และกฎสิทธิ์การมองเห็น ความต้องการของระบบอยู่ใน [`spec.md`](spec.md) ส่วนที่เป็นข้อเสนอรอ PO ยืนยันรวมอยู่ใน [`spec.md` ข้อ 11](spec.md#11-ข้อเสนอที่รอ-po-ยืนยัน)

## 1. หลักการ

1. **ฐานข้อมูลคือ Google Sheet หนึ่งไฟล์** หนึ่งแท็บคือหนึ่งตาราง แถวแรกเป็นชื่อคอลัมน์
2. **แกนกลางตายตัว** ตารางในข้อ 3 ไม่เปลี่ยนเมื่อเพิ่มโรค ช่องข้อมูลอยู่ในแกนกลางได้ก็ต่อเมื่อทุกโรคใช้ช่องนั้น ช่องเฉพาะโรคอยู่ใน `task_results.data_json` ตามคำนิยามของชุดโรค (ข้อ 5)
3. **ตัวเชื่อมคือ ID** แถวอ้างถึงกันด้วย ID ไม่อ้างเลขแถว ทุกตารางใช้ UUID ยกเว้นห้าตารางที่มีกุญแจตามธรรมชาติ: `diseases` ใช้ `disease_code`, `population` ใช้ `village_code` คู่กับ `year`, `public_snapshot` ใช้ `year`, `month`, `subdistrict` และ `disease_code` ร่วมกัน, `settings` ใช้ `key` และ `sessions` ใช้ `session_hash`
4. **ทุกเซลล์เป็นข้อความ** ทุกแท็บตั้งรูปแบบเป็น plain text เพื่อไม่ให้ Sheets แปลงค่าเอง เช่น บ้านเลขที่ `12/3` กลายเป็นวันที่ หรือรหัสที่ขึ้นต้นด้วยศูนย์เสียเลขศูนย์ ค่าจริงเท็จเก็บเป็น `true` หรือ `false`
5. **เวลา** เก็บเป็น ISO 8601 UTC เช่น `2026-11-16T04:30:00.000Z` คอลัมน์ลงท้ายด้วย `_at` วันที่ที่ไม่มีเวลาเก็บเป็น `YYYY-MM-DD` คอลัมน์ลงท้ายด้วย `_date` หน้าจอแสดงเป็นเวลาไทย
6. **เวลาสองแบบ** คอลัมน์ `_at` ของขั้นตอน เช่น `received_at`, `verified_at`, `first_alerted_at`, `notified_at`, `followed_up_at` และ `performed_at` เก็บ**เวลาที่ทำจริง**ซึ่งผู้ใช้กรอก **เวลาที่บันทึก**ของการกระทำเดียวกันอยู่ใน `timeline.recorded_at` หรือ `task_results.recorded_at` ซึ่งระบบใส่ การเทียบกำหนดเสร็จและเป้าเวลาใช้เวลาที่ทำจริง คอลัมน์ `created_at`, `updated_at`, `uploaded_at` และ `logged_at` เป็นเวลาที่ระบบใส่
7. **ไม่ลบแถว** การยกเลิกเปลี่ยน `status` หรือ `stage` และเก็บแถวไว้ `timeline` และ `audit_log` เพิ่มได้อย่างเดียว ข้อยกเว้นมีสองตาราง: `sessions` ซึ่งลบแถวที่หมดอายุแล้วได้ และ `public_snapshot` ซึ่งถูกเขียนทับทั้งตารางทุกรอบเผยแพร่ เพราะคำนวณใหม่จากตารางอื่นได้เสมอ ข้อยกเว้นอีกอย่างหนึ่งเกิดครั้งเดียว คือคำสั่งเริ่มใช้ข้อมูลจริง ซึ่งล้างข้อมูลสมมติตาม[ข้อ 9](#9-การเริ่มใช้ข้อมูลจริง)
8. **แก้ไขต้องตรวจ revision** ตารางที่แก้ไขได้มีคอลัมน์ `revision` การเขียนทำภายใต้ lock ตรวจว่า revision ที่ผู้ใช้ถืออยู่ตรงกับในตาราง แล้วเพิ่มค่าขึ้นหนึ่ง
9. **กันการส่งซ้ำ** ทุกคำขอสร้างข้อมูลมี `request_id` ที่ฝั่งหน้าเว็บสร้าง ถ้า `request_id` ซ้ำ server คืนแถวเดิมและไม่สร้างใหม่
10. **การกระทำหนึ่งครั้งต้องครบ** Google Sheets ไม่มี transaction การกระทำที่เขียนหลายตาราง เช่น สร้างงานพร้อมแถวไทม์ไลน์ จึงเขียนทั้งหมดภายใต้ lock เดียว และทุกแถวที่เกิดจากคำขอเดียวกันเก็บ `request_id` เดียวกัน ถ้าการเขียนหยุดกลางทาง คำขอเดิมที่ส่งซ้ำจะเติมแถวที่ขาดให้ครบแล้วคืนผลเดิม
11. **ค่าที่ใช้ประเมินเก็บไว้กับงาน** งานเก็บกำหนดเสร็จ และรุ่นของชุดโรคที่ใช้ ไว้กับตัวเองตั้งแต่ตอนสร้าง การแก้เป้าเวลาในหน้าตั้งค่าหรือการแก้ชุดโรคในโค้ดมีผลกับงานที่สร้างหลังจากนั้นเท่านั้น ผลการเทียบเป้าของงานเก่าจึงไม่เปลี่ยนย้อนหลัง
12. **วันนับตามเวลาไทย** วันที่ 0 รอบการทำงาน และ "สิ้นวัน" คำนวณตามเขตเวลา Asia/Bangkok
13. **ค่าที่ผู้ใช้กรอกเป็นข้อความเสมอ** ค่าที่ขึ้นต้นด้วย `=`, `+`, `-` หรือ `@` ต้องไม่ถูกตีความเป็นสูตร ทั้งในไฟล์ฐานข้อมูลและในไฟล์ที่ส่งออก
14. **โครงสร้างมีเลขรุ่น** `settings` เก็บ `schema_version` เมื่อเริ่มทำงาน server ตรวจว่าทุกแท็บมีชื่อคอลัมน์ตรงกับรุ่นที่โค้ดต้องการ ถ้าไม่ตรง server ปฏิเสธทุกคำขอ การเปลี่ยนโครงสร้างหลังเริ่มใช้ข้อมูลจริงทำด้วย migration ที่มีเลขรุ่น ระบบสำรองไฟล์ก่อนและหยุดถ้าสำรองไม่สำเร็จ ทำระหว่างโหมดปิดปรับปรุง และ PO อนุมัติด้วยการสั่ง merge เข้า `release` ([spec ข้อ 8](spec.md#ชุดใช้งานจริงและชุดทดสอบ))

ชื่อแท็บและชื่อคอลัมน์เป็นภาษาอังกฤษแบบ `snake_case` ข้อความที่ผู้ใช้เห็นเป็นภาษาไทยและอยู่ในหน้าเว็บ

## 2. ภาพรวมความเชื่อมโยง

```
units ──< users
  │
  ├──< villages ──< population
  │
  └──< tasks >── events ──< patients
          │         │
          │         └──< timeline
          └──< task_results ──< attachments

events ── report_drafts (ไม่เกินหนึ่งแถวต่อเหตุการณ์)

diseases ── events.disease_code
settings, sessions, audit_log
public_snapshot (คำนวณจาก events, patients, villages และ diseases)
```

## 3. ตารางแกนกลาง

คอลัมน์ `created_at`, `created_by`, `updated_at`, `updated_by` มีในทุกตารางที่แก้ไขได้ และไม่แสดงซ้ำในรายการด้านล่าง คอลัมน์ที่ลงท้ายด้วย `_by` เก็บ `user_id`

### `units` — หน่วยงาน

| คอลัมน์ | ความหมาย |
|---|---|
| `unit_id` | UUID |
| `name` | ชื่อหน่วย เช่น รพ.สต. ก |
| `type` | `sso` (สสอ.) หรือหน่วยบริการชนิดใดชนิดหนึ่ง: `rpst` (รพ.สต.), `rp` (รพ.) หรือ `ssch` (สสช.) ทั้งระบบมีแถว `sso` หนึ่งแถว |
| `active` | หน่วยที่เลิกใช้แล้วมีค่า `false` และไม่ถูกเสนอเป็นผู้รับงาน server ปฏิเสธการเลิกใช้หน่วยที่ยังมีงานที่ไม่เสร็จ ผู้ใช้ที่ `status` เป็น `active` หรือหมู่บ้านในความรับผิดชอบ |
| `revision` | |

### `villages` — หมู่บ้านและหน่วยที่รับผิดชอบ

จังหวัดและอำเภอของทั้งระบบอยู่ใน `settings` เพราะหนึ่งระบบใช้กับอำเภอเดียว

| คอลัมน์ | ความหมาย |
|---|---|
| `village_id` | UUID |
| `subdistrict` | ตำบล ใช้รวมตัวเลขใน Dashboard สาธารณะ |
| `moo` | หมู่ที่ ตรงกับสองหลักท้ายของ `village_code` |
| `village_name` | ชื่อหมู่บ้าน |
| `village_code` | รหัสหมู่บ้าน 8 หลักของกรมการปกครอง ไม่ซ้ำกัน ใช้เชื่อมกับ `population` และใช้ในไฟล์ส่งออก |
| `unit_id` | หน่วยบริการที่รับผิดชอบ หนึ่งหมู่บ้านมีหนึ่งหน่วย ว่างได้เฉพาะหมู่บ้านที่เพิ่งนำเข้าและผู้ดูแลยังไม่ได้กำหนด ใช้เสนอผู้รับงาน ไม่ได้ให้สิทธิ์มองเห็น |
| `active`, `revision` | |

### `diseases` — รายการโรคและภัย

| คอลัมน์ | ความหมาย |
|---|---|
| `disease_code` | รหัสสั้น เช่น `dengue` |
| `name_th` | ชื่อที่แสดง |
| `legal_class` | `dangerous` (โรคติดต่ออันตราย), `surveillance` (โรคติดต่อที่ต้องเฝ้าระวัง) หรือ `other` |
| `investigation_criteria` | ข้อความเกณฑ์สอบสวนของทีม แสดงในขั้นประเมินเกณฑ์ ผู้ดูแลแก้ได้ ว่างได้ |
| `investigate_within_hours` | จำนวนชั่วโมงจากรับแจ้งถึงกำหนดเริ่มสอบสวน ว่างหมายถึงค่าทั่วไป: 12 เมื่อ `legal_class` เป็น `dangerous` และ 24 สำหรับโรคอื่น |
| `pack_code` | ชุดโรคที่โรคนี้ใช้ ว่างได้ ผู้ดูแลเลือกจากชุดที่มีในโค้ด (ข้อ 5) โรคหนึ่งใช้ได้ชุดเดียว |
| `show_public` | `true` เมื่อโรคนี้มีแถวของตัวเองใน Dashboard สาธารณะ `false` เมื่อนับรวมในแถว "โรคอื่น ๆ" ผู้ดูแลแก้ได้ ([spec ข้อ 7](spec.md#โรคที่ไม่แสดงชื่อ)) |
| `active`, `revision` | |

รายการนี้มีโรค `other` ("อื่น ๆ") เสมอ และเลิกใช้ไม่ได้

โรคที่ `legal_class` เป็น `dangerous` และโรค `other` ไม่แสดงชื่อใน Dashboard สาธารณะเสมอ ไม่ว่า `show_public` มีค่าใด และ server ปฏิเสธการตั้ง `show_public` ของโรคเหล่านี้เป็น `true`

### `population` — ประชากรรายหมู่บ้านรายปี

| คอลัมน์ | ความหมาย |
|---|---|
| `village_code` | รหัส 8 หลัก รหัสที่ลงท้ายด้วย `00` คือผู้ที่มีชื่อในทะเบียนของตำบลโดยไม่ระบุหมู่ ใช้รวมเป็นยอดของตำบลเท่านั้น |
| `year` | ปี ค.ศ. ของข้อมูล หน้าจอแสดงเป็น พ.ศ. |
| `male`, `female`, `population` | จำนวนชาย หญิง และรวม ณ สิ้นปีนั้น |
| `households` | จำนวนบ้าน |
| `source` | ที่มา เช่น `dopa` หรือ `manual` |
| `revision` | |

ยอดของตำบลคือผลรวมของทุกแถวที่หกหลักแรกของ `village_code` ตรงกัน

### `users` — ผู้ใช้

| คอลัมน์ | ความหมาย |
|---|---|
| `user_id` | UUID |
| `email` | อีเมล Google ตัวพิมพ์เล็ก ไม่ซ้ำกัน สำหรับที่อยู่ `gmail.com` การเทียบและการตรวจซ้ำไม่นับจุดในชื่อ เพราะ Google ถือเป็นบัญชีเดียวกัน |
| `google_sub` | รหัสบัญชีที่ Google ให้ ระบบบันทึกเมื่อล็อกอินครั้งแรก หลังจากนั้นใช้ค่านี้ยืนยันตัวตน การแก้ `email` ล้างค่านี้ |
| `display_name` | ชื่อที่แสดง |
| `role` | `admin`, `unit` หรือ `viewer` |
| `unit_id` | บังคับเมื่อ `role` เป็น `unit` |
| `status` | `active` หรือ `suspended` แถวของผู้ใช้ไม่ถูกลบ |
| `last_login_at` | เวลาที่ล็อกอินสำเร็จครั้งล่าสุด ว่างเมื่อยังไม่เคยเข้า |
| `revision` | |

เมื่อตารางนี้ว่าง ระบบสร้างผู้ดูแลคนแรกจากอีเมลใน Script Property `BOOTSTRAP_ADMIN_EMAIL`

### `sessions` — การเข้าสู่ระบบ

| คอลัมน์ | ความหมาย |
|---|---|
| `session_hash` | SHA-256 ของ token ตัว token ไม่ถูกเก็บ |
| `user_id` | |
| `created_at`, `expires_at` | อายุ 7 วัน |
| `revoked_at` | มีค่าเมื่อออกจากระบบ การสั่งออกจากระบบทุกเครื่องใส่ค่านี้ในทุกแถวของผู้ใช้นั้น |

### `events` — เหตุการณ์

| คอลัมน์ | ความหมาย |
|---|---|
| `event_id` | UUID |
| `event_no` | เลขที่เหตุการณ์ที่ผู้ใช้เห็นบนหน้าจอและในข้อความ LINE เช่น `2569-0012` คือปี พ.ศ. ของ `received_at` ตามเวลาไทย ตามด้วยลำดับของปีนั้น ออกตอนสร้าง ไม่ซ้ำ และไม่เปลี่ยน |
| `revision` | |
| `stage` | `received`, `verified`, `not_confirmed`, `responding`, `closed` หรือ `void` |
| `disease_code` | อ้าง `diseases` |
| `source_type` | แหล่งข่าว เช่น โรงพยาบาล รพ.สต. อสม. ประชาชน D506 |
| `source_name` | หน่วยงานที่แจ้ง |
| `received_at` | เวลาที่ได้รับแจ้ง |
| `reporting_unit_id` | มีค่าเมื่อหน่วยบริการเป็นผู้แจ้งเข้าระบบ ในกรณีนี้ระบบใส่ `received_at` เป็นเวลาที่ส่ง และใส่ `source_type` กับ `source_name` จากหน่วยนั้น ผู้ดูแลแก้ได้ |
| `village_id` | พื้นที่เกิดเหตุ บังคับ |
| `place_note` | สถานที่เพิ่มเติม เช่น โรงเรียน |
| `summary` | รายละเอียดเหตุการณ์ ห้ามมีชื่อผู้ป่วย |
| `event_type` | `single` (ผู้ป่วยเฉพาะราย) หรือ `outbreak` (การระบาด) กรอกตอนตรวจสอบข่าว |
| `case_count`, `death_count` | จำนวนผู้ป่วยและผู้เสียชีวิตที่ผู้ดูแลกรอก ว่างได้ |
| `verified_with` | บุคคลหรือหน่วยงานที่ใช้ตรวจสอบข่าว ห้ามเป็นชื่อผู้ป่วย |
| `verification_note` | หมายเหตุของการตรวจสอบ |
| `verified_at`, `verified_by` | เวลาที่ตรวจสอบข่าว ผลของการตรวจสอบอยู่ใน `stage` |
| `first_alerted_at` | เวลาที่ทำจริงของการแจ้งเตือนข่าวครั้งแรกสุด ว่างเมื่อยังไม่มีการแจ้งเตือนข่าว ผู้รับและช่องทางของแต่ละครั้งอยู่ใน `timeline` |

การยืนยันว่าแจ้งหน่วยบริการแล้ว และการยืนยันว่าติดตามงานแล้ว ทำกับหลายงานของหน่วยบริการเดียวกันในเหตุการณ์เดียวกันได้ในคำขอเดียว ([spec ข้อ 4](spec.md#ข้อความ-line)) คำขอระบุรายการงานที่อยู่ในข้อความ server เขียน `notified_at` หรือ `followed_up_at` ของทุกงานในรายการ และเพิ่มแถว `task_notified` หรือ `task_followed_up` ใน `timeline` หนึ่งแถวต่อหนึ่งงาน ทุกแถวใช้ `request_id` เดียวกันตามข้อ 1.10 server ข้ามงานที่ถูกยกเลิกหรือมีผลการทำงานแล้ว และการยืนยันว่าแจ้งแล้วข้ามงานที่มี `notified_at` อยู่แล้ว การแก้ `notified_at` ภายหลังบันทึกเป็น `task_edited`

ระบบไม่เก็บตัวข้อความ LINE ผู้รับ และช่องทางที่ใช้แจ้ง ข้อความสร้างที่หน้าเว็บจากข้อมูลที่ผู้ใช้มีสิทธิ์เห็น

`ai_report.enabled` เป็น `true` หรือ `false` ผู้ดูแลแก้ในหน้าตั้งค่า เมื่อเป็น `false` หรือเมื่อ Script Properties ไม่มี `GEMINI_API_KEY` server ปฏิเสธคำขอร่างด้วย AI ([spec ข้อ 4](spec.md#ร่างรายงานสอบสวน))

`synthetic_data` เป็น `true` ตลอดช่วงที่ระบบใช้ข้อมูลสมมติ และทำให้ทุกหน้ามีแถบข้อมูลสมมติ ([spec ข้อ 8](spec.md#8-ข้อกำหนดทั่วไป)) ค่านี้ไม่อยู่ในหน้าตั้งค่า คำสั่งเริ่มใช้ข้อมูลจริงเปลี่ยนค่าของชุดใช้งานจริงเป็น `false` ([ข้อ 9](#9-การเริ่มใช้ข้อมูลจริง)) และชุดทดสอบเป็น `true` เสมอ

`org_contact` คือช่องทางติดต่อของหน่วยงาน ซึ่งผู้ดูแลแก้ในหน้าตั้งค่า และแสดงในหน้าคู่มือกับหน้าการคุ้มครองข้อมูลส่วนบุคคล ([spec ข้อ 4](spec.md#ข้อมูลตั้งต้น))

`backup.last_success_at`, `storage.used_percent` และ `storage.checked_at` เป็นค่าที่ระบบใส่ ผู้ดูแลแก้ไม่ได้ ค่าแรกคือเวลาของชุดสำรองล่าสุดที่ตรวจแล้วว่าครบ สองค่าหลังคือร้อยละของพื้นที่ที่ใช้ของบัญชีเจ้าของกับเวลาที่อ่าน ซึ่งระบบอ่านตอนสำรองและเมื่อผู้ดูแลเปิดหน้าตั้งค่า หน้า "งานวันนี้" ใช้สามค่านี้แสดงแถบเตือน ([spec ข้อ 8](spec.md#สำรองข้อมูล))

### `public_snapshot` — ตัวเลขรวมสาธารณะ

ตารางเดียวที่คำขอของ Dashboard สาธารณะอ่าน ([spec ข้อ 7](spec.md#7-dashboard-สาธารณะ)) ทุกค่าในตารางนี้ซ่อนค่าน้อยแล้ว ตารางนี้จึงไม่มีจำนวน 1 ถึง 4 ระบบเขียนทับทั้งตารางทุกรอบเผยแพร่ ผู้ใช้แก้ไม่ได้ และไม่มี `revision`

| คอลัมน์ | ความหมาย |
|---|---|
| `year` | ปี ค.ศ. ของวันรับแจ้งตามเวลาไทย หน้าจอแสดงเป็น พ.ศ. |
| `month` | เดือนของวันรับแจ้ง `1` ถึง `12` |
| `subdistrict` | ตำบลของหมู่บ้านของเหตุการณ์ ตาม `villages.subdistrict` |
| `disease_code` | โรคที่แสดงชื่อ หรือ `other` สำหรับแถว "โรคอื่น ๆ" ซึ่งรวมโรค `other` โรคติดต่ออันตราย และโรคที่ `show_public` เป็น `false` |
| `events` | จำนวนเหตุการณ์ที่ซ่อนค่าแล้ว: `<5` เมื่อจำนวนจริงเป็น 1 ถึง 4 และจำนวนจริงเมื่อเป็น 5 ขึ้นไป |
| `patients` | จำนวนผู้ป่วยที่ซ่อนค่าแล้ว ตามกฎเดียวกัน และ `0` เมื่อเหตุการณ์ของช่องนั้นไม่มีผู้ป่วย |

- ช่องที่ไม่มีเหตุการณ์ไม่มีแถว หน้าจอแสดงช่องนั้นเป็น 0
- จำนวนของแถว "โรคอื่น ๆ" รวมจากจำนวนจริงของทุกโรคในแถวก่อน แล้วจึงซ่อนค่า
- ระบบคำนวณตารางนี้ทุกเช้าวันจันทร์ตามเวลาไทย และเมื่อผู้ดูแลเปิด Dashboard สาธารณะขณะที่ตารางว่าง การคำนวณใช้กติกาการนับของ [spec ข้อ 6](spec.md#กติกาการนับ) กับเหตุการณ์ที่ `stage` เป็น `verified`, `responding` หรือ `closed`
- เมื่อผู้ดูแลเปลี่ยน `show_public` ของโรคหนึ่งเป็น `false` ระบบลบแถวของโรคนั้นทันที จำนวนของโรคนั้นเข้าแถว "โรคอื่น ๆ" ในรอบถัดไป

### `audit_log` — บันทึกความปลอดภัย

เพิ่มได้อย่างเดียว ใช้ตรวจสอบย้อนหลัง เห็นได้เฉพาะผู้ดูแล

| คอลัมน์ | ความหมาย |
|---|---|
| `log_id` | UUID |
| `logged_at` | เวลาที่ระบบบันทึก |
| `user_id` | ผู้กระทำ ว่างได้เมื่อยังไม่รู้ตัวตน เช่น การล็อกอินที่ถูกปฏิเสธ |
| `action` | เช่น `login`, `login_denied`, `user_created`, `user_updated`, `user_suspended`, `user_reactivated`, `sessions_revoked`, `export`, `ai_request`, `report_downloaded`, `setting_changed`, `access_denied`, `database_restored`, `real_data_started` |
| `target_type`, `target_id` | |
| `detail` | ข้อมูลประกอบที่ไม่มีชื่อผู้ป่วย ข้อความบรรยายเหตุการณ์ หรือ token |

แถว `export` เก็บใน `detail`: ชนิดของไฟล์ ช่วงวันที่ ตัวกรอง จำนวนแถว และการรวมชื่อกับบ้านเลขที่ ([spec ข้อ 6](spec.md#การส่งออก))

แถว `ai_request` ถูกเพิ่มทุกครั้งที่ server ส่งข้อความให้ AI ทั้งที่สำเร็จและไม่สำเร็จ และเก็บใน `detail`: ชื่อรุ่น รุ่นของคำสั่ง จำนวนตัวอักษรที่ส่งและที่ได้รับ จำนวนข้อความอิสระที่ผู้ดูแลเลือกไม่ส่ง และผลหรือรหัสข้อผิดพลาด โดย `target_id` คือ `event_id` แถว `report_downloaded` เก็บว่าไฟล์มีข้อความของ AI หรือเป็นไฟล์ตั้งต้น ทั้งสองแถวไม่มีข้อความที่ส่ง ข้อความที่ AI ตอบ และข้อความในไฟล์ ([spec ข้อ 4](spec.md#ร่างรายงานสอบสวน))

แถว `database_restored` ถูกเพิ่มหลังการกู้คืน และเก็บใน `detail`: เวลาของชุดสำรองที่ใช้ กับจำนวนแถวของแต่ละแท็บ แถว `real_data_started` เป็นแถวแรกของตารางนี้ในชุดใช้งานจริง ([spec ข้อ 8](spec.md#กู้คืน))

## 4. ข้อมูลตั้งต้น

ระบบใช้ Google Sheet ไฟล์เดิม ก่อนสร้างแท็บใหม่จะคัดลอกทั้งไฟล์เป็นชุดสำรอง แล้วลบแท็บของระบบเก่า ([roadmap ช่วงที่ 0](roadmap.md)) ไม่มีข้อมูลใดจากแท็บของระบบเก่าถูกนำมาใช้ต่อ ทุกแท็บเดิมอยู่ในชุดสำรองเท่านั้น

| ข้อมูล | ที่มาของชุดแรก |
|---|---|
| `units` | ผู้ดูแลเพิ่มบนหน้าจอ |
| `villages` และ `population` | ไฟล์สถิติระดับหมู่บ้านรายปีของ[กรมการปกครอง](https://stat.bora.dopa.go.th/new_stat/webPage/statByYear.php) นำเข้าเฉพาะแถวของอำเภอที่ตั้งไว้ใน `settings` ในช่วงที่ 1 |
| หน่วยที่รับผิดชอบของแต่ละหมู่บ้าน | ผู้ดูแลกำหนดบนหน้าจอหลังนำเข้า |
| `diseases` | รายการตั้งต้นด้านล่าง ซึ่ง PO ตรวจก่อนใช้ |
| ชื่อและโลโก้หน่วยงาน | ผู้ดูแลตั้งในหน้าตั้งค่า |

### ไฟล์สถิติของกรมการปกครอง

ตรวจกับไฟล์ระดับหมู่บ้านของเดือนธันวาคม 2568 เมื่อ 16 พฤศจิกายน 2026

- ไฟล์เป็นข้อความ UTF-8 คั่นด้วย `|` หนึ่งแถวมีปีและเดือน รหัสและชื่อจังหวัด รหัสและชื่อสำนักทะเบียน รหัสและชื่อตำบล รหัสและชื่อหมู่บ้าน จำนวนชาย หญิง รวม และจำนวนบ้าน
- หมู่บ้านที่อยู่ในเขตเทศบาลบางส่วนมีสองแถว แถวหนึ่งของสำนักทะเบียนอำเภอ และอีกแถวของสำนักทะเบียนท้องถิ่นเทศบาล ประชากรของหมู่บ้านคือผลรวมของทุกแถวที่รหัสหมู่บ้านเดียวกัน
- แถวที่รหัสหมู่บ้านลงท้ายด้วย `00` ไม่สร้างหมู่บ้าน และถูกเก็บใน `population` เพื่อให้ยอดของตำบลครบ
- ชื่อหมู่บ้านในไฟล์ไม่มีคำว่า "บ้าน" นำหน้า ผู้ดูแลแก้ชื่อได้หลังนำเข้า และการนำเข้าปีถัดไปไม่เขียนทับชื่อที่แก้แล้ว
- ระบบเก็บจำนวนชาย หญิง รวม และจำนวนบ้าน รุ่นแรกแสดงเฉพาะจำนวนรวม
- รหัสหมู่บ้านในไฟล์ที่ไม่พบใน `villages` และหมู่บ้านใน `villages` ที่ไม่พบในไฟล์ ต้องถูกรายงานให้ผู้ดูแลเห็นก่อนบันทึก

### รายการโรคตั้งต้น

เป็นข้อเสนอ PO ยืนยันก่อนช่วงที่ 1 ([spec ข้อ 11](spec.md#11-ข้อเสนอที่รอ-po-ยืนยัน)) รายชื่อและที่มาอยู่ใน[ผลการค้นมาตรฐาน ส่วนที่ 4](research/event-handling-standards.md)

| `legal_class` | ที่มา | จำนวน |
|---|---|---|
| `dangerous` | ประกาศกระทรวงสาธารณสุข เรื่อง ชื่อและอาการสำคัญของโรคติดต่ออันตราย พ.ศ. 2559 และฉบับแก้ไขถึงฉบับที่ 6 พ.ศ. 2569 | 14 |
| `surveillance` | ประกาศกระทรวงสาธารณสุข เรื่อง ชื่อและอาการสำคัญของโรคติดต่อที่ต้องเฝ้าระวัง พ.ศ. 2562 และฉบับแก้ไขถึงฉบับที่ 3 พ.ศ. 2565 | 57 |
| `other` | "อื่น ๆ" และโรคหรือภัยที่ผู้ดูแลเพิ่มเอง | 1 |

- ชื่อโรคใช้ตามประกาศ ผู้ดูแลแก้ชื่อที่แสดงได้ เช่น ประกาศใช้ "ไข้เด็งกี่"
- `show_public` ตั้งต้นเป็น `true` ยกเว้นโรคติดต่อทางเพศสัมพันธ์ เอชไอวี/เอดส์ วัณโรค โรคเรื้อน และไวรัสตับอักเสบ ซึ่งตั้งต้นเป็น `false` PO ตรวจรายชื่อนี้พร้อมรายการโรค โรคที่ผู้ดูแลเพิ่มเองตั้งต้นเป็น `false` ([spec ข้อ 7](spec.md#โรคที่ไม่แสดงชื่อ))
- `pack_code` ตั้งต้นเป็น `aedes` สำหรับ "ไข้เด็งกี่" "ไข้ปวดข้อยุงลาย" และ "โรคติดเชื้อไวรัสซิกา" ([spec ข้อ 5](spec.md#5-ชุดโรค)) และว่างสำหรับโรคอื่น
- ก่อนนำเข้าในช่วงที่ 1 ต้องตรวจว่ามีประกาศฉบับใหม่กว่านี้หรือไม่ มีข่าวว่าคณะกรรมการโรคติดต่อแห่งชาติเห็นชอบร่างที่เพิ่มโรคติดต่อที่ต้องเฝ้าระวังเมื่อกันยายน 2569 แต่ยังไม่พบประกาศ
- `investigation_criteria` และ `investigate_within_hours` ตั้งต้นจากตารางเกณฑ์ออกสอบสวนรายโรคของกองระบาดวิทยา คอลัมน์ "อำเภอ/ศบส." ข้อความที่สกัดจากไฟล์ต้องเทียบกับหน้าต้นฉบับก่อนใช้

## 5. ชุดโรค

ชุดโรคเป็นคำนิยามในโค้ดฝั่ง server มีการทดสอบกำกับ และมีโครงดังนี้

| ส่วน | เนื้อหา |
|---|---|
| `code`, `version`, `name_th` | รหัส รุ่น และชื่อชุด รุ่นเพิ่มขึ้นทุกครั้งที่ชนิดงาน เป้า หรือรอบเปลี่ยน |
| `task_types` | ชนิดงานของชุด: `code`, `name_th`, `form_code`, `per_patient` และคำแนะนำที่แสดงในหน้างาน |
| `targets` | เป้าเวลา: `code`, `name_th`, คอลัมน์ที่เป็นจุดเริ่ม, คอลัมน์ที่เป็นจุดสิ้นสุด, ค่าตั้งต้นเป็นชั่วโมง |
| `forms` | แบบบันทึกผล: `code`, `version`, รายการช่อง (`key`, `label_th`, `type`, `required`, ขอบเขตค่า) |
| `rounds` | รอบการทำงาน: `code`, ชนิดงาน, จำนวนวันนับจากวันที่หน่วยบริการได้รับรายงาน, วิธีคิดกำหนดเสร็จ (จำนวนชั่วโมงหลังได้รับรายงาน หรือสิ้นวันของรอบ) และเป้าหมายของผล เช่น HI ไม่เกินร้อยละ 5 รอบที่ไม่มีชนิดงานใช้เป็นวันครบระยะเฝ้าระวัง |
| `default_diseases` | โรคที่ใช้ชุดนี้ตั้งต้น ใช้ตอนนำรายการโรคเข้า หลังจากนั้นโรคใช้ชุดใดอยู่ใน `diseases.pack_code` |

กฎ

- การเพิ่มหรือแก้ชุดโรคไม่เปลี่ยนแท็บและคอลัมน์ใด ๆ
- ชุดหนึ่งใช้กับหลายโรคได้ เหตุการณ์ใช้ชุดของ `diseases.pack_code` ของโรคปัจจุบัน เมื่อชุดนั้นเปิดใช้
- งานของชุดที่ระบบเสนอมี `pack_code`, `pack_version` และ `round_code` งานของชุดที่ผู้ดูแลเพิ่มเองมี `round_code` ว่าง
- ผลการเทียบเป้าไม่ถูกเก็บในตาราง server คำนวณทุกครั้งที่แสดง จากงาน ผลที่ใช้งานอยู่ และคำนิยามของ `pack_version` ที่งานเก็บไว้
- เมื่อแก้ช่องของแบบบันทึก ให้เพิ่ม `version` แถวเก่าใน `task_results` ยังอ่านได้ด้วยคำนิยามรุ่นเดิม
- server ตรวจ `data_json` ตามคำนิยามก่อนบันทึก ค่าที่ไม่อยู่ในคำนิยามถูกปฏิเสธ
- ค่าที่ผู้ดูแลแก้ได้คือการเปิดปิดชุด เป้าเวลา และจำนวนวันของรอบ ค่าเหล่านี้อยู่ใน `settings` และทับค่าตั้งต้นในโค้ด

ค่าของชุดโรคติดต่อนำโดยยุงลาย (`aedes`) อยู่ใน [`spec.md` ข้อ 5](spec.md#5-ชุดโรค)

### ชนิดงานกลาง

ชนิดงานกลางและแบบบันทึกผลกลางเป็นคำนิยามในโค้ดเช่นเดียวกับชุดโรค ใช้ได้กับทุกเหตุการณ์ งานที่ใช้ชนิดงานกลางมี `pack_code` ว่าง

| `task_type` | ชื่อ | `form_code` | ช่องใน `data_json` |
|---|---|---|---|
| `investigate` | สอบสวนโรค | `investigation` | `summary` (สรุปผล บังคับ) และ `prelim_report_at` (เวลาที่เขียนรายงานสอบสวนเบื้องต้น ว่างได้) |
| `control` | ควบคุมโรค | `general` | `summary` |
| `contact_tracing` | ติดตามผู้สัมผัส | `general` | `summary` |
| `other` | อื่น ๆ | `general` | `summary` |

`performed_at` ของงาน `investigate` คือเวลาที่ออกสอบสวน

กฎเพิ่มเติมของ `unit`

- เหตุการณ์ที่หน่วยบริการแจ้งเอง หน่วยบริการเห็นข้อมูลที่ตนกรอกและสถานะปัจจุบัน ส่วนผู้ป่วยที่ผู้ดูแลเพิ่มภายหลังเห็นได้ตามกฎของผู้ป่วยข้างบน
- งานที่มี `status` เป็น `cancelled` ไม่ให้สิทธิ์เห็นเหตุการณ์และผู้ป่วย คำขออ่านงานนั้นได้คำตอบว่าไม่พบ
- งานที่ไม่ผูกกับผู้ป่วยให้หน่วยบริการเห็นจำนวนผู้ป่วยของเหตุการณ์ และไม่ให้เห็นแถวของผู้ป่วย
- หน่วยบริการแก้ข้อมูลของเหตุการณ์ที่ตนแจ้งไม่ได้หลังส่ง
- ผู้ใช้ทุกคนของหน่วยเดียวกันมีสิทธิ์กับงานของหน่วยเท่ากัน
- สิทธิ์คำนวณจากหน่วยปัจจุบันของผู้ใช้ทุกครั้ง การย้ายหน่วยมีผลทันที
- การเตือนผู้ป่วยซ้ำที่แสดงต่อผู้ใช้หน่วยบริการบอกเพียงว่าชื่อนี้อาจมีอยู่แล้วในเหตุการณ์ และไม่แสดงข้อมูลของผู้ป่วยรายที่หน่วยนั้นไม่มีสิทธิ์เห็น
- การเป็นหน่วยที่รับผิดชอบหมู่บ้านใน `villages.unit_id` ไม่ได้ให้สิทธิ์เห็นเหตุการณ์ในหมู่บ้านนั้น

## 7. ขนาดที่ออกแบบรองรับ

ตัวเลขในตารางเป็นสมมติฐานของการออกแบบ PO ยืนยันก่อนเริ่มช่วงที่ 2 ของ roadmap

| เรื่อง | สมมติฐาน |
|---|---|
| ผู้ใช้ | ไม่เกิน 50 บัญชี ใช้งานพร้อมกันไม่เกิน 10 คน |
| เหตุการณ์ | ไม่เกิน 2,000 เรื่องต่อปี |
| งานและผลการทำงาน | ไม่เกิน 20,000 แถวต่อปี |
| ไทม์ไลน์ | ไม่เกิน 50,000 แถวต่อปี |

ข้อจำกัดของ Apps Script ที่กำหนดการออกแบบ ตรวจกับ[เอกสารโควตาของ Google](https://developers.google.com/apps-script/guides/services/quotas)เมื่อ 16 พฤศจิกายน 2026

- คำขอหนึ่งครั้งทำงานได้ไม่เกิน 6 นาที
- ทำงานพร้อมกันได้ไม่เกิน 30 คำขอต่อผู้ใช้หนึ่งคน API รันในนามเจ้าของบัญชีคนเดียว จึงตีความว่าทั้งระบบรับคำขอพร้อมกันได้ไม่เกิน 30 คำขอ หน้าจอจึงต้องใช้คำขอน้อย และส่งรูปทีละรูป
- เอกสารเดียวกันที่อ่านเมื่อ 17 พฤศจิกายน 2026 มีอีกบรรทัดหนึ่ง คือทำงานพร้อมกันได้ไม่เกิน 1,000 คำขอต่อสคริปต์ และไม่ระบุว่าคำขอของผู้ที่ไม่ล็อกอินนับในโควตา 30 คำขอของเจ้าของบัญชีหรือไม่ การตีความในข้อก่อนหน้าจึงเป็น **Not Verified** พิสูจน์ด้วยการวัดในช่วงที่ 0 ของ roadmap ([ผลการค้นเรื่อง Dashboard สาธารณะ ข้อ 4.2](research/public-dashboard-facts.md))

หน้า "งานวันนี้" ([spec ข้อ 4](spec.md#4-หน้าจอหลัก)) คำนวณจาก `events`, `patients`, `tasks` และผลที่ใช้งานอยู่ใน `task_results` ของงานในกลุ่ม "ผลรอตรวจ" ซึ่งใช้แสดงเวลาที่ทำจริงและป้าย "ผลไม่ถึงเป้า" หน้านี้ไม่อ่าน `timeline` ซึ่งเป็นตารางที่โตเร็วที่สุด ค่าที่หน้านี้ต้องใช้จากไทม์ไลน์จึงเก็บซ้ำไว้ที่แถวของเหตุการณ์และงาน: `events.first_alerted_at` และ `tasks.followed_up_at`

หน้ารายการเหตุการณ์ หน้าสรุปภาพรวม และไฟล์ส่งออก ([spec ข้อ 4](spec.md#รายการเหตุการณ์) และ[ข้อ 6](spec.md#6-สรุปภาพรวมและการส่งออก)) คำนวณทุกครั้งที่เรียก จาก `events`, `patients`, `tasks`, ผลที่ใช้งานอยู่ใน `task_results`, `units`, `villages`, `diseases` และ `population` สามอย่างนี้ไม่มีตารางเก็บตัวเลขสรุป ไม่เก็บเลขสัปดาห์ระบาด และไม่อ่าน `timeline` ตัวชี้วัดการแจ้งเตือนข่าวใช้ `events.first_alerted_at` อัตราป่วยใช้ `population.population` ของปีที่ spec ข้อ 6 กำหนด ไฟล์ส่งออกไม่ถูกเก็บใน Google Drive

Dashboard สาธารณะเป็นข้อยกเว้น ตัวเลขของหน้านี้คำนวณสัปดาห์ละครั้งแล้วเก็บใน `public_snapshot` เพราะรอบเผยแพร่ที่คงที่เป็นส่วนหนึ่งของการคุ้มครองผู้ป่วย ([spec ข้อ 7](spec.md#รอบเผยแพร่)) คำขอของหน้านี้อ่าน `public_snapshot`, `diseases` สำหรับชื่อโรค และ `settings` เท่านั้น และคำตอบเก็บใน cache ของ Apps Script ซึ่งถูกล้างเมื่อเขียน `public_snapshot` ใหม่ ตารางนี้มีไม่เกินหนึ่งแถวต่อโรค ตำบล และเดือนที่มีเหตุการณ์ จึงไม่เกินจำนวนเหตุการณ์ของทุกปีรวมกัน

server อ่านทั้งแท็บในแต่ละคำขอ วิธีนี้พอสำหรับขนาดในตาราง เมื่อ `timeline` หรือ `task_results` เกิน 100,000 แถว ต้องทบทวนการออกแบบ เช่น ย้ายเหตุการณ์ที่ปิดเกินหนึ่งปีไปไฟล์เก็บถาวร

## 9. การเริ่มใช้ข้อมูลจริง

คำสั่งเริ่มใช้ข้อมูลจริงทำงานครั้งเดียวในชุดแรก หลัง PO อนุมัติ และทำงานเฉพาะเมื่อ `synthetic_data` เป็น `true` ลำดับของคำสั่งอยู่ใน [spec ข้อ 8](spec.md#การเริ่มใช้ข้อมูลจริง)

| การกระทำ | ตาราง |
|---|---|
| ล้างทุกแถว เหลือแถวชื่อคอลัมน์ | `events`, `patients`, `tasks`, `task_results`, `attachments`, `report_drafts`, `timeline`, `public_snapshot`, `sessions`, `audit_log` และ `users` |
| เก็บไว้ | `units`, `villages`, `population`, `diseases` และ `settings` |

- ใน `settings` คำสั่งเปลี่ยน `synthetic_data` เป็น `false` เปลี่ยน `public_dashboard.enabled` และ `ai_report.enabled` เป็น `false` และล้าง `public_dashboard.published_at` ค่าอื่นไม่เปลี่ยน
- ไฟล์รูปที่แถวของ `attachments` อ้างถึงถูกย้ายลงถังขยะของ Google Drive ก่อนล้างตาราง
- เมื่อ `users` ว่าง ผู้ดูแลคนแรกถูกสร้างจาก `BOOTSTRAP_ADMIN_EMAIL` เมื่อล็อกอินครั้งแรก
- `events` ว่าง เลขที่เหตุการณ์จึงเริ่มที่ลำดับ 1 ของปีนั้น
- `units` และ `villages.unit_id` ไม่ถูกล้าง PO จึงใส่หน่วยบริการจริงและหน่วยที่รับผิดชอบจริงตั้งแต่ช่วงที่ 1 ของ roadmap คอลัมน์ `created_by` และ `updated_by` ของตารางที่เก็บไว้อ้างถึงผู้ใช้ที่ถูกล้างแล้ว หน้าจอแสดงค่านี้ว่าง
- ชุดสำรองที่คำสั่งสร้างก่อนล้างมีข้อมูลสมมติ และถูกหมุนออกตามรอบภายใน 8 สัปดาห์ ชื่อไฟล์ของชุดนี้บอกว่าเป็นชุดก่อนเริ่มใช้ข้อมูลจริง เพื่อไม่ให้ถูกเลือกตอนกู้คืนชุดใช้งานจริง
